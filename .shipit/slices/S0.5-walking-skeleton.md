# S0.5 Walking skeleton

Status: built
Branch: slice/S0.5-walking-skeleton
Size: S to M

## Goal

Someone can open the web app, sign in with an email and password, see a dashboard that shows their name, roles and clinic read from the database, sign out, and start the whole stack with one command.

## Acceptance criteria

1. **Rewrite.** In the web app, a request to `/api/<path>` is proxied to `API_BASE_URL/<path>`. The destination comes from `API_BASE_URL` (default `http://127.0.0.1:8000`). A test checks the rewrite rule that `next.config.ts` produces. `Set-Cookie` from the API reaches the browser unchanged.
2. **Login page.** `/login` shows an email field, a password field and a "Sign in" button, and has no app shell (no nav, no user menu). It posts to `/api/auth/login`.
3. **Login success.** On 200 the browser goes to `/` and the page shows the signed-in user's name.
4. **Login failure.** On 401 the form shows one fixed message ("Email or password is wrong.") and stays on `/login`. On 422 it shows a fixed "Enter an email and password." message. If the API cannot be reached it shows a fixed "Could not reach the server." message. No message echoes anything the user typed. The password field is cleared after a failure.
5. **Double submit.** The button is disabled while a request is in flight.
6. **Dashboard.** `/` shows the user's full name, roles and clinic name, taken from `GET /auth/me`. This is the one authenticated, clinic-scoped screen.
7. **Guard.** A signed-in-only page (`/` and `/status`) redirects to `/login` when the API returns 401 for `/auth/me`. The check runs on the server, forwards the `dc_session` cookie, and shows no page content before it passes. If the API is down or returns something unreadable, the page shows the error state, not a redirect.
8. **Already signed in.** Opening `/login` while signed in redirects to `/`.
9. **Sign out.** The header shows the user's name and a "Sign out" button. It posts to `/api/auth/logout`, then goes to `/login`. After that, `/` redirects to `/login` and the old cookie gets 401 from the API.
10. **One command.** `make dev` starts PostgreSQL (waits until healthy), applies migrations, then runs the API and the web app together. Ctrl-C stops both. The README steps from clone to a visible login page are updated and tested by following them.
11. **Contract.** `make check` and `pnpm build` pass. CI stays green. The OpenAPI snapshot does not change (this slice adds no API route).

## Changes

- Data: none. No migration.
- API: none. The existing `POST /auth/login`, `POST /auth/logout` and `GET /auth/me` are used as they are.
- UI (`apps/web`):
  - `next.config.ts`: add `rewrites()` for `/api/:path*`.
  - Route groups: `app/(auth)/login/page.tsx` (no shell) and `app/(app)/layout.tsx` (shell and guard). `page.tsx` and `status/` move into `(app)`. The root layout stops wrapping everything in `AppShell`.
  - `features/auth/`: `login-form.tsx` (client component), `sign-out-button.tsx` (client component), `current-user.ts` (server helper: `requireUser()` redirects on 401).
  - `lib/api/client.ts`: add `getCurrentUser(cookieHeader)` with a small shape check, like `getHealth`.
  - `components/app-shell.tsx`: takes the user, shows name, clinic and the sign-out button.
  - `app/(app)/page.tsx`: dashboard card with name, roles, clinic. Empty and error states: roles list is never empty for a valid session; API failure uses the existing `error.tsx`.
  - `components/ui/`: add `input` and `label` from shadcn (copied source, no new package). Both build on `radix-ui`, already installed.
- Tooling: `Makefile` gets `dev` (and `db-up` waits with `--wait`). README and `.env.example` updated.
- Migrations: none.

## Out of scope

- Role-based navigation and per-role screens (S7.1). Every signed-in user sees the same nav.
- A "return to the page you wanted" redirect after login. It adds an open-redirect risk for no gain yet.
- Forgot password, signup, "remember me", rate limiting, CSRF token or Origin check (known gaps in PRODUCT.md).
- A staff list or any new API route. See the decision below.
- Deployment. See the decision below.
- Dockerizing the API or web app.

## Decisions and risks

Your calls, to be recorded in PRODUCT.md on approval:

- **What is the "real data" screen: the signed-in user and clinic from `/auth/me` (recommended).** No new API and no new route to review. It is read from the database and scoped by the clinic in the session, which is enough to prove the chain: browser, rewrite, cookie, API, session, database. Alternative: a "Staff" list (`GET /users`, `clinic_admin` only) that shows the scoping with several rows. Tradeoff: it adds a route, a role decision, and a screen that is not on the roadmap, and S1.1 gives us a better real list soon. I would wait for patients.
- **Deployment: defer (recommended).** The roadmap says optional, data is synthetic, and there is nothing worth showing remotely yet. A host choice (and its cost, secrets and `Secure` cookie setup) is cheaper to make once M2 gives a demo. I would record "deferred to the end of Phase 1" in PRODUCT.md. Alternative: pick a host now (for example one VM running Docker Compose). Say so and I will write a separate slice.
- **Guard in the server layout, not in a Next `proxy.ts` (recommended).** The layout asks the API whether the session is valid. A proxy that only checks "cookie exists" would let a stale cookie through and gives a false sense of safety. Tradeoff: one extra API call per page load, which is the same cost the API already pays on every request. The API remains the real gate: a page without the guard would still get 401 from every data call.
- **`/status` becomes signed-in only.** It lives in the shell, so it moves behind the guard. Tradeoff: you cannot see health from the browser when logged out. `curl /health` still works.
- **Login and logout run in the browser through the rewrite,** not through server actions. This is what the rewrite is for, and the cookie is set by the API directly. Server components still call the API at `API_BASE_URL` with the forwarded cookie.
- **Auto-migrate in `make dev`.** Migrations are idempotent, so running them on every start is safe locally. It is not used in any real deployment path.
- **New dependencies: none.** shadcn `input` and `label` are copied source on the Radix package we already have.

Risks:

- **Rewrite target is fixed at build time** for `next start`. `next dev` reads it on start. Fine for local work. A production build must set `API_BASE_URL` when it builds. Noted for the deployment slice.
- **Rewrite body limits.** Not an issue for login. Re-check at S3.1 (uploads), as PRODUCT.md already says.
- **`COOKIE_SECURE`.** `.env.example` sets it to false for http localhost. A browser test over plain http would drop a Secure cookie, so keep it false locally.
- **Branch base.** Branch from `main` (S0.4 merged in PR #5).
- **Both processes under one `make`.** `make -j2` handles Ctrl-C well on macOS and Linux, but a crash in one process does not stop the other. Acceptable for a dev command.

### Decisions made

- A login response that is not 200, 401, or 422 shows "Could not reach the server." The rewrite returns 500 when the API is down, and the browser never sees a network error in that case. The response body is not shown.
- The email field uses `type="email"`. The browser blocks a malformed address before the request. The 422 message is for when the API returns 422.
- The layout and the dashboard each call `/auth/me`. A dashboard load does it twice. I did not add a request cache.
- A missing page stays on the root not-found screen, without the shell. The shell requires a valid session.
- Only HTTP 401 redirects to `/login`. Any other `/auth/me` failure shows the error page.

### Unsure points

- `router.push` plus `router.refresh` is what moves the browser after login and logout. A full page load would also work. I confirmed both in the browser.
- Pressing Back after sign-out: in this session, Back stayed on `/login`. Opening `/` and `/status` after sign-out does redirect to `/login`, and the API log shows `/auth/me` 401 after logout.
- I could not read the browser cookie jar from the tool. `curl` through `http://localhost:3000/api/auth/login` showed `Set-Cookie: dc_session=...; HttpOnly; Max-Age=43200; Path=/; SameSite=lax` with no `Domain` and no `Secure`. Signing in, reloading, and signing out in the browser shows that cookie is stored and then cleared on the web origin.
