# S2.8 Appointment client maintenance

Status: done
Branch: slice/S2.8-appointment-client-maintenance
Size: M

## Goal

Booking and rescheduling share reliable availability loading and HTTP handling, so a
request-policy fix happens once while each form keeps its own understandable workflow.

## Scope and starting point

Maintenance slice proposed after S2.7, before S3.1; not a roadmap completion or scope
change. Assessment: `docs/architecture-assessment-2026-10-21.md`.
Create the branch only after approval, from the reviewed S2.7 state (currently
`80c4fb0982c68f21337b990114f85ecbe5a64170`), preserving unrelated working-tree edits.

## Acceptance criteria

1. **Shared transport compatibility.** Existing client functions retain their public
   inputs/results and runtime response validation after transport extraction. Server
   reads retain API_BASE_URL/default URL, explicit cookie forwarding and no-store;
   browser requests retain `/api` and same-origin credentials. Existing five-second
   timeout and safe malformed-body/network error results remain. Non-JSON and malformed
   success bodies are rejected by the existing applicable parser; no raw body leaks.
2. **Both availability modes.** Booking sends date, clinician and appointment type;
   rescheduling sends date, clinician and appointment id, preserving original-duration
   semantics and availability for the unchanged inactive clinician. Both show the same
   wall-time slots and loading, closed, empty, forbidden and generic failure copy as now.
   Consumed fields are validated at runtime at least as strictly as now. Wire types
   derive from generated OpenAPI types or explicit projections of those types;
   never cast an unvalidated body to a full generated response.
3. **One lifecycle with cancellation.** Both forms use one feature-local availability
   lifecycle. Changing date, clinician or booking type clears selection and cancels the
   superseded request. Cleanup cancels on unmount. Only the newest active request may
   update slots, selection or error state, including when an old response or its JSON
   parsing resolves/rejects late. Cancellation stays silent. Submit cannot use a slot
   belonging to an earlier input or an in-flight refresh.
4. **Bounded requests.** Availability and booking/reschedule submits now use the existing
   five-second request policy (new hardening: these direct fetches currently lack it).
   A timeout leaves loading/submitting, presents fixed failure text and allows another
   deliberate attempt. Availability cleanup is distinguished from timeout. No mutation
   is automatically retried after timeout or network failure, because it may have committed.
5. **Explicit form workflows.** Keep BookScreen's patient, follow-up and recall entry
   points, their exact URLs/payloads and successful navigation. Keep reschedule's payload
   and calendar redirect; omit clinician_id when unchanged. Keep the synchronous ref
   guard and disabled state: rapid duplicate submits issue one mutation. A normal failed
   submit releases the guard for a deliberate retry. Queue terminal errors still replace
   the form with its supplied closed message. Do not create a universal mutation/form hook.
6. **Useful conflicts.** In both forms, 409 `patient_busy` says “That patient already has
   an appointment then. Pick another time.” A clinician `slot_taken` retains each form's
   current slot-conflict copy. Both clear selection and reload availability. Unknown 409s
   keep the existing generic conflict fallback; existing queue terminal handling keeps
   precedence. Permission, network and other errors use fixed safe copy. Raw backend
   messages/values never render. No backend error codes or contracts change.

## Changes

- Data: none. No migrations.
- API: no backend endpoint, request, response, role or error-code changes.
- Shared web code: extract HTTP mechanics from `apps/web/lib/api/client.ts` into
  `lib/api/transport.ts`, reusing `errors.ts`. Preserve existing client exports/parsers
  and only minimally adapt their request calls. No wholesale migration of endpoints.
- Feature code: a small appointment request module under `features/appointments/`
  owns the touched browser operations, their generated request types/response projections
  and runtime parsing. A local availability hook owns cancellation, stale-result guards,
  selection validity and reload; `TimeSlots` renders. Both screens keep their own
  submission orchestration, terminal states and redirects. Share only proven common
  request/error mechanics, not a generalized workflow engine.
- Generated files: consume existing `schema.d.ts`; do not hand-edit or regenerate it
  without a contract change (none intended).
- Dependencies/services/accounts: none. Installed agent skills are tooling setup only.

## Out of scope

- Moving all existing feature endpoints, types and parsers out of `client.ts`.
- Backend appointment module extraction, query optimization, follow-up/recall redesign.
- Auth, sessions, tenancy/role behavior, audit/timeline writes, transactions or lock order.
- New routes, UI redesign, appointment rules, automatic mutation retries or idempotency.
- New libraries, browser automation, schema generators, migrations or stack changes.
- Changing unrelated forms or fixing unrelated findings; report them separately.

## Decisions and risks

- **Approval required before implementation.** This draft proposes the scope and test
  seams below. Approval covers the intentional improvements in criteria 3, 4 and 6;
  all other observable behavior is preserved. If the implementation needs wider changes,
  stop and revise the brief.
- **Test seams proposed for approval (TDD requirement).** Render BookScreen and
  RescheduleScreen with controlled fetch/time/navigation adapters: catches lifecycle,
  payload, error text, redirects and duplicate mutations; misses actual browser/proxy
  integration. Exercise existing public client functions and touched appointment request
  functions with controlled fetch: catches wire handling and runtime parsing; misses live
  HTTP. Keep the real hook, transport and parsers inside these tests, without internal mocks.
  No tests asserting filenames, private helper calls or hook state structure.
- **Selection/race risk.** Abort alone is insufficient after JSON decoding starts.
  Verify delayed success AND failure cannot override the latest request, including unmount.
- **Cancellation/timeout risk.** Existing isTimeoutError treats AbortError as timeout.
  Preserve old callers while distinguishing explicit availability cancellation locally.
- **Generated types risk.** Some existing parsers validate projections only. Do not
  silently require previously unused wire fields or claim to validate the full shape.
- **Review size.** Stop if transport extraction requires migrating unrelated feature
  logic. This is one branch and one reviewable change; no sealing until developer review.
