# S4.4 Inventory alerts

Status: built
Branch: slice/S4.4-inventory-alerts
Size: M

## Goal

Staff can find inventory needing attention and open its batches to restock or write off expired stock.

## Acceptance criteria

1. **Usable stock.** Keep `stock` as the sum of all transactions, including expired batches. Add `usable_stock`: the sum for batches with no expiry or expiry on/after clinic-local today. Empty items return 0. Neither value is stored. Expiry alone never writes a transaction.
2. **Stock alerts.** An active item has `out_of_stock` when usable stock is 0; otherwise `low_stock` when usable stock is at or below its threshold. These two never overlap. Threshold 0 disables low-stock alerts but not out-of-stock alerts. An item with no batches is out of stock.
3. **Expiry alerts.** An active item has `expiring_soon` if any positive-quantity batch expires from today through today + 30 days, inclusive; `expired` if any positive-quantity batch expired before today. No-expiry and zero-quantity batches trigger neither. An item can have both expiry alerts and one stock alert. All calculations use one clinic-local date per request.
4. **Live results.** Alerts reflect restock, adjustment, consumption, threshold/expiry edits, deactivation and the next clinic day on the next read. Inactive items return no alerts, including in All/Inactive views; their quantities and existing batch `expired` flags remain readable. Reading writes no audit or timeline events.
5. **Filter and paging.** `GET /inventory/items` accepts optional `alert=attention|low_stock|out_of_stock|expiring_soon|expired`. Omission means no alert filter; `attention` means any alert. Combine with existing status, category and search filters before counting/paging; each item appears once. Keep existing ordering and paging limits. Invalid alert is 422. No match returns an empty page with total 0.
6. **Access.** Existing inventory read roles apply: `inventory_admin`, `clinic_admin`, `clinician`; receptionist is 403 and no session is 401. All aggregates and joins stay clinic-scoped. Another clinic's stock cannot change an item's figures, alerts or filtered total; another clinic's detail id stays 404. Existing write permissions and no-echo errors stay intact.
7. **Inventory UI.** `/inventory` adds an alert filter (All, Needs attention, Low stock, Out of stock, Expiring soon, Expired), alert badges and separate Total stock / Usable stock columns. Filters and paging preserve each other; changing a filter resets page to 1. Filtered empty state: “No inventory items match these filters.” Keep existing error/no-access states. Each item links to its detail.
8. **Detail UI.** `/inventory/[id]` shows both totals, item alerts and “Expiring soon” beside qualifying stocked batches. Keep existing expired badges, quantities and restock/adjustment forms. Explain: “Usable stock excludes expired batches. Expiring soon means within 30 days, including today.” Clinicians see the same attention information without write controls.

## Changes

- Data/migrations: none. No stored alert, new table, column, index, job or dependency.
- API: extend only list/detail GET item shapes with `usable_stock: integer` and `alerts: array` of the four alert codes, in order `out_of_stock`, `low_stock`, `expired`, `expiring_soon`. Detail batch shapes add `expiring_soon: boolean` (false for inactive items). Mutation response contracts and transaction history stay unchanged. Add the list query parameter above; regenerate OpenAPI and web types/parsers.
- Implementation: inventory domain rules, repository aggregates/filtering and service views; thin existing inventory routes. Reuse feature-local web screens, rows, links and API client. Do not load the entire inventory into Python or filter a single page in the browser.

## Out of scope

Dashboard cards/counts (S6.2), notifications, saved/dismissed alerts, configurable expiry windows, automatic write-offs, usage forecasts, reorder levels, suppliers/costs, recording consumption shortfalls, and changes to consumption or stock-write rules.

## Decisions and risks

**Approved 2026-10-29:** use usable stock for alerts while preserving ledger totals. This reveals an item whose only stock is expired without silently removing stock; the cost is displaying two totals. Use a fixed 30-day expiry window and inclusive low-stock threshold. Alert on active items only to avoid replenishment noise from retired items; inactive batches remain inspectable. Alerts are calculated on reads, so staff refresh to see changes. Nothing in `.shipit/open.md` blocks this slice; S4.1–S4.3 are sealed. The current checkout is `slice/UI.1-client-dashboard`; build from a verified base containing S4.3 and preserve unrelated work.

### Decisions made

- Calculate each batch's net quantity before summarizing the item, so zero-stock batches do not trigger expiry alerts and filtering happens before paging.
- Keep mutation response models separate from GET response models to preserve the existing write contracts.
- Allow horizontal scrolling on the wider list table at narrow viewport widths.

### Unsure points

- The list has several columns and filters; please judge whether the attention badges and two totals are easy to scan, especially on a narrow screen.
- The aggregate query is the most subtle part: review its clinic-scoped joins and the grouping of transactions by batch.

### Click-through

1. Run `make dev` and sign in as an inventory admin or clinic admin in a synthetic clinic. Create a category and an item with threshold 5.
2. Add batches expiring yesterday, today, in 30 days and in 31 days; restock each. Open the item and compare total and usable stock, and the expired and expiring-soon badges.
3. Open Inventory, choose Needs attention, then combine a category and search. Check each alert filter and the filtered empty state. An item without batches appears out of stock.
4. Restock an unexpired batch until usable stock is above the threshold; refresh and check that Low stock clears. Adjust the expired batch down to zero and check that Expired clears.
5. Sign in as a clinician and open the same item; the totals and badges remain visible without write controls.
