# S4.2 Restock and transactions

Status: built
Branch: slice/S4.2-restock-and-transactions
Size: M (split point named in decisions)

## Goal

An inventory admin can add stock to a batch, write off or correct stock with a reason, and see current stock and the full history for every item. Stock is never typed in or overwritten. It is the sum of an append-only list of transactions.

## Acceptance criteria

### Recording

1. **Restock.** `POST /inventory/batches/{id}/restock` with `{quantity}` returns 201 with the transaction. `quantity` is a whole number from 1 to 1,000,000 (booleans, decimals and strings are 422). The type is `restock`, the reason is null.
2. **Adjust.** `POST /inventory/batches/{id}/adjustments` with `{quantity_change, reason}` returns 201. `reason` is `damaged`, `expired` or `correction` (anything else is 422). `quantity_change` is a whole number, not 0, magnitude up to 1,000,000. `damaged` and `expired` must be negative. `correction` may be either sign. The type is `adjustment`.
3. **No negative stock.** A transaction that would take the batch below 0 is 409 `insufficient_stock`. Nothing is written. The check reads the batch total under a lock on the batch row, so two simultaneous removals of the last units give one 201 and one 409.
4. **Inactive item.** Restock on an inactive item is 409 `item_inactive`. An adjustment is still allowed, so old stock can be written off. Order of checks: 401, role, 422, 404, then 409.
5. **Append-only.** There is no route and no service method that updates or deletes a transaction. The database also refuses `UPDATE` and `DELETE` on the table. A mistake is fixed with a `correction`.
6. **Audit.** Each transaction writes one `inventory_transaction` `create` audit event (no changed fields, no quantity) in the same transaction. If the audit write fails, no transaction row remains.
7. **No echo.** No error body or log line contains a submitted quantity, batch number or id. The test covers 404, 409 and 422.

### Reading stock

8. **Batch quantity.** The batch shape gains `quantity` (sum of its transactions, 0 when none). It is calculated, never stored.
9. **Item stock.** The item shape (list, one item, and write responses) gains `stock` (sum over all its batches). Batches that are expired still count here. How expired stock is treated in alerts is S4.4.
10. **History.** `GET /inventory/items/{id}/transactions?page&page_size` returns `{items, total, page, page_size}`, newest first. Each row has `id`, `type`, `reason`, `quantity_change`, `batch` (`id`, `batch_number`), `recorded_by` (name of the staff member) and `created_at` in the clinic timezone. Paging and 422 rules match `GET /inventory/items`. An item with no transactions returns an empty list.
11. **Roles.** `restock` and `adjustments` need `inventory_admin` or `clinic_admin`. Stock fields and history are read by those two plus `clinician`. `receptionist` is 403 everywhere, no session is 401. The route-walk test still passes.
12. **Tenancy.** Every query filters `clinic_id`. Another clinic's batch or item is 404 with no hint of which part failed. A transaction and its batch must belong to the same clinic (composite foreign key).

### Migration

13. **Migration `0019`** is additive: one new table `inventory_transaction`, plus the trigger that blocks update and delete. Up, down, up works. Checks: `type` in (`restock`, `adjustment`); `quantity_change` not 0 and within ±1,000,000; `restock` implies positive change and null reason; `adjustment` implies a known reason and `damaged` or `expired` implies negative. No existing table changes.

### Web

14. **Item page** shows the item's stock beside the name, a Quantity column on each batch, and a History panel (type, reason, signed change, batch, who, when, pagination, empty state "No stock movements yet.").
15. **Forms.** Each batch row has "Add stock" (quantity) and "Adjust" (signed quantity and reason). Both are hidden for `clinician` (read only) and for an inactive item's restock. Fixed text for 409 `insufficient_stock` and 404, field errors for 422. The batch list refreshes after a save.
16. **List page** shows a Stock column. Low-stock and out-of-stock styling is S4.4, so the number is plain.
17. **Break it once.** The builder removes in turn the batch lock, the non-negative check, the clinic scope on the batch lookup, the inactive-item guard on restock, and the write-role check on one route, sees a test fail each time, restores them, and records it in the review packet.
18. **Visual proof** in `.shipit/proof/S4.2/`.

## Changes

- Data, migration `0019` (additive): `inventory_transaction` with `id`, `clinic_id`, `batch_id`, `type`, `reason` (nullable), `quantity_change` (integer), `created_by_user_id`, `created_at`. It has no `item_id`: the item is always reached through the batch, so a row cannot disagree with its batch. Composite foreign key `(batch_id, clinic_id)` to the existing unique key on `inventory_batch`, and a foreign key to the user. Index on `(clinic_id, batch_id, created_at desc)`. A plain PL/pgSQL trigger raises on `UPDATE` and `DELETE`. No existing table changes.
- API, existing layers: `domain/inventory.py` (types, reasons, limits, sign rules), `models/inventory_transaction.py`, `repositories/inventory_repository.py` (sums, history, locked batch read), `services/inventory_service.py`, `api/inventory.py`. Regenerated `openapi.json` and `schema.d.ts`.

## Decisions and risks

- **Stock is calculated, not stored (recommended).** Quantity is the sum of transactions, so it cannot drift from the history. Tradeoff: every list sums rows. Fine at one clinic. If it gets slow, add a stored balance later. Alternative: a stored `quantity` on the batch updated with each transaction, which is faster but can disagree with the history.
- **Stock lives on batches.** Restock names an existing batch, so expiry is already known and S4.4 and S4.3 can pick the earliest-expiry batch. Tradeoff: two steps for a brand new batch (add batch, then add stock). Alternative: restock accepts a new batch number and expiry and creates both in one step. It is the spec's form, but it duplicates the batch rules. I recommend the two-step form now.
- **Two types, three reasons (recommended).** `restock` and `adjustment` with `damaged`, `expired`, `correction`. The spec also lists transfer and procedure consumption. Transfer is dropped (one clinic). Consumption is S4.3.
- **Cost and supplier stay out.** You asked to confirm this at S4.2. The spec's restock form has cost, but PRODUCT.md puts billing and financial analytics out through M5. Recommendation: keep both out. Say if you want them.
- **Database blocks update and delete.** This is the first trigger in the repo. It makes "append-only" true even for a bug in the service. Tradeoff: one more thing to read in the migration. Tests use throwaway databases, so cleanup is not affected. Alternative: rely on the missing routes only.
- **Adjustments on inactive items are allowed.** Writing off stock of a retired item is real. Restock is not.
- **Whole numbers only,** as decided in S4.1. A smaller unit stands in for fractions.
- **Migration touches no existing table,** so it needs no extra stop. The trigger is new database behavior, so please approve it here.
- **Size.** M. If it runs long, split adjustments (criteria 2, part of 3, 13, 15) into S4.2b and ship restock, stock and history first. I recommend keeping one slice.
- **Branch base.** Current branch is `slice/S4.1-inventory-items` (sealed). Branch from `main` if its PR is merged, otherwise from `slice/S4.1-inventory-items`.
- **Open items:** nothing in `.shipit/open.md` blocks this slice. The appointment concurrency flake may show up in `make check`.

### Decisions the brief left open

- The user foreign key is composite, `(created_by_user_id, clinic_id)` to `app_user`, the same shape as timeline and audit. A transaction cannot point at another clinic's user.
- Restock and adjust return the same transaction shape as a history row.
- A damaged or expired adjustment with a positive change is a 422 `must_be_negative` on `quantity_change`, raised in the service before the batch is looked up. A missing batch with that body is 422, not 404.
- `created_at` is the database clock. The response converts it to the clinic zone (`Asia/Kolkata`). The service does not take a `now` for these writes.
- History on the item page uses page size 20. The `page` query on `/inventory/{id}` is the history page.
- The forms check the same limits locally. A 422 from the API is still mapped to field text.

### Unsure points

- The existing request log line includes the URL path, so the batch id from the path is in that one `dentacircle.request` line. Error bodies and the dentacircle logs do not contain the submitted quantity or the batch number. The no-echo test checks the body and those logs, not the path.
- History is ordered by `created_at` descending, then `id` descending. Two commits in the same microsecond are not ordered by time, because the id is a random uuid.
- The name on a write response is a second read of `app_user` after the flush. The history list joins that user in the one query.

### Break it once

Each change was restored. The suite was not left in the broken state.

1. `adjust` called `get_batch` with `lock=False`. `test_two_removals_of_the_last_units_yield_one_success` failed: both waits timed out, so the result was not one success and one shortfall.
2. `_refuse_negative_stock` returned without raising. `test_a_removal_below_zero_writes_nothing_and_an_inactive_item_can_be_written_off` no longer raised `InsufficientStockError`.
3. `get_batch` selected by id only. The same tenancy test failed on `get_batch(...) is None`, because the other clinic's batch came back.
4. The inactive check was removed from restock only. That test no longer raised `ItemInactiveError`.
5. `post_restock` used `can_read`. `test_every_inventory_route_names_its_roles` failed the write-role set.

### Checklist

- Tenancy: repository reads use `clinic_id`. The transaction points at a batch and a user in the same clinic through composite foreign keys. Another clinic's batch or item is 404. A test asserts `get_batch` on the other clinic is `None`.
- Roles: the route walk names the write routes and the history read. The screen hides the forms for a clinician. The API still returns 403.
- Migration is additive, reverses to `0018_inventory`, and upgrades again. Checks and the trigger are in the migration. Money does not apply. Times are `timestamptz` and shown in the clinic zone. The stock row and its audit are flushed in one transaction. The batch row lock is held while the sum is read.
- The quantity, reason, and sign rules live in the domain and the service. Covered edges: below zero, restock of an inactive item, adjustment of an inactive item, zero, booleans, the range, a positive damaged or expired change, and a correction of either sign.
- No patient data in the new errors, logs, or fixtures. No AI call. Each transaction writes one `inventory_transaction` `create` audit with no changed fields and no quantity.
- The tests failed when the lock, the non-negative check, the clinic scope, the inactive guard, and the write role were removed. See Break it once.
- Nothing here is stored for a later slice. Low-stock styling, consumption, and receptionist access are absent on purpose.
