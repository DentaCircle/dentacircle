# S2.6 Patient timeline

Status: approved
Branch: slice/S2.6-patient-timeline
Size: L (kept as one slice at your request; the old S2.6b is in here)

## Goal

Staff open one patient and see every step of the core loop in order: registered, visit booked, arrived, care recorded, completed, follow-up or recall created, contacted, booked, closed.

## Why a new table

The audit log cannot do this. By decision (S1.2) it stores no values and no direction of a status change, so "arrived" and "completed" look the same. The appointment row only holds its current status, with no time per step. So the steps must be written down when they happen.

## Acceptance criteria

### Recording

1. **Event table.** Each step writes one `timeline_event` row in the same transaction as the change. If the event write fails, the change rolls back. Rows are never updated or deleted. There is no route to write one.
2. **Closed list of kinds.** `kind` is one of the names below, enforced by a check constraint. An event holds the patient, the actor, the time and the id of the one thing it is about. It holds no names, dates, notes or other patient values.

   | Group | Kinds |
   | --- | --- |
   | Patient | `patient_registered` |
   | Visit | `visit_booked`, `visit_rescheduled`, `visit_cancelled`, `visit_arrived`, `visit_started`, `visit_completed`, `visit_no_show` |
   | Care | `care_item_added`, `care_item_started`, `care_item_completed`, `care_item_cancelled`, `care_session_recorded` |
   | Follow-up | `follow_up_created`, `follow_up_updated`, `follow_up_contacted`, `follow_up_booked`, `follow_up_completed`, `follow_up_released`, `follow_up_cancelled` |
   | Recall | the same seven names with `recall_` |

3. **Every write path is covered.** Each existing service path that does one of these steps records its event: registration, booking (also from a follow-up or recall), reschedule, cancel, each status move, care item add and status move (also inside a care session), session save, and every follow-up and recall create, move, contacted, book, complete, release and cancel. A test per kind fails if its call is removed.
4. **Order is stable.** Events in one transaction keep the order they were written (completed visit, then its follow-up closing, then the new follow-up). A `seq` identity column breaks ties on equal times.
5. **No change to the rules.** No status rule, role, audit row or response of an existing route changes. All S0 to S2.5 tests pass unchanged.

### Reading

6. **Route.** `GET /patients/{id}/timeline?page&page_size` returns `{items, total, page, page_size}`, newest first (time, then `seq`). Paging and 422 rules match `GET /follow-ups`.
7. **Item shape.** `id`, `kind`, `occurred_at`, `actor` (`id`, `name`; deactivated users still resolve), and one `subject`. A visit subject has `appointment_id`, type name, clinician name and `starts_at`. A care subject has the item name. A follow-up or recall subject has `due_on` and, for recalls, the type name. Subject details are read live at request time, so a renamed item shows its current name.
8. **Scope.** Only the signed-in clinic's events for that patient. Another clinic's patient is 404. Inactive patients can be read.
9. **Roles and order of checks.** `clinician`, `receptionist`, `clinic_admin` may read. `inventory_admin` gets 403, no session 401. Order: 401, role, 422, then 404.
10. **Not audited.** Reading writes no audit row.

### Web

11. **Page.** `/patients/[id]/timeline` shows entries grouped by clinic-local day, newest first. Each entry has the clinic-local time, a short sentence (for example "Visit completed: Scaling with Dr Rao"), and who did it. Entries link to `/patients/[id]/care` or `/calendar` where one already exists. Empty state: "Nothing has happened for this patient yet." Pagination as on the queues. `inventory_admin` sees "You do not have access." Not found and error states match the care page.
12. **Entry point.** The patient page has a "Timeline" button next to "Care" for the three roles.

### Proof

13. **Core loop in one test.** One API test runs book, arrive, start, record session, complete (with an unfinished item), follow-up created, mark contacted, book from queue, complete that visit, and asserts the exact kind sequence from the timeline route.
14. **Break it once.** Before handover the builder removes one event call from each of visits, care, follow-ups and recalls, sees a test fail, restores it, and records it in the review packet.
15. **Screenshots** in `.shipit/proof/S2.6/` with `index.md` and commit hash:
    1. Full loop timeline (visit, care, follow-up, recall entries, two days).
    2. Empty state for a new patient.
    3. `inventory_admin`: "You do not have access."
    4. Patient page with the Timeline button.
    5. Page 2 of a long timeline.

## Changes

- Data, migration `0014`, additive: new table `timeline_event` with `id`, `seq` (identity), `clinic_id`, `patient_id`, `actor_user_id`, `kind`, `occurred_at`, and nullable `appointment_id`, `care_item_id`, `care_session_id`, `follow_up_id`, `recall_id`. A check allows at most one subject id. Composite FKs to `(…, clinic_id)` on every id so a row cannot point at another clinic. Index on `(clinic_id, patient_id, occurred_at DESC, seq DESC)`. No backfill: the timeline starts when this ships. Existing synthetic patients show an empty timeline.
- API: `GET /patients/{id}/timeline` as in 6 to 10. No other route changes.
- Code, existing layers: `domain/timeline.py` (kinds); `models/timeline_event.py`; `repositories/timeline_repository.py`; `services/timeline_service.py` (`record` and `list`); one added call in each service path from criterion 3. Same pattern as `audit_service.record`.
- UI: `features/timeline/`, the page, the button on `patient-detail.tsx`, client types.
- No new dependency.

## Out of scope

- Backfilling history from before this slice.
- Patient active or inactive changes and detail edits on the timeline. They stay in audit only.
- Care notes, documents, lab work, inventory and messages. Later slices add their own kinds.
- Filters, search, export, or a clinic-wide feed.
- The audit viewer (S7.3). Timeline is a working view, not the compliance record.
- Undo, edit or hide of an entry.

## Decisions and risks

- **Write events, do not derive them (recommended, needs your call).** Reading audit rows and current state cannot show direction or time of a step, as above. Tradeoff: about twenty call sites in sealed services, and no history before this slice. Alternative: a read-only view from current rows, with no migration and no edits to sealed code. It would show visits, items, follow-ups and recalls with their current status, but never when a visit was marked arrived or completed. That does not meet the "shows every step" goal in PRODUCT.md.
- **A second table beside audit (recommended).** Audit keeps its rule of no values and no direction. The timeline stores the direction as a `kind`, because staff need it, and still no patient values. Tradeoff: two writes per step. Alternative: add `kind` to `audit_event`, which breaks the S1.2 decision.
- **One slice, not split (your call).** The follow-up and recall kinds that a split would have put in S2.6b are in this brief. ROADMAP.md keeps a single S2.6. Size is L, the same as S2.5. The four commits under "Review in pieces" keep the diff readable, and commit 2 is grouped by visit, care, follow-up and recall so each can be read alone.
- **Subject details are live.** A renamed care item or a rescheduled visit shows its current data on an old entry. This avoids copying patient values into the event. Tradeoff: an entry may not match what was true that day. The kind and time are always true.
- **Ties inside one transaction.** `occurred_at` is the transaction time, so one completion writes several rows with the same time. `seq` plus flush order gives the order. Risk: a service that records out of order shows it wrong. Criterion 13 pins it.
- **Branch base.** The working tree is on `slice/S2.5-recalls`. Branch from the S2.5 head, or from `main` once the PR merges.
- **Open items:** none in `.shipit/open.md` block this.
