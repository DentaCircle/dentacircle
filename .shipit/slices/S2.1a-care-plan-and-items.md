# S2.1a Care plan and care items

Status: built
Branch: slice/S2.1a-care-plan-and-items
Size: M (first half of S2.1. Care sessions are S2.1b. See the first decision.)

## Goal

A clinician can write a care plan for a patient, add the services it covers, and move each service through planned, started, completed or cancelled. Reception can read the plan.

## Acceptance criteria

### API

1. **Schema.** `alembic upgrade head` creates `care_plan` and `care_item`. `downgrade` to `0007` removes them. Upgrade, downgrade, upgrade works. The database refuses a care item whose status is not one of the four, and refuses a plan or item that points at a patient or plan of another clinic.
2. **Create a plan.** `POST /patients/{id}/care-plans` with `{title}` returns 201 with the plan: `id`, `patient_id`, `title`, `created_at`, `is_open` (false, no items yet), `items` (empty). The title is trimmed, 1 to 200 characters. A blank or longer title, or an extra field, returns the standard 422 without echoing the value and writes nothing.
3. **Add an item.** `POST /care-plans/{id}/items` with `{name}` returns 201 with the item: `id`, `name`, `status` `planned`, `created_at`. Same name rules as the title. Duplicate names are allowed.
4. **Read.** `GET /patients/{id}/care-plans` returns every plan of the patient, newest first, each with its items oldest first. `is_open` is true when at least one item is `planned` or `started`. A plan with only completed or cancelled items is not open. A patient with no plans returns an empty list.
5. **Rename.** `PATCH /care-plans/{id}` with `{title}` and `PATCH /care-items/{id}` with `{name}` return the updated plan or item. Extra fields, including `status`, return 422. An item that is `completed` or `cancelled` cannot be renamed: 409 `invalid_status`.
6. **Status.** `POST /care-items/{id}/status` with `{status}` where status is `started`, `completed` or `cancelled` returns the item. Allowed moves only: `planned` to `started`, `completed` or `cancelled`; `started` to `completed` or `cancelled`. Every other pair, including the same status again and any move out of `completed` or `cancelled`, returns 409 `invalid_status` and changes nothing. `planned` or an unknown value returns 422 on `status`. There is no undo.
7. **Who may do what.** Write routes (create plan, add item, rename, status): `clinician` and `clinic_admin`. `GET`: also `receptionist`. `inventory_admin` gets 403 on everything. No session gets 401. A forbidden request changes nothing and writes no audit row.
8. **Order of checks.** 401, then role, then 404, then 422 on the body, then 409. A bad body is a 422 even when the move would also be a 409.
9. **Inactive patient.** A plan or item cannot be added for an `inactive` patient: 409 `patient_inactive`. Reading, renaming and moving existing items still work, so open care can be wrapped up.
10. **Tenancy.** Clinic A gets 404 on every route for clinic B's patient, plan or item, and `GET` never lists B's plans.
11. **Audit.** One `audit_event` in the same transaction as each successful write. `entity_type` `care_plan` with `create` or `update` (`changed_fields` `["title"]`). `entity_type` `care_item` with `create`, `update` (`["name"]`) or `status_change` (`["status"]`). No titles, names or status values are stored. If the audit write fails, nothing is saved. A rejected request writes nothing.
12. **No double move.** The item row is locked. Two requests for the same move at once give one 200 and one 409 (two real sessions, as in S1.5). Adding two items to one plan at once creates both.
13. **Contract and checks.** The route-walk test passes. `openapi.json` and `schema.d.ts` are regenerated. `make check` and `make web-build` pass.

### Web

14. **Care page.** `/patients/[id]/care` lists the plans, newest first, each with its items and a status badge ("Planned", "Started", "Completed", "Cancelled") and an "Open" or "Finished" mark from `is_open`. Empty state: "No care plans yet." The patient page links to it. A load failure shows "Care could not be loaded." A 403 shows "You do not have access." and a 404 shows not found.
15. **Writers see actions.** `clinician` and `clinic_admin` see "New care plan" (a title field), "Add item" on each plan (a name field), and per item: "Start" (planned), "Complete" (planned or started), "Cancel" (planned or started) and "Rename". "Complete" and "Cancel" ask first ("Mark as completed?", "Cancel this item?", with "Yes" and "Keep"). `receptionist` sees the plans and no actions. The API check in 7 stays the real rule.
16. **Outcomes.** Every action sends one request even on a double click. On success the page reloads with a notice ("Care plan added.", "Item added.", "Item updated.", "Marked started.", "Marked completed.", "Item cancelled."). On 409 `invalid_status` "This care item has already changed." and a reload. On 409 `patient_inactive` "This patient is inactive." On 422 a message next to the field. On 403 "You do not have access." Other failures "Something went wrong." An unknown `notice` value is ignored.
17. **No clinical fields.** The forms ask for a title and a service name only. Helper text under the item field: "Service name only. No clinical notes."

### Proof that it works

18. **Tests that can fail.** Each rule in 2 to 12 has a test that fails if the rule is removed. The transition test walks all 16 status pairs (4 by 4) from a table written in the test, not read from the code. The role test walks every role by every write route, and checks the rows and the audit table are unchanged on 403. Before handing over, the builder breaks each of these once on purpose (role check, row lock, transition table, tenancy scope), sees a test go red, and restores it. The result goes in the review packet. Web tests assert on what the user sees (button names, notices, requests sent).
19. **Screenshots of the real app** on synthetic data, in `.shipit/proof/S2.1a/` with an `index.md` and the commit hash:

    4. The same page as a receptionist: plans, no actions.
    5. A stale tab: "This care item has already changed."

## Changes

- Data (`clinic_id` and `created_at` on both, UUID ids):
  - `care_plan`: `id`, `clinic_id`, `patient_id`, `title` (varchar 200). Unique `(id, clinic_id)`. Composite FK `(patient_id, clinic_id)` to `patient`. Index `(clinic_id, patient_id, created_at)`.
  - `care_item`: `id`, `clinic_id`, `care_plan_id`, `name` (varchar 200), `status` (text, check in the four statuses, default `planned`). Composite FK `(care_plan_id, clinic_id)` to `care_plan`. Index `(clinic_id, care_plan_id, created_at)`.

## Out of scope

- Care sessions, linking care to an appointment, and anything that completes an item from a visit (S2.1b).
- Incomplete-care detection and follow-ups (S2.2, S2.3). No queue, no due dates.
- Notes, tooth or area, cost, priority, order of items, a service catalog, and links to inventory rules (S4.3).
- Delete, undo, cancel-whole-plan, and a plan status. Cancel items one at a time.
- Showing care on the timeline (S2.6) or the calendar. Role-based nav (S7.1).

## Decisions and risks

Your calls (my recommendation first):

- **Split S2.1 in two (recommended).** The roadmap warned S2.1 might be too big. Plan, items and sessions need three tables, two status flows, the appointment link and a second UI. Together that is about 30 criteria, which does not fit one review. S2.1a is plan and items, with no appointment. S2.1b is the care session against an arrived or in-progress visit, and it moves items through the status method built here. Tradeoff: nothing in S2.1a touches a visit, so the loop is not visible yet. If you agree I update ROADMAP.md to S2.1a and S2.1b and leave S2.2 onward unchanged.
- **Writers are clinician and clinic_admin (recommended).** A care plan is the clinician's record. Reception can read it because the coordinator queue (S2.4) needs to see unfinished care. Alternative: reception writes too. Simpler, but the desk could mark care completed that the clinician never did.
- **No plan status (recommended).** A plan is open while any item is planned or started. One fewer state to keep in sync. Alternative: a stored plan status, with rules for cancelling a plan that still has open items.
- **Item is a free-text service name (recommended).** No catalog, no tooth, no notes. Names like "Root canal, visit 1" are what the clinic writes today. Risk: S4.3 needs to tie a service to stock rules, and free text may make that a manual mapping. A later additive link (to an appointment type or a catalog) is cheap.
- **Manual status route now (recommended).** The transition rules and audit are built and tested once here, and S2.1b calls the same service method. Risk: after S2.1b a clinician can still mark an item completed without a session. S2.1b decides whether to tighten that.
- **Inactive patient (recommended).** No new care for them, but open items can be finished or cancelled. Mirrors booking.
- **No undo.** A wrong Complete or Cancel cannot be reversed in the product, as with appointment status. This is the same open item in `.shipit/open.md`. Confirms guard the two final moves.

Risks:

- Names are free text a clinician types. They can drift toward clinical detail. The UI says "No clinical notes" and there is no notes field, but the product cannot stop it. Names stay out of audit rows and logs.
- The care page loads every plan of a patient with no paging. Fine for a handful of plans, as the spec expects (30 to 100 care plans in total). Add paging if a patient ever has many.

### Decisions the brief did not settle

- A create audit stores `changed_fields: []`, the same as a new patient. A rename stores `["title"]` or `["name"]`. A status move stores `["status"]`.
- Renaming to the same text still writes an update audit.
- Renaming an item locks the row, so it cannot race a status move. Adding an item does not lock the plan, so two adds both succeed.
- The 404 lookup does not lock and does not treat an inactive patient as missing. Inactive is a 409 after the body is valid.
- Patching a plan returns the plan and its items. Patching an item, or changing its status, returns the item only.
- Plans sort by `created_at` descending, then id. Items sort by `created_at` ascending, then id.
- A missing patient or plan shows "Not found." A 409 for an inactive patient stays on the form. A 409 for a stale status reloads with "This care item has already changed."
- The Care link is on every ready patient page, including reception and an inactive patient.
- The page is a client component, because it passes the submit function into the form.

### Unsure points

- A rename that does not change the text still writes an audit row. The brief did not say to skip that.
- Two items inserted in one database transaction share `created_at`, so their order falls back to the id. Separate requests get different times.
- The page loads every plan. The brief accepts no paging.
- A clinician can still mark an item completed with no care session. That is left for S2.1b.
- The saved screenshots are the narrow browser frame (891 wide), so they show the mobile header.
