# S3.3 Lab work

Status: built
Branch: slice/S3.3-lab-work
Size: L (kept as one slice at your request; the lab result document is in here)

## Goal

Staff record a piece of external lab work for a patient, move it from pending to ready (back at the clinic) to collected (the patient has taken it), attach the returned lab result as a document, see it on the patient and on one clinic-wide Lab list, and when it is ready the patient lands on the follow-up queue.

## Acceptance criteria

### Record

1. **Create.** `POST /patients/{id}/lab-work` with `{title, expected_on?, appointment_id?}` returns 201 and the lab item. `title` is trimmed, 1 to 200 characters (same rule as care item names). `expected_on` is an optional clinic-local date, today through 365 days ahead (same window as follow-up dates). Status starts as `pending`. No other fields: no notes, description, lab name or cost.
2. **Related visit.** `appointment_id`, if given, must be a visit of this patient in the caller's clinic. Anything else is 404 with no hint of which part failed. The visit's status does not matter. It is shown on the item as `appointment` (`id`, `starts_at` in the clinic offset, `type_name`), read live, or null.
3. **Inactive patient.** Creating lab work is 409 `patient_inactive`. Listing and status moves on existing items still work (as for care items).
4. **Audit and timeline on create.** One `lab_work` `create` audit event with no changed fields, and one timeline event `lab_work_created`, in the same transaction as the row. If either write fails, no row remains.

### Statuses

5. **Moves.** Statuses are `pending`, `collected`, `ready`, `cancelled`. `POST /lab-work/{id}/status` with `{status}` takes the targets `ready`, `collected`, `cancelled`. Allowed: `pending` to `ready` or `cancelled`, `ready` to `collected` or `cancelled`. `collected` and `cancelled` are final. A patient cannot collect work that is not ready, so `pending` to `collected` is refused. The same status again, a move out of a final status, or `pending` as a target is 409 `invalid_status`. An unknown value is 422. No undo.
6. **Audit and timeline on move.** Each move writes one `lab_work` `status_change` audit event with `["status"]` (never the direction) and one timeline event (`lab_work_ready`, `lab_work_collected`, `lab_work_cancelled`), in the same transaction.
7. **Locking.** The patient row is locked first, then the lab row, then any follow-up (the same order S2.2 and S2.4 use). Two simultaneous `ready` calls on one item give one 200 and one 409, and one follow-up row.

### Ready puts the patient on the queue

8. **No open follow-up.** Moving to `ready` for an active patient with no open follow-up creates one: status `scheduled`, `due_on` = clinic-local today, no visit. It writes the usual `follow_up` `create` audit event and `follow_up_created` timeline event.
9. **Open follow-up exists.** A `scheduled` or `contacted` follow-up with `due_on` later than today moves to today. Its status stays. A follow-up already due, or one that is `booked`, is not changed. When the date moves, one `follow_up` `update` audit event lists `["due_on"]` and one `follow_up_updated` timeline event is written. When nothing changes, neither is written.
10. **Inactive patient.** Marking ready still works. No follow-up is written or changed.
11. **Collected and cancelled touch nothing.** Only `ready` affects follow-ups. A patient collecting the work does not close the follow-up. The coordinator closes it, as for finished care (S2.4b).

### Views

12. **Patient list.** `GET /patients/{id}/lab-work?page&page_size` returns `{items, total, page, page_size}`, newest first, every status. Unknown patient is 404. Paging and 422 rules match `GET /patients/{id}/documents`.
13. **One item.** `GET /lab-work/{id}` returns one lab item with its `patient`, in the shape of the clinic list (14). Unknown id or another clinic's is 404. The Documents page uses it for its heading.
14. **Clinic list.** `GET /lab-work?view=open|all&page&page_size`. `open` (default) is `pending` and `ready`, work the patient has not yet collected. `all` adds `collected` and `cancelled`. Order: `expected_on` ascending with empty dates last, then oldest created first. Each item has `id`, `status`, `title`, `expected_on`, `overdue`, `appointment`, and `patient` (`id`, `display_id`, `full_name`, `phone`). `overdue` is calculated from the clinic-local date: true only for a `pending` item whose `expected_on` is before today (the work is late). A `ready` item is never overdue. It is never stored. Inactive patients' items are included (open work still has to be finished or cancelled).
15. **Roles and order of checks.** `clinician`, `receptionist`, `clinic_admin` read and write. `inventory_admin` gets 403, no session 401. Order: 401, role, 422, 404, then 409.
16. **Tenancy.** Every query filters `clinic_id`. Another clinic's patient, visit or lab item is 404.
17. **No echo.** No error body or log line contains the title or a submitted id. A test checks the 404, 409 and 422 paths.

### Lab result document

These copy the S3.2 link rules for visits and follow-ups. The upload, the file routes and the viewer are unchanged.

18. **Column.** A document may also link to one lab item, optional and independent of the visit and follow-up links. The link is stored on the document row. A lab item may have many documents. A document with no link stays the default.
19. **Item shape.** The document item gains `lab_work` (`id`, `title`, `status`, or null), read live. The viewer page shows it as text next to the visit and follow-up links.
20. **Set and clear.** `PATCH /patients/{id}/documents/{document_id}` also takes `lab_work_id`: a UUID sets it, `null` clears it, omitted stays. An empty object is still 422. The roles and the order of checks from S3.2 are unchanged.
21. **Same patient, same clinic.** The lab item must belong to this patient in the caller's clinic. Anything else is 404 with no hint of which part failed. The status of the lab item does not matter (a collected or cancelled one still counts as history).
22. **Inactive patient.** Changing the lab link is 409 `patient_inactive`, as for the other links. Listing and viewing still work.
23. **Link at upload.** `POST /patients/{id}/documents` takes an optional `lab_work_id` query parameter, checked by the rule in 21 before the file is stored. A bad id is 404 and nothing is stored.
24. **Filter.** `GET /patients/{id}/documents` takes an optional `lab_work_id`. An id from another patient or clinic returns an empty list, not 404. Paging and 422 rules stay as they are.
25. **Audit.** A lab link change writes one `document` `update` audit event whose `changed_fields` includes `lab_work_id` (name only, never the id, never direction). A change that leaves the row as it was writes none. No timeline event for link changes, as in S3.2.
26. **Web, linking from the lab item.** Each lab row (patient page and clinic page) gets a "Documents" link to `/patients/[id]/documents?lab_work_id=<id>`. On that page:
    - a heading says which lab work it is for (its title, read live with `GET /lab-work/{id}`), with a "Show all documents" link;
    - the list shows only documents linked to it;
    - the upload form sends the same id, so a new result is linked at once;
    - "Link a document that is already uploaded" lists the patient's other documents with a Link button;
    - each linked row has an Unlink button.
    Fixed notices for linked and unlinked, and fixed text for 404 and 409. If a page URL has more than one context id, the visit wins, then the follow-up, then the lab item (as S3.2 already does for the first two).

### Timeline

27. **New kinds.** `lab_work_created`, `lab_work_ready`, `lab_work_collected`, `lab_work_cancelled`, each with `lab_work_id` as its one subject. The timeline item carries the lab id and the current title (read live, like care item names). The web row says "Lab work added", "Lab work ready", "Lab work collected by the patient" or "Lab work cancelled", shows the title, and links to `/patients/[id]/lab`.
28. **Migration safety.** After migration `0017`, up, down, up works. A lab kind with a missing or extra subject id is refused by the check constraint. Downgrade deletes the lab timeline rows first and clears `document.lab_work_id` (said in the migration docstring).

### Web

29. **Patient page** `/patients/[id]/lab`: list with title, status badge, expected date, related visit, who and when it was added, and the Documents link. Add form (title, optional expected date). Row buttons: `pending` shows Mark ready and Cancel. `ready` shows Mark collected and Cancel (cancel asks for confirmation). Buttons match the allowed moves, and final rows have none. Fixed notices per outcome, including "Marked ready. Active patients are added to the Follow-ups queue." Empty, not-found, no-access and error states match the Documents page. The form is hidden for an inactive patient. The patient page links to it.
30. **Clinic page** `/lab` (nav item "Lab"): Open and All switch mapped to `view`, patient name (links to the patient's lab page), ID, title, expected date, Overdue badge, status, the Documents link, and the same row buttons. Empty state "No lab work is open." Pagination as on the follow-up queue. `inventory_admin` sees "You do not have access."
31. **No visit picker.** The visit link on the lab form is not offered on the web in this slice. The API accepts it, the UI does not send it.

### Proof

32. **Break it once.** The builder removes in turn the clinic scope on the lab lookup, the patient scope on the visit check, the patient scope on the document's lab link check, the inactive-patient guard on follow-up creation, and the "final status" rule, sees a test fail each time, restores them, and records it in the review packet.
33. **Visual proof** in `.shipit/proof/S3.3/` (see below).

## Out of scope

- Notes, description, requested date, lab or vendor name, cost, and any billing.
- Edit or rename of lab work, undo of a status, delete.
- More statuses (sent, in progress, received, delivered). The roadmap fixed four.
- A reason on the follow-up ("because lab work is ready"). The coordinator sees the patient, and the patient's Lab page shows why.
- Marking lab work ready automatically when a document is attached. Status stays a manual action.
- Picking a related visit in the web form.
- A document picker from the document side, or a timeline event for link changes.
- Dashboard counts and lab alerts (Phase 6), messages to the patient (Phase 5), inventory use (Phase 4).

## Decisions and risks

- **One L slice (decided by you).** Lab work, its follow-up rule and the result document stay together, as S2.5 did. The commits below keep the review in pieces. If the review runs long, the document link (piece 4) can be the first thing moved out.
- **Timeline constraint change (AGENTS.md stop, approved by you).** Same as S3.2: migration `0017` drops and recreates `kind_known` and `subject_matches_kind` and adds one column. Nothing is lost going up. Going down deletes lab timeline rows. Recommendation: do it here. Alternative: no lab entries on the timeline, which drops 27 and most of 28 and breaks "the timeline shows every step".
- **Statuses follow the patient (decided by you).** Pending is work requested and not yet back. Ready is back at the clinic and waiting for the patient. Collected is the patient taking it from the clinic. We do not track the clinic-to-lab hand-off (no "sent" or "in progress", as the roadmap says). The order is pending, ready, collected, with no skipping, so a patient cannot collect work that is not ready.
- **Cancel from ready.** Allowed, for work that comes back unusable or is no longer wanted. Tradeoff: the follow-up that ready created stays open until the coordinator cancels it.
- **Collected and cancelled final, no undo.** Matches care items and visit status. A mistaken ready would already have created a follow-up, so undo would need a rule for it. It joins the undo items in `.shipit/open.md`.
- **Ready pulls an open follow-up forward (approved by you).** If a follow-up exists for a later date, a ready result makes the patient due today, keeping the status. A booked follow-up is left alone, because a visit is already set. Alternative: leave an existing follow-up untouched, which can hide a ready result for weeks.
- **Follow-up has no visit.** It is created with no `appointment_id`, as the manual one is. Not linking it to the lab's related visit keeps the follow-up rules in S2.2 to S2.4b unchanged.
- **Documents link to the lab item, not the other way round.** A lab item has many documents, and a document has at most one lab item. Same shape as the follow-up link. No many-to-many table.
- **Linking starts from the lab item (recommended).** As in S3.2, no picker on the Documents page alone. Tradeoff: from the unfiltered Documents page you cannot attach a file to lab work. The lab row has the id, so the Documents link is one click.
- **New `GET /lab-work/{id}`.** The Documents heading needs the title, and S3.2 showed that an empty filtered page has no other source. It is the one route beyond the list and move routes.
- **Three roles read and write (decided by you).** `clinician`, `receptionist` and `clinic_admin`. Lab tracking is coordination, so reception does it daily. Care items are clinician-only because they are clinical status. Document roles are unchanged and already match.
- **Inactive patients.** No new lab work and no link changes, but open work can still be marked ready, collected or cancelled, and a ready item writes no follow-up.
- **`overdue` is calculated, not stored,** the same as follow-up timing.
- **Title and filename can hold sensitive text.** Both are free text. They stay out of audit rows, logs, error bodies and timeline rows (read live). Seed and test data is synthetic.
- **Branch base.** S3.2 is sealed. Branch from `main` if its PR is merged, otherwise from `slice/S3.2-document-viewer-and-links`.
- **Open items:** nothing in `.shipit/open.md` blocks this slice.

### Decisions

- One response shape for create, the patient list, the clinic list, and GET one. It includes `created_at` and `created_by` because the patient page shows who added the item. The clinic fields in the brief are all present.
- Every Cancel asks for confirmation, including from pending, because cancelled is final.
- The open empty state is "No lab work is open." The All empty state is "No lab work."
- If GET `/lab-work/{id}` fails or the patient does not match, the documents heading is "Documents for this lab work".
- `pending` is a valid status in the request body so a known item returns 409, not 422. An unknown string is still 422, and that check happens before the lookup.
- A bad title or date is 422 before the patient lookup. A bad visit is 404 before the inactive check.

### Unsure points

- The access log line includes the URL path, so a lab id in `GET /lab-work/{id}` appears there. The title and ids from the body do not. The no-echo test checks the title in the whole log and the submitted id on POST lines.
- The clinic table wraps in a narrow window. The columns are all there.
- Overdue proof for Crown used a database update to a past date. The API will not accept that date on create.

### Break it once

Each guard was removed, the named test failed, and the guard was restored.

- Clinic filter on the joined lab lookup: `test_another_clinic_cannot_see_the_item` failed, `500 == 404`.
- Patient filter on the visit lookup: `test_a_related_visit_must_belong_to_this_patient` failed, `LabWorkNotFoundError` was not raised.
- Patient filter on the document lab link: `test_another_patients_lab_work_is_not_found_and_nothing_is_stored` failed, `DocumentNotFoundError` was not raised.
- Inactive return in `place_follow_up_for_ready_lab`: `test_an_inactive_patient_can_be_marked_ready_without_a_follow_up` failed. The follow-up due date moved to today.
- Final statuses left empty: `test_only_the_written_moves_are_allowed` failed. `can_move("collected", "ready")` became true.
