# S6.2 Inventory attention on the dashboard

Status: approved
Branch: slice/S6.2-inventory-dashboard
Size: S

## Goal

Staff with inventory access can see inventory attention counts on the dashboard and open the exact filtered lists behind them.

## Acceptance criteria

1. Show an Inventory attention section to `inventory_admin`, `clinic_admin` and `clinician`, including users with multiple roles. Add it to the coordination dashboard for clinicians/admins and to the inventory-only dashboard for inventory staff, keeping its inventory and visit-type-rule shortcuts. Receptionist-only and unsupported-role users see no inventory section and trigger no inventory requests. Inventory-only users trigger no patient, appointment or coordination-queue requests. Existing sign-in protection stays in place.
2. Show four counts of active **items**: Out of stock, Low stock, Expiring soon and Expired. Each count uses the matching S4.4 filtered API `total`, including when results span pages; never count batches, sum quantities or filter one fetched page. Stock alerts use usable stock; expiry alerts require positive batch stock and use the clinic-local date and inclusive 30-day window from S4.4. Explain that an item can appear in more than one category; do not add the counts into a combined total.
3. Each count, including zero, links to `/inventory?status=active&alert=<code>&page=1`, using `out_of_stock`, `low_stock`, `expiring_soon` or `expired`. The destination retains the alert filter through paging and shows the matching list. A general Open inventory link goes to `/inventory?status=active`.
4. A successful zero count displays `0`; when all four reads succeed with zero, show “No inventory items need attention.” A failed category shows “Unavailable”, never zero or all-clear copy. Other inventory categories and coordination sections remain usable. Do not derive inventory availability from the dashboard's clinic-day request: the inventory API calculates its own date. Page refresh fetches current counts, including after stock changes, item deactivation and clinic-day rollover; no polling.

## Changes

- **Data / migrations:** none. No stored counts, audit writes, jobs or dependencies.
- **API:** no new or changed endpoints, query parameters or response schemas. Reuse S4.4's `GET /inventory/items` four times with `status=active`, the category's `alert`, `page=1`, `page_size=1`, and no search/category filter. Read `{items, total, page, page_size}` via the existing typed client. Existing inventory read roles and clinic scoping apply.
- **UI:** extend `features/dashboard/load-dashboard.ts`, `dashboard-screen.tsx` and their tests; reuse the inventory client and URL helpers. Fetch permitted inventory categories concurrently and preserve independent results. Reuse the dashboard styling and server-side session forwarding. All stock actions stay on inventory screens.

## Out of scope

Item/batch previews, new alert rules, notifications, automatic write-offs, restock controls on the dashboard, forecasts, inventory analytics, aggregate dashboard endpoints, polling and navigation redesign.

## Decisions and risks

Build after S6.1 is integrated and the base contains S4.4's API, types and filtered inventory UI. S6.1 is currently draft and depends on unfinished Phase 5 work; S4.4 is recorded as merged in PRODUCT.md but absent from this checkout. Do not rebuild either prerequisite here. `.shipit/open.md` has no inventory-dashboard blocker.

Recommendation for approval: show attention to all existing inventory readers, including clinicians, and reuse four filtered reads rather than add an aggregate endpoint. This keeps permissions and alert rules authoritative, at the cost of four requests. Counts can change between loading and clicking or across midnight; there is no shared snapshot across requests.

## How it will be verified

- Criteria 1–4: loader/component tests for every role and mixed roles, exact request filters and totals beyond one page, exact links, overlapping categories, zero/all-clear, partial failures, failed clinic-day lookup and fresh reads. Keep S6.1 dashboard coverage passing.
- Reuse S4.4 service/API integration tests for threshold/expiry boundaries, clinic-local rollover, changes on reread, inactive-item exclusion, clinic isolation and read permissions; add any missing cases. Verify destination filtering/paging with web tests. No new alert calculations in the frontend.
- Run `make check` and `make web-build` with `API_BASE_URL` set; report unavailable checks. Human click-through uses synthetic inventory and follows each count to its list.

Visual proof in `.shipit/proof/S6.2-inventory-dashboard/`, synthetic data only:

- All-zero inventory attention and one failed category with other sections available.
