# S2.4 Coordinator queue

Status: approved
Branch: slice/S2.4-coordinator-queue
Size: M (one list route, two write routes, one additive column, one page, one book variant)

## Goal

A coordinator opens one page, sees which patients are due or overdue for a follow-up, marks one contacted, and books their next visit from that row.

## Acceptance criteria

### API

1. **Due state is calculated.** A pure function takes `due_on` and the clinic-local today and returns `overdue` (before today), `due_today`, or `upcoming`. Nothing is stored. The list response carries it per row.
2. **List.** `GET /follow-ups?view=due|all&page&page_size` returns `{items, total, page, page_size}`. `view=due` (default) is open follow-ups with status `scheduled` or `contacted` and `due_on` today or earlier. `view=all` is every open follow-up, including `booked` and future dates. Completed and cancelled never appear. Each item has `id`, `status`, `due_on`, `timing`, and `patient` (`id`, `display_id`, `full_name`, `phone`). Order is `due_on` ascending, then patient number. Page size follows the patient list (default 20, max 100). Bad `view`, `page` or `page_size` gives 422.
3. **Scope.** Only the signed-in clinic's follow-ups appear. Follow-ups of inactive patients are left out.
4. **Mark contacted.** `POST /follow-ups/{id}/contacted` (no body) moves `scheduled` to `contacted` and returns the list item shape. From `contacted` or `booked` it gives 409 `invalid_status` and changes nothing. There is no undo.
5. **Book from the queue.** `POST /follow-ups/{id}/book` takes `clinician_id`, `appointment_type_id`, `starts_at` (the same rules and errors as `POST /appointments`, patient comes from the follow-up). From `scheduled` or `contacted` it creates the appointment, sets the follow-up to `booked`, and stores the visit in `booked_appointment_id`, all in one transaction. It returns 201 with the new appointment in the `POST /appointments` shape.
6. **Book is all or nothing.** If the slot is taken (409 `slot_taken`), the patient is busy (409 `patient_busy`), or any field is invalid (422), no appointment is created and the follow-up keeps its status. A follow-up already `booked` gives 409 `invalid_status`.
7. **Inactive patient.** Contacted and book on an inactive patient give 409 `patient_inactive` and write nothing.
8. **Audit.** Contacted writes `follow_up` / `status_change` / `["status"]`. Book writes the S1.3 `appointment` / `create` event and `follow_up` / `status_change` / `["status", "booked_appointment_id"]`, same transaction, actor is the user. If an audit write fails, nothing is saved. No values are stored.
9. **Roles and order of checks.** `clinician`, `receptionist`, `clinic_admin` may use all three routes. `inventory_admin` gets 403, no session 401, on every route. Order: 401, role, 404 (unknown or other-clinic follow-up), 422, 409.
10. **Concurrency.** Two contacted requests at once: one 200, one 409. Two books at once on one follow-up: one 201, one 409, and one appointment only. The service locks the patient, then the follow-up, the same order S2.2 uses.
11. **Existing behaviour holds.** S2.2 and S2.3 tests pass unchanged. The route-walk test passes. `openapi.json` and `schema.d.ts` are regenerated. `make check` and `make web-build` pass.

### Web

12. **Queue page.** `/follow-ups` shows a table or list of patient name, ID, phone, due date, a badge (Overdue, Due today, Upcoming), and status. A "Due" and "All open" switch maps to `view`. Empty state: "No follow-ups are due." Pagination as on the patient list. `inventory_admin` sees "You do not have access." The nav has a "Follow-ups" link.
13. **Mark contacted.** Each `scheduled` row has a "Mark contacted" button. After success the row shows Contacted and the button is gone. A 409 refreshes the row and shows "This follow-up has already changed."
14. **Book from a row.** "Book visit" on a `scheduled` or `contacted` row opens `/follow-ups/[id]/book`, the same type, clinician, date and slot picker as the patient booking page. Booking returns to `/follow-ups` with "Visit booked." and the row shows Booked. A taken slot shows "That time was just taken. Pick another." and reloads the slots. A follow-up that is already booked or no longer open shows a plain message.
15. **Links.** The patient name links to `/patients/[id]`.

### Proof that it works

16. **Tests that can fail.** Each rule in 1 to 10 has a test that fails if the rule is removed. The role test walks four roles on all three routes and checks tables are unchanged for refused ones. The timing test covers the day before, the day itself, and the day after, including a clinic-local day that differs from the UTC day. Web tests assert on what the user sees. Before handing over, the builder breaks these once on purpose (the due filter, the status guard, the rollback of a failed booking, the clinic scope), sees a test go red, restores it, and records it in the review packet.

## Changes

- Data (migration `0012`, additive): `follow_up.booked_appointment_id` nullable UUID, composite FK `(booked_appointment_id, clinic_id)` to `appointment`, so it cannot point at another clinic's visit. No existing column changes. The list query uses the existing `(clinic_id, status, due_on)` index.
- API (`clinic_id` from the session):

  | Route | Roles | Result |
  | --- | --- | --- |
  | `GET /follow-ups` | clinician, receptionist, clinic_admin | 200, 401, 403, 422 |
  | `POST /follow-ups/{id}/contacted` | same | 200, 401, 403, 404, 409 |
  | `POST /follow-ups/{id}/book` | same | 201, 401, 403, 404, 409, 422 |

- Code, in the existing layers: `domain/follow_up.py` (timing function, status moves, view names); `repositories/follow_up_repository.py` (a paged list joined to patient, a locked read by id); `services/follow_up_service.py` (list, contacted, book, which calls `appointment_service.book_appointment`); `api/follow_ups.py` (three routes). `models/follow_up.py` gets the column.
- UI: `features/follow-ups/` (queue screen, row, contacted button, view switch). `/follow-ups` and `/follow-ups/[id]/book` pages. `BookScreen` takes a submit URL and a done URL so both flows share it. A nav item. Client functions and types.
- No new dependency.

## Out of scope

- Closing a follow-up: completed, cancelled, or completing when the booked visit is done. See decisions.
- Notes, reasons, call logs, or contact history. "Contacted" is a status and nothing else.
- Sending messages, reminders (Phases 5), and AI.
- Editing a follow-up's date.
- Recalls (S2.5), the patient timeline (S2.6), dashboard counts (S6.1).
- Filters by clinician or text search. Role-based nav (S7.1).
- Showing the booked visit's time in the queue. The id is stored now for later slices.

## Decisions and risks

- **Closing is not in this slice (recommended, needs your call).** Without it, a `booked` follow-up stays open forever. It blocks a new follow-up for that patient (409 `follow_up_open`), and when that visit completes, S2.2 only moves `appointment_id` and keeps status `booked`, so a patient with care still open would not come back into the Due view. Recommendation: S2.4b, small: finishing the booked visit completes the follow-up before S2.2 runs, plus a Cancel button on the queue. That also settles the open item in `.shipit/open.md`. Do it before S2.7. Tradeoff: the loop has a known gap until then. Alternative: put both in S2.4 and make it L, which the roadmap says to split.
- **`booked_appointment_id` column (recommended).** It proves which visit the booking made and is what S2.4b and the timeline need. Tradeoff: a column nothing reads yet in the UI. Alternative: add it in S2.4b, which cannot backfill rows booked before then. AGENTS.md lists migrations only when they change or remove tables, and this one only adds, but I list it so you approve the schema.
- **Booking may start from `scheduled` as well as `contacted`.** A coordinator often books while on the call. Tradeoff: `contacted` does not always precede `booked`. Alternative: require contacted first, one extra click.
- **Inactive patients are hidden from the queue.** They were retired on purpose. Tradeoff: a follow-up can sit unseen if a patient is retired by mistake and reactivated later, it returns then.
- **Phone is shown in the queue.** The coordinator needs it to call. Only roles that can already list patients see it.
- **Book route reuses `book_appointment`.** One code path for overlap, hours and grid rules. Tradeoff: the follow-up route depends on the appointment service, which is allowed (service to service).
