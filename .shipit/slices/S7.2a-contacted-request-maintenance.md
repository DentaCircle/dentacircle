# S7.2a Contacted request maintenance

Status: draft
Branch: slice/S7.2a-contacted-request-maintenance
Size: S

## Goal

Staff marking a follow-up or recall contacted receive accurate, safe failure feedback
through one bounded request implementation, while each queue keeps its own workflow.

## Scope and starting point

Deferred to Phase 7 hardening, after S7.2 and before the S7.3 pilot review. S3.1 and
Phases 3–6 do not depend on this work. Scheduling was agreed on 2026-10-23.
The behavior and test scope below remain draft and require brief approval before building.
At that time, recheck the current implementation and capture the latest reviewed revision
as the branch base; do not branch from the old S2.8 snapshot. Preserve unrelated local edits.
The optional appointment-booking refactor is independent of this slice.

## Acceptance criteria

1. **Endpoint compatibility.** Both buttons send one same-origin POST with no request
   body to their existing `/api/follow-ups/{id}/contacted` or `/api/recalls/{id}/contacted`
   route, encoding the identifier. Success navigates to the original queue with its
   current view, page and `notice=contacted`, then refreshes. No response body is needed
   on success; preserve the existing successful-response acceptance behavior.
2. **Accurate conflicts.** Only 409 `invalid_status` navigates with `notice=changed`.
   `patient_inactive` displays “This patient is inactive.” without navigation. Unknown
   409s, malformed error bodies and other unrecognized failures display “Something went
   wrong.” A 403 displays “You do not have access.” Raw response messages and submitted
   values never render. This deliberately corrects follow-up's blanket 409 handling.
3. **Bounded failure and recovery.** Both actions use the existing five-second transport
   policy. Timeout or network failure leaves the pending state and displays “Could not
   reach the server.” A deliberate retry is possible; nothing automatically retries a
   mutation or assumes it did not commit. Do not extend timeout policy to other actions.
4. **Submission behavior.** Keep the synchronous ref guard and disabled button so rapid
   repeat clicks send one request. A failed attempt releases both guards. Successful
   or already-changed navigation occurs once and preserves queue-specific URLs/copy.

## Changes

- Data and migrations: none.
- Routes, role declarations and wire contracts: unchanged; no generated schema changes.
- Frontend: touched follow-up and recall contacted buttons and their tests; a small
  shared contacted-request module under `apps/web/features/` may own endpoint handling
  and safe outcome interpretation. Reuse `lib/api/transport.ts` and `errors.ts`.
- Interface: the buttons learn contacted outcomes, rather than HTTP status/body rules.
  Keep navigation and submission state explicit in each button. Use the existing fetch
  adapter in tests. No transport framework or new adapter registry.
- Existing `markRecallContacted` export may remain for compatibility; do not migrate
  unrelated client exports. Do not add a forwarding-only module as the refactor's result.

## Out of scope

Booking, cancel actions, queue unification, backend behavior, auth, sessions, tenancy,
role checks, new messaging, idempotency, universal mutation hooks, automatic retries,
new dependencies and a full shared-client migration.

## Decisions and risks

- Follow-up's inactive-patient result and bounded failure are intentional improvements.
  Recall's existing visible behavior is preserved.
- Contacted is a staff-recorded status; the product does not send communication.
- A timed-out request may have committed. Preserve server conflict handling on any
  deliberate second attempt; do not manufacture success or roll back client-side.
- Depth comes from concentrating request/error knowledge. Locality improves only if
  both callers use that implementation; leverage does not justify a general action engine.
- No audit/timeline/transaction changes: backend writes remain authoritative.

## How it will be verified

Use TDD for the inactive-patient regression and timeout recovery. The interface is the
test surface: render each button with the real request implementation and controlled
fetch/time/navigation adapters. Replace request-function mocks in the recall tests;
do not assert private helper calls, filenames or hook state.

Criterion-to-test map:

- 1: both rendered buttons; exact encoded URL, POST, credentials, absent body, success
  destination with Due/All and non-first page, refresh, successful empty response.
- 2: both buttons; `invalid_status`, `patient_inactive`, unknown 409, 403, 404/500,
  malformed/non-JSON error, and hostile raw message never displayed.
- 3: controlled abort-aware fetch and time; timeout/network failure, pending cleared,
  deliberate retry and no automatic extra request.
- 4: rapid repeat clicks, disabled pending state, failed-attempt recovery, single navigation.

Run focused Vitest tests first, then `make check` with configured PostgreSQL and
`make web-build` with API_BASE_URL configured. Report unavailable checks/skipped database
tests honestly. No new dependencies, browser automation or secrets in outputs.

Synthetic click-through and proof in `.shipit/proof/S7.2a/`:

- Follow-up and recall successful contacted notice in the original view/page.
- Inactive-patient message without navigation.
- Pending button and bounded failure with a deliberate retry available.
- Already-changed notice and access-denied message.
