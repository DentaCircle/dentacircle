# S5.3 Appointment reminders

Status: built
Branch: slice/S5.3-reminders
Size: M

## Goal

Staff can schedule an appointment reminder, see when it is due, and record that they handled it.

## Acceptance criteria

1. From a future scheduled visit for an active patient, staff can schedule a reminder for now or for a time before the visit. The API rejects past, timezone-naive and at-or-after-start times, and returns a conflict for an ineligible visit or a second pending reminder, including simultaneous requests.
2. The Due list shows pending reminders whose due time has arrived, earliest first with stable pagination. All pending also shows future reminders. Both lists hide inactive patients and visits that have started or left scheduled status. Times display in the clinic timezone.
3. Staff can complete or cancel a pending reminder. Completion requires an eligible visit and active patient. Cancellation can also close a pending reminder that has become ineligible. Both outcomes are final. A repeated or competing transition returns a conflict. Creation and state changes write one audit event each in the same transaction, and leave the visit, follow-up and recall states alone.
4. Moving the visit to a different start time, cancelling it, or recording arrival or no-show cancels any pending reminder in the same transaction, with audit attribution from the visit action. A clinician-only move keeps the reminder. A failed visit change leaves it intact. Staff can schedule a fresh reminder for the new time.
5. Receptionists, clinicians and clinic admins can use the queue and its actions. Signed-out requests and other roles are refused. Reads exclude other clinics' rows and writes to their IDs return 404. The UI distinguishes an empty queue from a load failure and reports stale action conflicts.

## Changes

- **Data and migration** Add a `reminder` table with UUID `id`, `clinic_id`, `appointment_id`, timezone-aware `due_at`, `created_at`, nullable `resolved_at`, and checked `status` (`pending`, `completed`, `cancelled`). Use a composite clinic/appointment foreign key, a partial unique index on clinic and appointment for pending rows, and a pending list index on clinic, due time and ID. Apply an additive Alembic migration at the build branch's head. Existing visits are eligible for manual scheduling.
- **API** Add `POST /appointments/{id}/reminders` with optional `due_at` (omitted means now), returning 201 with `id`, `appointment_id`, `due_at` and `status`. Add `GET /reminders?view=due|pending&page=1` (default due, 20 per page), returning `items`, `total`, `page` and `page_size`. Each item includes those reminder fields plus `starts_at`, `patient_id` and `patient_name`. Add `POST /reminders/{id}/complete` and `POST /reminders/{id}/cancel`, both with an empty request and 204 response. Use the roles above on all four routes. Regenerate API types.
- **Services** Use the existing patient-before-appointment lock order for reminder writes, then lock the reminder if present. Recheck eligibility and state under those locks. Record `reminder` audit events with field names only.
- **UI** Add Schedule reminder to eligible calendar rows and a Reminders page with Due and All pending views, links to the patient and visit's calendar day, and Complete and Cancel actions. Display empty, forbidden, load-error and action-error states.

## Out of scope

WhatsApp sending and delivery states, automatic scheduling and backfill, reminders for other record types, priority and assignment, and dashboard counts.

## Decisions and risks

Manual, appointment-only reminders were approved on 2026-11-10. Staff choose which visits need a reminder and when. Completing a reminder records that staff handled it. A moved visit needs a fresh reminder because staff chose the time for the original visit. Build after S5.2a and S5.2b are integrated so the migration and visit hooks can be checked against the shared booking path.

### Decisions and unsure points

- Calendar responses include patient status so the scheduling control is hidden for inactive patients; the API rechecks under lock.
- An empty due time means now. A clinic-local time that is missing or occurs twice at a daylight-saving transition is rejected instead of choosing an instant silently.
- The queue displays clinic-local times and links to the visit's clinic-local calendar day.
- Screenshots were taken at `92502d8`; subsequent changes add tests and move the queue read behind the service without changing the visible flow.
- Please judge the form placement and wording in the screenshots. No other known unsure points.

### Click-through

1. Start PostgreSQL, set `DATABASE_URL` as in `.env.example`, and run `make dev`.
2. In another terminal run `make create-user ARGS='--clinic "Synthetic Clinic" --email sample@x.test --name "Sample Clinician" --roles clinician,receptionist'` and enter a password. Sign in at `http://localhost:3000`. Register a synthetic patient and book a future visit with that clinician.
3. Open a future scheduled visit for an active patient in Calendar. Select **Schedule reminder**, leave the time blank, and select **Schedule**.
4. Open **Reminders**. The Due view contains the reminder; **All pending** includes reminders set for later.
5. Select **Complete** and confirm the Due view is empty. To test cancellation on a moved visit, create a fresh reminder and reschedule the visit to a different time.
