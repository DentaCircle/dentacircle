# S1.0 Clinic day

Status: done
Branch: slice/S1.0-clinic-day
Size: S

## Goal

A clinic has a timezone, weekly working hours, a default appointment duration and a list of appointment types, all stored in the database and readable through the API, so S1.3 can compute availability from them.

## Acceptance criteria

1. **Schema.** `alembic upgrade head` adds two columns to `clinic` and creates `clinic_working_hours` and `appointment_type`. `downgrade` to `0002` removes them. Upgrade, downgrade, upgrade works.
2. **Clinic columns.** `clinic.timezone` defaults to `Asia/Kolkata`. `clinic.default_appointment_minutes` defaults to 30. A database check rejects a default outside 5 to 480.
3. **Working hours rules.** A weekday (0 is Monday, 6 is Sunday) can have up to six open intervals, so a lunch break is just a gap between two intervals. A day with no interval is closed. The database rejects a weekday outside 0 to 6, rejects `opens_at` not before `closes_at`, and rejects two intervals on the same clinic and weekday that overlap. Intervals that touch (12:00 end, 12:00 start) are also rejected, because they should be one interval. Times are clinic-local wall time.
4. **Appointment type rules.** Names are unique per clinic, ignoring case, so `Scaling` after `scaling` is rejected. Duration is empty or 5 to 480 minutes. Two clinics may use the same name.
5. **Defaults for existing and new clinics.** The migration gives every existing clinic Monday to Saturday 09:00 to 18:00 and four active types: Consultation (30), Scaling (30), Root canal visit (60), Crown visit (45). `get_or_create_clinic` seeds the same defaults for a new clinic and does not touch an existing one.
6. **Read the clinic day.** `GET /clinic/day` returns `{timezone, default_appointment_minutes, working_hours: [{weekday, opens_at, closes_at}]}` ordered by weekday. Any of the four roles may call it. No session gets 401.
7. **Change the clinic day.** `PUT /clinic/day` replaces the timezone, the default duration and the whole hours list, and returns the new state. Only `clinic_admin` may call it. Other roles get 403. A weekday with no interval in the list is closed. An empty list is allowed. The admin decides per day whether there is a break and how many, by sending one interval or several.
8. **Validation.** The PUT returns the standard 422, without echoing submitted values, for: an unknown timezone name, `opens_at` not before `closes_at`, a weekday outside 0 to 6, two intervals on one weekday that overlap or touch, more than 6 intervals on one weekday, a default duration outside 5 to 480. A failed PUT changes nothing.
9. **List types.** `GET /appointment-types` returns active types ordered by name. `include_inactive=true` adds inactive ones. Each item has `id`, `name`, `duration_minutes` (as stored, may be null), `effective_duration_minutes` (the type's own, else the clinic default) and `is_active`. Any of the four roles may call it.
10. **Create a type.** `POST /appointment-types` with `{name, duration_minutes}` returns 201. Only `clinic_admin`. A duplicate name (any case) returns 409 `conflict`. A blank name or a bad duration returns 422. Names are trimmed.
11. **Update a type.** `PUT /appointment-types/{id}` replaces `name`, `duration_minutes` and `is_active`. Only `clinic_admin`. An unknown id returns 404. There is no delete route: a type is deactivated, so later appointments can still point at it.
12. **Tenancy.** Both clinic-owned tables carry `clinic_id`. With two clinics, an admin of clinic A reads and changes only A's hours and types, and gets 404 for B's type id. The clinic id comes from the session, never from the request.
13. **Deny by default.** The existing route-walk test passes with the new routes. Each lists its roles.
14. **Contract and docs.** `openapi.json` and `schema.d.ts` are regenerated. `make check` passes. README gets a short note on how to change hours and types without a screen. PRODUCT.md records the decisions.

## Changes

- Data (additive, UUID ids, `created_at` where the table is new):
  - `clinic` gains `timezone` (text, not null, default `Asia/Kolkata`) and `default_appointment_minutes` (int, not null, default 30, check 5 to 480).
  - `clinic_working_hours`: `clinic_id` FK, `weekday` (smallint, check 0 to 6), `opens_at` (time), `closes_at` (time, check `opens_at < closes_at`). Primary key `(clinic_id, weekday, opens_at)`. Any number of intervals per day. An exclusion constraint on `(clinic_id, weekday, timerange(opens_at, closes_at, '[]'))` forbids overlapping or touching intervals. It needs the `btree_gist` extension, which the migration creates.
  - `appointment_type`: `id`, `clinic_id` FK (indexed), `name`, `duration_minutes` (int, null allowed, check 5 to 480 when set), `is_active` (default true). Unique index on `(clinic_id, lower(name))`. Unique `(clinic_id, id)` so S1.3 can reference it with a composite key, as S0.4 does.
- API (`clinic_id` always from the session):

  | Route | Roles | Result |
  | --- | --- | --- |
  | `GET /clinic/day` | all four | 200 |
  | `PUT /clinic/day` | `clinic_admin` | 200, 403, 422 |
  | `GET /appointment-types` | all four | 200 |
  | `POST /appointment-types` | `clinic_admin` | 201, 403, 409, 422 |
  | `PUT /appointment-types/{id}` | `clinic_admin` | 200, 403, 404, 409, 422 |

  `errors.py` gains 409 `conflict` with a fixed message, so the error body stays on the one shape.
- UI: none. There is no settings screen in this slice (ROADMAP). The only web change is the regenerated `schema.d.ts`.
- Migrations: one revision `0003`. Adds columns to `clinic` and two tables, then inserts the default rows for existing clinics. Nothing is dropped or rewritten.
- Code, in the existing layers:
  - `models/` (`clinic.py` edited, new `working_hours.py`, `appointment_type.py`).
  - `repositories/` (`clinic_day_repository.py`, `appointment_type_repository.py`). Both take `clinic_id` on every method.
  - `services/clinic_day_service.py` (read, replace, validate the timezone with `zoneinfo`, seed defaults) and `services/appointment_type_service.py` (list, create, update, effective duration). `provisioning_service.get_or_create_clinic` calls the seed.
  - `api/clinic_day.py`, `api/appointment_types.py`, registered in `main.py`.
  - `domain/clinic_day.py` holds the default hours and default types as plain data, shared by the migration check and the seed.

## Out of scope

- A settings screen, or any web page for this. Changes go through the API (README shows a `curl` example).
- Availability and slots, and any use of hours when booking (S1.3). Nothing in this slice rejects an appointment.
- Holidays and one-off closures, per-clinician rotas, rooms and resources. (Breaks inside a day are in scope, as gaps between intervals.)
- Follow-up, recall and inventory defaults. They arrive with their slices.
- Clinic name and contact details, user and role management screens.
- Audit events. `AuditEvent` starts at S1.1, and AGENTS.md lists patient, appointment, care, follow-up and inventory data. Clinic setup is not on that list.
- Deleting appointment types, reordering them, colours, or per-type clinician restrictions.

## Decisions and risks

No new dependency. `zoneinfo` is in the standard library.

Needs your approval (AGENTS.md stop): **this migration alters the existing `clinic` table** by adding two columns with defaults. It removes and rewrites nothing, and the downgrade drops the columns. The alternative is a separate one-to-one `clinic_settings` table that leaves `clinic` alone, at the cost of a join on every read. I recommend the two columns: there is one clinic per tenant and the values are plain facts about it.

Your calls, to be recorded in PRODUCT.md on approval:

- **Who edits: `clinic_admin` only, everyone reads (recommended).** Receptionists and clinicians need the hours to book and see types. Changing them is a rare admin act. Tradeoff: with no screen, an admin changes them with `curl` until a settings screen exists. If that hurts, a small settings page is a later slice, not this one.
- **Several open intervals per weekday (your call, now in the brief).** A break is a gap between intervals, so the clinic decides whether it has breaks and how many, and can change it any time without a migration. Default is one interval per day, no break. Tradeoff: the no-overlap rule moves into the database as an exclusion constraint, and S1.3 availability has to walk a list of intervals instead of one. The cap of 6 per day is a code constant for input safety, not a setting.
- **New extension `btree_gist` (AGENTS.md stop: approval needed).** It ships with PostgreSQL 16 and is needed for the no-overlap constraint. S1.3 needs the same extension for its "no overlapping appointments for one clinician" rule, so enabling it here costs nothing extra. It must be created by a database user allowed to do so, which is true for the local Docker database. Any future host has to allow it. Alternative: check overlap only in the service, which a second request could slip past. I recommend the constraint.
- **Type duration is optional and falls back to the clinic default (recommended).** If a type has its own minutes, booking uses them. If it has none, booking uses the clinic default. Example: default 30, "Root canal visit" set to 60, "Consultation" left empty. Booking a root canal takes 60 minutes and a consultation takes 30. If the admin later changes the default to 20, every type left empty becomes 20 at once, and the 60 stays. Tradeoff: one more field to explain. The alternative is a required duration on every type, with the default used only to prefill a form.
- **Types are never deleted, only deactivated.** S1.3 appointments will reference them. Tradeoff: the list can grow stale, and `include_inactive` hides that.
- **Backfill inside the migration.** Every clinic, including your dev one, has hours and types right after `make migrate`, so S1.3 never meets a clinic with none. The defaults are only starting values: the admin changes hours with `PUT /clinic/day` and types with the type routes, and the seed never runs again for that clinic. The default list itself lives in code (`domain/clinic_day.py`), not in a setting. Tradeoff: seed data in a migration. The alternative is a manual step per environment. The default hours (Monday to Saturday, 09:00 to 18:00) and the type names are synthetic placeholders, not clinical advice. Type names are labels for the calendar only.
- **Timezone is editable but validated against the IANA list.** The default is `Asia/Kolkata`. Changing it later shifts how stored UTC times display, so S1.3 must always convert through the clinic zone. The product still has one timezone per clinic and no per-user zones.
- **409 needs a new error code.** A small addition to `errors.py`, covered by the existing error-shape tests.

Risks:

- Small slice, but the migration inserts data, so the upgrade test runs it against a database that already has a clinic.
- Times are stored without a zone, as wall time. That is right for opening hours, and it means they only mean something together with `clinic.timezone`.
- Before merging, confirm the S1.0 branch is aligned with current `main` (see `.shipit/open.md`).

### Decisions made

- `origin/main` already contains S0.5 (`0002_auth`). Merge or rebase the S1.0 branch onto current `main` before merging the PR.
- The migration keeps its own frozen default values. `domain/clinic_day.py` feeds the runtime seed for new clinics.
- `GET /clinic/day` orders intervals by weekday, then `opens_at`.
- A type name is at most 200 characters, the size of the column. The service trims it.
- The unique name index covers inactive types too. Deactivating a type does not free the name. That matches the index in the brief, which is not partial.
- The 409 message is "That name is already in use."
- A new type is active. `POST` does not take `is_active`. Omitting `duration_minutes` is the same as null.
- `zoneinfo.ZoneInfo` is the timezone check. It accepts IANA names, including links such as `Asia/Calcutta`.
- The route-walk helper now opens included routers. This FastAPI build keeps those routes on the router object, so a walk of `app.routes` alone never saw `/health` or `/auth` either.

### Unsure points

- Overlap uses PostgreSQL `timerange(..., '[]')`, so a shared endpoint counts as overlap. A gap of one minute is allowed. Both are covered by schema tests.
- The cap of 6 intervals is only in the service and the request check. A direct SQL insert can add a seventh. That is what the brief asked for.
- Downgrade leaves `btree_gist` installed. S1.3 will reuse it for appointment overlap.
