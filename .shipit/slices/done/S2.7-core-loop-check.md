## Goal

One test file proves the whole M3 loop end to end on the API, and one written click-through lets you (or anyone) run the same story in the browser and see the same result.

## What already exists

`test_timeline_loop.py` (S2.6) walks one path: book, arrive, start, session, complete, follow-up, contacted, book from queue, complete. It checks only the timeline order. It does not check the queue views, the recall side, the "neither" outcome, or the release path. S2.7 adds those. It changes no product code unless the check finds a bug.

## Acceptance criteria

Tests go in `apps/api/tests/test_core_loop.py`, through the HTTP routes, as `clinician@x.test` unless stated. Dates are clinic-local.

1. **Follow-up path.** Book a Scaling visit, arrive, start. Create a plan with items Scaling and Root canal. Record a session: Scaling `completed`, Root canal `started`. Complete the visit. Then `GET /patients/{id}/follow-up` returns an open `scheduled` row due 7 days out, and `GET /recalls` (All open) returns one recall due 6 months out.
2. **Queue views.** Right after step 1, the follow-up is in `GET /follow-ups?view=all` as `upcoming` and not in the Due view. After its `due_on` is moved to yesterday (a direct DB update, as the existing tests do), it is in Due as `overdue`. The recall stays out of `/follow-ups`.
3. **Contact and book.** Mark the follow-up contacted, then book from the queue. The row is `booked` with the new visit stored. Complete that visit (arrive, start, complete). The follow-up becomes `completed`. Because Root canal is still open, a new open follow-up exists with a 7-day due date.
4. **Recall path.** Mark the recall contacted, book from `/recalls`, complete that visit. The recall is `completed` and a new recall is written.
5. **Clinician date.** Completing a visit with `follow_up_due_on` set to today puts the patient in the Due view as `due_today`, with no database edit and with every care item finished.
6. **Neither.** Completing a Consultation visit with every item finished, no date and no recall rule writes no follow-up and no recall. The timeline shows the visit steps only.
7. **Release.** Cancelling a booked follow-up visit returns the follow-up to `contacted` and the patient to the Due view.
8. **Timeline.** After the full run in 1 to 4, `GET /patients/{id}/timeline` lists the exact kind sequence, newest first, with page size large enough for one page. Every kind is one of the 27 allowed.
9. **Scope and roles.** `inventory_admin` gets 403 on `/follow-ups`, `/recalls` and the timeline. A user of a second clinic sees none of this patient's rows in the queues and gets 404 on the timeline.
10. **Written click-through.** `docs/demo-m3.md` lists the steps for the demo story as built (below), with who signs in, what to click, and what to see. It names the setup (users, roles) and is linked from `README.md`.
11. **Click-through is true.** The builder follows `docs/demo-m3.md` once in the browser with synthetic data, fixes the text where it was wrong, and saves one screenshot per step group in `.shipit/proof/S2.7/`.
12. **Bugs.** Any bug the check finds starts with a failing regression test. A fix that is more than a few lines, or that touches auth, tenancy, roles or a decided rule, is not made here. It goes to `.shipit/open.md` and I stop and tell you.

Criteria 10 and 11 are the only ones with no automated test. They are checked by following the document.

## The demo story as built

PRODUCT.md's Demo thread has lab work, a crown and a document in step 3. Those arrive in S3.x. The M3 version is:

1. Register a synthetic patient. Book a Scaling visit. The patient arrives and the clinician starts it.
2. The clinician makes a plan with Scaling and Root canal, records the session (Scaling done, Root canal started), and completes the visit. A follow-up and a six-month recall appear.
3. Coordinator opens Follow-ups, marks the patient contacted, and books the next visit from the queue.
4. That visit is completed and the follow-up closes. The recall is contacted, booked and completed the same way.
5. The patient timeline shows every step.

For the browser run, the follow-up is due in 7 days, so it would not show in Due today. The click-through uses the clinician date on completion (S2.3): set it to today, and the patient is in Due at once. No clock tricks or database edits.

## Decisions and risks

- **API-level test, no browser test (recommended, needs your call).** The API tests already pin every rule and the web pages have Vitest tests. A browser test needs Playwright, a new dependency, a second service in CI and a seeded login, and it breaks on layout changes. Tradeoff: nothing automatic proves the web screens work together. The written click-through covers that by hand. Alternative: add Playwright in its own slice after M3.
- **Visits are moved onto today by a direct DB update**, because arrived is only allowed on the visit's clinic-local day and the slots found may be later. `test_timeline_loop.py` already does this. It is test-only and not a product shortcut.
- **PRODUCT.md demo thread.** I suggest adding one line that step 3 (crown, lab, document) belongs to S3.x, and that M3 uses the story above. I will not edit it without your say.
- **Branch base.** The working tree is on `slice/S2.6-patient-timeline`. Branch from its head, or from `main` once the S2.6 PR merges.
- **Risk:** the check may find bugs between slices. Criterion 12 sets the rule: test first, small fix only, otherwise stop.
- **Open items:** none in `.shipit/open.md` block this.

### Decisions

- The follow-up visit is a Consultation. Completing it does not rewrite the Scaling recall.
- The recall visit is a Scaling, so completing it writes a new recall.
- The care plan is created after arrive and start, matching the brief. `care_item_added` is therefore newer than `visit_started`.
- Criteria 5 and 7, and the browser Due view, use a clinician follow-up date of today. No clock change and no database edit on those paths. Criterion 2 still moves `due_on` to yesterday, as the existing queue tests do.
- The follow-up body has `appointment_id` for the source visit and does not return the booked visit id. Criterion 3 stores the book response id, checks status `booked`, and completes that visit. A new open follow-up is the proof the booked visit was stored.
- Criterion 6's "visit steps only" is an exact kind list: the finished care item and the session are in it, and every `follow_up_` and `recall_` kind is absent.

### Unsure points

- The full-loop kind list is tied to write order inside one transaction (`occurred_at` desc, then `seq` desc). A later change that writes one of those events earlier will fail this test on purpose.
- The calendar shows a Next.js hydration overlay (`features/calendar/controls.tsx`). It blocked one Arrived click. Dismissing the overlay let the rest of the story through. No product change was made for it.
- Shots 1 and 2 include a repeated sliver of the page on the right. That is the capture surface. Shots 3 to 6 drop the sidebar so the row fits the panel.
