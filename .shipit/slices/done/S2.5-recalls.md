# S2.5 Recalls

Status: done
Branch: slice/S2.5-recalls
Size: L (kept as one slice at your request; the old S2.5b is in here)

## Goal

When a visit of a recall-enabled type (for example Scaling) is completed, the patient gets a recall dated months ahead. A coordinator opens a separate Recalls page, sees who is due or overdue, marks them contacted, books the next visit, or cancels the recall. Completing that booked visit closes the recall.

## Acceptance criteria

### Rule and date

1. **Rule on the appointment type.** `appointment_type.recall_after_months` is empty (no recall) or a whole number from 1 to 60. Nothing else defines a recall rule.
2. **Due date is calculated.** A pure function adds N months to the clinic-local completion date. If the target month is shorter, the date moves to that month's last day (31 Aug + 6 months = 28 Feb, or 29 in a leap year). Timing (`overdue`, `due_today`, `upcoming`) comes from the stored date and the clinic-local today, as for follow-ups. Timing is never stored.

### Creating a recall

3. **On completion.** `POST /appointments/{id}/status` with `completed` creates one open recall when the visit's type has a rule and the patient is active. Fields: patient, the type, the visit (`source_appointment_id`), `due_on`, status `scheduled`, `booked_appointment_id` empty. It happens in the same transaction as the status change, after follow-up recording.
4. **One open recall per patient.** Open means `scheduled`, `contacted`, or `booked`. If the patient already has a `scheduled` or `contacted` recall, completing another rule-enabled visit moves that recall to the new date, type and source visit. The most recent visit wins. Its status is kept. A `booked` recall is not moved and a second open recall is not created.
5. **No recall when it should not exist.** No rule on the type: no recall, and an existing recall is untouched. Inactive patient: the visit still completes and no recall is written. A visit that was not completed (cancelled, no-show) writes none. A `booked` recall blocks a new one until that row leaves the open set.
6. **Independent of follow-ups.** A completion can write a follow-up, a recall, both, or neither. The follow-up behaviour from S2.2, S2.3, S2.4 and S2.4b does not change. A patient may be in both lists. Closing or releasing one does not close or release the other.
7. **Audit on create and move.** Create writes `recall` / `create`. A move writes `recall` / `update` with `["appointment_type_id", "source_appointment_id", "due_on"]`. Same transaction, actor is the user who completed the visit. No values are stored. If the audit write fails, the visit stays un-completed.

### Setting the rule

8. **Appointment type API.** `POST /appointment-types` accepts optional `recall_after_months`. `PUT /appointment-types/{id}` accepts it too: left out means unchanged, `null` clears it. Values outside 1 to 60, or not whole, give 422. `GET /appointment-types` returns it on every item. Roles are unchanged: everyone reads, only `clinic_admin` writes. Changing a rule does not touch recalls that already exist.
9. **Defaults.** New clinics get Scaling with 6 months. The migration sets 6 on existing clinics' type named Scaling (case-insensitive) only if it is empty. All other types stay empty.

### Due list

10. **List.** `GET /recalls?view=due|all&page&page_size` returns `{items, total, page, page_size}`. `due` (default) is `scheduled` and `contacted` recalls with `due_on` today or earlier. `all` is every open recall, including `booked` and future rows. Completed and cancelled never appear. Each item has `id`, `status`, `due_on`, `timing`, `last_visit_on` (clinic-local date of the source visit), `recall_type` (`id`, `name`), and `patient` (`id`, `display_id`, `full_name`, `phone`). Order is `due_on` ascending, then patient number. Paging and 422 rules match `GET /follow-ups`.
11. **Scope.** Only the signed-in clinic's recalls. Recalls of inactive patients are left out.
12. **Separate from follow-ups.** `GET /follow-ups` and the follow-up queue never include recalls, and the reverse.
13. **Roles and order of checks.** `clinician`, `receptionist`, `clinic_admin` may list and act. `inventory_admin` gets 403, no session 401. Order: 401, role, 422, then 404.

### Acting on a recall

These copy the follow-up queue. There is no undo.

14. **Mark contacted.** `POST /recalls/{id}/contacted` moves `scheduled` to `contacted` and returns the queue item. Anything else open, or an inactive patient, is 409 (`invalid_status` or `patient_inactive`). Unknown id is 404. Audit is `recall` / `status_change` with `["status"]`.
15. **Book.** `POST /recalls/{id}/book` with `{clinician_id, appointment_type_id, starts_at}` reuses `book_appointment`. It may start from `scheduled` or `contacted`. In one transaction it creates the visit, sets the recall to `booked`, and stores `booked_appointment_id`. Response is 201 and the appointment body used by follow-up booking. Errors match `POST /follow-ups/{id}/book` (`invalid_status`, `slot_taken`, `patient_busy`, `patient_inactive`, 422, 404). Audit is `recall` / `status_change` with `["status", "booked_appointment_id"]`. Booking from the calendar does not attach a visit to a recall.
16. **Cancel.** `POST /recalls/{id}/cancel` is 204, no body, no reason. It works from `scheduled`, `contacted`, or `booked`. A booked visit stays on the calendar. Inactive patient is 409. Audit is `recall` / `status_change` with `["status"]`.
17. **Close and release from the visit.** Completing the visit stored in `booked_appointment_id` of a `booked` recall sets that recall to `completed`, in the same transaction, before a new recall can be written, and even when the patient is inactive. The completion rule can then create a new `scheduled` recall if this visit's type has a rule and the patient is active. Cancelling or no-show on that visit sets the recall back to `contacted`. `due_on` and `booked_appointment_id` stay, so Due can show the patient again. Reschedule changes nothing. A visit that is not the booked visit does not close or release a recall. Audit is `recall` / `status_change` with `["status"]`. If that audit write fails, the visit stays unchanged.
18. **Existing behaviour holds.** All S2.x and S1.x tests pass unchanged. The route-walk test passes. `openapi.json` and `schema.d.ts` are regenerated. `make check` and `make web-build` pass.

### Web

19. **Recalls page.** `/recalls` shows patient name (links to `/patients/[id]`), ID, phone, recall type, last visit, due date, a badge (Overdue, Due today, Upcoming), and status (Scheduled, Contacted, Booked). A "Due" and "All open" switch maps to `view`. Empty state: "No recalls are due." Pagination as on the follow-up queue. `inventory_admin` sees "You do not have access." The nav has a "Recalls" link.
20. **Row actions.** `scheduled`: Mark contacted, Book visit, Cancel recall. `contacted`: Book visit, Cancel recall. `booked`: Cancel recall only. Book visit goes to `/recalls/[id]/book` and reuses the follow-up booking screen. Cancel recall asks for confirmation, then calls cancel. Wording matches the follow-up queue, with "recall" in place of "follow-up".

### Proof that it works

21. **Tests that can fail.** Each rule in 2 to 7 and 10 to 17 has a test that fails if the rule is removed. Month-end clamp, leap year and a clinic-local day that differs from the UTC day are covered. A booked recall is covered for "not moved", for close-then-new-recall, and for release. Before handing over, the builder breaks these once on purpose (the inactive-patient guard, the one-open rule, the clinic scope, the due filter, and the close-before-create order), sees a test go red, restores it, and records it in the review packet.

## Changes

- Data, migration `0013`, additive:
  - `appointment_type.recall_after_months` nullable integer, check `IS NULL OR BETWEEN 1 AND 60`. One data `UPDATE` sets Scaling to 6 where empty (criterion 9).
  - New table `recall`: `id`, `clinic_id`, `patient_id`, `appointment_type_id`, `source_appointment_id`, `booked_appointment_id` (nullable), `status`, `due_on`, `created_at`, `updated_at` (same mixins as `follow_up`). Status check allows `scheduled`, `contacted`, `booked`, `completed`, `cancelled`. This slice writes all five.
  - Composite FKs `(patient_id, clinic_id)`, `(appointment_type_id, clinic_id)`, `(source_appointment_id, clinic_id)`, `(booked_appointment_id, clinic_id)`, so a row cannot point at another clinic. Partial unique index on `(clinic_id, patient_id)` where status is open. Index on `(clinic_id, status, due_on)`.
- API (`clinic_id` from the session). Roles for every recall route: `clinician`, `receptionist`, `clinic_admin`.

  | Route | Result |
  | --- | --- |
  | `GET /recalls` | 200, 401, 403, 422 |
  | `POST /recalls/{id}/contacted` | 200, 401, 403, 404, 409 |
  | `POST /recalls/{id}/book` | 201, 401, 403, 404, 409, 422 |
  | `POST /recalls/{id}/cancel` | 204, 401, 403, 404, 409 |
  | `POST`/`PUT /appointment-types` | new optional field; roles unchanged |

  `POST /appointments/{id}/status` gains no field. On `completed` it closes a booked recall for that visit, then may create or move a recall. On cancel and no-show it releases a booked recall for that visit. Reschedule is untouched.
- Code, existing layers: `domain/recall.py` (month add, timing, open and action statuses, roles); `models/recall.py`; `repositories/recall_repository.py`; `services/recall_service.py` (record, list, contacted, book, cancel, close, release); `api/recalls.py`. `appointment_service.change_status` calls recall close then record after `record_incomplete_care`. Cancel and no-show call recall release next to the follow-up release. `appointment_type` model, service and route get the new field.
- UI: `features/recalls/` (screen, row, view switch, contacted, book page, cancel, access check), `/recalls` and `/recalls/[id]/book`, nav item, client types.
- No new dependency.

## Out of scope

- A settings screen for rules. Rules are set through the API, with a README example, as in S1.0.
- Rules by care item, patient age, or interval days. Per-patient overrides.
- Hiding a recall when the patient already has some other future visit. Only the visit stored on the recall is linked.
- Notes, reminders, messages (Phase 5), the patient timeline (S2.6), dashboard counts (S6.1).
- Undo of contacted, book, cancel, or close.
- Any change to follow-up closing or release from S2.4b.

## Decisions and risks

- **The rule lives on the appointment type (recommended, needs your call).** It is structured, the demo's "scaling" is already a seeded type, and the service needs no free-text matching. Tradeoff: one type means one interval, and a recall depends on how the visit was booked, not on what care was done. Alternative: match the care item name. Care items are free text, so that is fragile.
- **Latest rule-enabled visit wins, unless the recall is booked (recommended).** One open recall per patient keeps the list short. A later completed Scaling replaces a `scheduled` or `contacted` date and keeps that status. A `booked` row stays until that visit is completed, cancelled, a no-show, or the coordinator cancels the recall. Tradeoff: a Scaling completed while a recall is already booked does not move the date and does not start a second recall. Alternative: one open recall per type.
- **Acting on a recall is in this slice.** You asked to include the old S2.5b here instead of a later slice. The page is a queue, copied from S2.4 and S2.4b. The Due view therefore matches follow-ups: booked rows show only under All open. Size is L. It stays one branch and one review, in the commits below.
- **Backfilling Scaling to 6 months (recommended).** Without it the dev database shows no recalls until someone calls the API. The migration only fills an empty value and touches no other column or table. Alternative: leave existing clinics empty and set the rule by curl.
- **`PUT` leaves out means unchanged.** It keeps existing callers and tests working. Tradeoff: `PUT` is no longer a pure full replace for this one field.
- **`change_status` is edited again.** S2.4b (sealed) already put follow-up closing and release in it. Recall close and record run in the `completed` branch, after `record_incomplete_care`. Recall release runs on cancel and no-show, next to the follow-up release. Nothing else in those functions changes.
- **Open items:** none block this slice. `.shipit/open.md` only lists undo and tidy-up items.

### Decisions

- No `updated_at`. The brief listed it and also said to use the follow-up mixins. `follow_up` has `clinic_id` and `created_at` only, so the recall table matches that.
- A booked recall is not moved, and it blocks a second open row. Due matches follow-ups: booked rows are only on All open.
- `PUT` omits `recall_after_months` to leave it, and sends null to clear it.
- Book checks the body before looking up the recall, so a bad body is 422 and a missing id with a valid body is 404. The role check still runs before the body.
