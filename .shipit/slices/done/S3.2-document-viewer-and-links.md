# S3.2 Document viewer and links

Status: done
Branch: slice/S3.2-document-viewer-and-links
Size: M

## Goal

Staff open a patient's PDF or image in the browser instead of only downloading it, link a document to a visit or a follow-up, and see "document uploaded" on the patient timeline.

## Acceptance criteria

### Viewer

1. **Inline file.** `GET /patients/{id}/documents/{document_id}/file?disposition=inline` returns the bytes with `Content-Disposition: inline` and a safe filename. Default and `disposition=attachment` behave as in S3.1. Any other value is 422. Both modes keep `Content-Type` from the stored type, `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`. Images (PNG, JPEG) inline also get `Content-Security-Policy: sandbox; default-src 'none'`. PDFs do not (see decisions). Same three roles. Another patient's or clinic's document is 404.
2. **One document.** `GET /patients/{id}/documents/{document_id}` returns one document item (shape in 5). Same roles, same 404 rules, readable for an inactive patient.
3. **Viewer page.** `/patients/[id]/documents/[documentId]` shows the filename, type, size, who and when, the links (see 8), a Download link, and the file: an `<img>` for PNG and JPEG, and an "Open in new tab" link for PDF. No iframe, no embed. Not-found, no-access (`inventory_admin`) and error states match the Documents page. Each row on the Documents page links to it.

### Links

4. **Columns.** A document may link to one appointment and one follow-up, both optional and independent. A link is stored on the document row. A document with no link is fine and stays the default.
5. **Item shape.** The document item gains `appointment` (`id`, `starts_at`, `type_name`, or null) and `follow_up` (`id`, `due_on`, or null). They are read live, like timeline subjects. `starts_at` is in the clinic's offset.
6. **Set and clear.** `PATCH /patients/{id}/documents/{document_id}` takes `{appointment_id?, follow_up_id?}`. A UUID sets the link, `null` clears it, an omitted field stays as it is. An empty object is 422. `receptionist`, `clinician` and `clinic_admin` may call it. `inventory_admin` gets 403, no session 401. Order of checks: 401, role, 422, 404, then the rest. Returns the document item.
7. **Same patient, same clinic.** The appointment or follow-up must belong to this patient in the caller's clinic. Anything else is 404, with no hint of which part failed. The status of the appointment or follow-up does not matter (cancelled and completed ones still count as history).
8. **Inactive patient.** Changing a link is refused (409 `patient_inactive`, as for upload). Listing and viewing still work.
9. **Link at upload.** `POST /patients/{id}/documents` takes optional `appointment_id` and `follow_up_id` query parameters, checked by the same rule as 7 before the file is stored. A bad id is 404 and nothing is stored. No id means no link, as in S3.1.
10. **Filter.** `GET /patients/{id}/documents` takes optional `appointment_id` and `follow_up_id`. A filtered list returns only documents with that link. Paging and 422 rules stay as they are. A filter id from another patient or clinic returns an empty list, not 404. The "link existing" list in 12 uses the unfiltered list and hides rows already linked to this context.
11. **Audit.** A link change writes one `document` `update` audit event with `changed_fields` listing `appointment_id` and/or `follow_up_id` (names only, never ids, never direction). A change that leaves the row as it was writes none. Upload keeps its one `create` event.
12. **Web, linking from the visit or the follow-up.** The calendar row of a visit and the follow-up queue row each get a "Documents" link (for the three roles) to `/patients/[id]/documents?appointment_id=<id>` or `?follow_up_id=<id>`. On that filtered page:
    - a heading says which visit or follow-up it is for, with a "Show all documents" link;
    - the list shows only linked documents;
    - the upload form sends the same id, so a new file is linked at once;
    - a "Link a document that is already uploaded" action expands the patient's other documents (those not linked to this visit or follow-up), each with a Link button;
    - each linked row has an Unlink button.
    Fixed notices for linked and unlinked. 404 and 409 show fixed text. On the unfiltered page and the viewer, rows only show their links as text.

### Timeline

13. **New kind.** Timeline gains `document_uploaded`, with `document_id` as its one subject. A successful upload writes it in the same transaction as the row and the audit event, with the same rollback and file cleanup as S3.1. Link changes write no timeline event.
14. **Timeline read.** The timeline item for it carries the document id and the current filename (read live, like care item names). The web timeline row says "Document uploaded", shows the name, and links to the viewer. A document row that was never uploaded through S3.2 (made in S3.1) has no event, because there is no backfill.
15. **Migration safety.** After migration `0016`, up, down, up works. A row of the new kind with a missing or extra subject id is refused by the check constraint. Downgrade removes `document_uploaded` timeline rows first (said in the migration docstring).

### Proof

16. **Break it once.** The builder removes in turn the patient scope on the link check, the clinic scope on the link lookup, and the `nosniff` header, sees a test fail each time, restores them, and records it in the review packet.
17. **No echo.** No error body or log line contains the filename or a submitted id. A test checks the 404, 409 and 422 paths of PATCH and the filtered list.
18. **Visual proof** in `.shipit/proof/S3.2/` (see below).

## Changes

- Data, migration `0016`:
  - `document` gets nullable `appointment_id` and `follow_up_id`, with composite FKs `(appointment_id, clinic_id)` and `(follow_up_id, clinic_id)` (both targets already have unique `(id, clinic_id)`), and one index per link column on `(clinic_id, appointment_id)` and `(clinic_id, follow_up_id)` for the filter. Existing rows stay unlinked. "Same patient" is a service rule, not a constraint, so no new unique is added to `appointment` or `follow_up`.
  - `timeline_event` gets nullable `document_id` with composite FK `(document_id, clinic_id)` to `document`. The two check constraints `kind_known` and `subject_matches_kind` are dropped and recreated with `document_uploaded` and `document_id`. **This changes existing constraints, which is an AGENTS.md stop. See decisions.**
- API, in `api/documents.py`: the two new routes (single GET, PATCH), the `disposition` parameter, the filters, the optional link parameters on upload. Link validation lives in `services/document_service.py`; `document_repository.py` and the existing appointment and follow-up repositories do the scoped lookups. Timeline write goes through the existing `timeline_service.record`. `domain/timeline.py` adds the kind and `document_id`. Regenerated `openapi.json` and `schema.d.ts`.
- UI: viewer page under `app/(app)/patients/[id]/documents/[documentId]/`, filtered context on the Documents page (`features/documents/`), a "Documents" link on the calendar row and the follow-up queue row, the document row on the timeline screen, client functions in `lib/api/client.ts`.
- Config and dependencies: none. No new dependency, no AI call.

## Out of scope

- Linking to recalls, care items, care sessions or lab work. Lab work and its document link are S3.3.
- Document type, date, description, rename, delete or replace.
- A picker that lists every visit and follow-up a patient ever had from the document side. Linking starts from the visit or follow-up.
- Inline PDF embedding, thumbnails, zoom, rotate, annotations, OCR.
- Backfill of timeline events for documents uploaded in S3.1.
- Link counts on the calendar or the queue (the link is a plain "Documents" link).
- Fixing the Next proxy body-size item or the flaky concurrency test in `.shipit/open.md`.

## Decisions and risks

- **Timeline constraint change (needs your call, AGENTS.md stop).** S3.1 deferred this to here. Migration `0016` drops and recreates `kind_known` and `subject_matches_kind` on `timeline_event` and adds a column. No data is lost going up. Going down deletes `document_uploaded` rows so the old constraint can return. Recommendation: do it here, as PRODUCT.md already says. Alternative: skip the timeline entry and drop 13 to 15, which shrinks the slice but leaves uploads invisible on the timeline.
- **Inline viewing (recommended, needs your call).** Images show through `<img>`, which cannot run script, plus a sandbox CSP on the response. A PDF is opened in a new tab with `inline`, `nosniff` and a type decided from the file's first bytes, so the browser's own PDF viewer handles it. We do not send the sandbox CSP for PDFs, because Chrome's PDF viewer does not work under it. Tradeoff: a PDF opens in the app's own origin, so we rely on the browser's PDF sandbox. Alternative: keep PDFs download-only and show only images inline, which is safer but gives the viewer little value for reports.
- **Linking starts from the visit or follow-up (recommended).** The calendar and the queue already have the ids, so there are no pickers and no new "all visits for a patient" or "all follow-ups for a patient" routes. The current patient route lists upcoming visits only, which is useless for past reports. Tradeoff: from the Documents page alone you cannot attach a file to a visit. Alternative: add a patient visit-history route and pickers, which is a bigger slice.
- **Two independent links, optional.** One document can belong to a visit and a follow-up at once, and a follow-up can have many documents. No many-to-many table.
- **Patient match is a service rule.** A wrong-patient id is 404. A database constraint would need new unique keys on `appointment` and `follow_up`. Tests and the break-it-once step cover the rule.
- **Link edits are refused for inactive patients (your call).** Same as upload. Alternative: allow them, since nothing new is added. Recommendation: refuse, until a rule says otherwise.
- **Filename on the timeline.** It is read live from the document row and shown in the timeline response, as care item names are. It is still never in audit rows, logs or error bodies.
- **Branch base.** Branch from `slice/S3.1-document-upload` at its head, or from `main` once the S3.1 PR merges.
- **Open items:** the Next proxy body-size item in `.shipit/open.md` does not block this slice. This slice sends no large request bodies.

### Decisions made (the brief did not settle these)

- If both `appointment_id` and `follow_up_id` are in the page query, the visit wins and the follow-up is ignored. The calendar and the queue only send one.
- A visit heading uses the appointment only when that visit's patient is this patient. Otherwise the heading is "Documents for this visit", with no other detail.
- A follow-up heading uses the due date on a linked row. There is no get-one follow-up route, so an empty page says "Documents for this follow-up".
- "Link a document that is already uploaded" loads the first 100 unfiltered documents. Page size stops at 100.
- Link and Unlink stay on screen for an inactive patient, so the 409 can be shown. The upload form stays hidden.
- A bad link on an inactive patient is 404. The ownership check runs before the inactive check. A real change, including a clear, is 409.

### Unsure points

- The clinic-scope failure is a WHERE-clause assertion. Patient ids are unique across clinics, so a cross-clinic id already fails the patient check. The test listens for `clinic_id` in the appointment and follow-up WHERE clauses.
- Link-existing cannot see documents past the first 100.
- The completed-visit proof moved that visit's start time to today in the database. The product will not book a past slot or complete a future one.
