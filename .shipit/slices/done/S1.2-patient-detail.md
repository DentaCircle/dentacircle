# S1.2 Patient detail

Status: done
Branch: slice/S1.2-patient-detail
Size: M
Actual time: not recorded.

## Goal

Staff can open a patient from the list, see their details, correct them, and mark the patient inactive or active again, and every change is recorded in the audit log.

## Acceptance criteria

1. **Schema.** `alembic upgrade head` adds `patient.status` and `audit_event.changed_fields`. `downgrade` to `0004` removes them. Upgrade, downgrade, upgrade works. Existing patients become `active`.
2. **Detail.** `GET /patients/{id}` returns the S1.1 fields plus `status` (`active` or `inactive`). An unknown id, or an id from another clinic, returns 404. A malformed id returns 422.
3. **Edit.** `PATCH /patients/{id}` with any of `full_name`, `phone`, `date_of_birth` updates only the fields sent and returns the patient. Sending `date_of_birth: null` clears it. `phone_digits` is recalculated when `phone` changes. `patient_number`, `id`, `status` and any other field return 422 naming the field, never echoing the value.
4. **Edit validation.** The S1.1 rules apply to the sent fields: trim, blank name, name over 200, phone not 7 to 15 digits, date of birth in the future or before 1900-01-01. `full_name` and `phone` cannot be `null`. A failed `PATCH` changes nothing and writes no audit event.
5. **Status.** `PUT /patients/{id}/status` with `{status}` sets `active` or `inactive`. Any other value returns 422. The patient number, fields and history are untouched. Nothing is deleted.
6. **No-op.** An edit that changes no value, or a status set to its current value, returns 200 and writes no audit event.
7. **Audit.** A `PATCH` that changes values writes one `audit_event` in the same transaction: `action` `update`, `entity_type` `patient`, and `changed_fields` listing only the field names that changed (for example `["phone"]`). A status change writes `action` `status_change` with `changed_fields` `["status"]`. No name, phone, date of birth or old value is stored. If the audit write fails, the change is not saved. S1.1's `create` events have `changed_fields` empty.
8. **Roles.** `GET`, `PATCH` and `PUT status` allow `receptionist`, `clinician`, `clinic_admin`. `inventory_admin` gets 403. No session gets 401.
9. **Tenancy.** With two clinics, clinic A can never read, edit or change the status of B's patient, and B's row and audit trail are unchanged after the attempt. The clinic id comes from the session.
10. **List.** `GET /patients` returns `status` on each item and accepts `status=active|inactive`. Without it the list shows all patients, as in S1.1. Any other `status` value returns 422. The filter combines with `q` and paging, and `total` counts the filtered rows.
11. **Contract and checks.** The route-walk test passes with the new routes. `openapi.json` and `schema.d.ts` are regenerated. `make check` and `make web-build` pass.
12. **Detail page.** `/patients/[id]` shows ID, name, phone, date of birth, status and registered date. Roles that may edit see an "Edit" link and a "Mark inactive" or "Mark active" button. It shows "Patient not found", "You do not have access." and a generic error state. After the status button is used, the page shows the new status. A double click sends one request.
13. **Edit page.** `/patients/[id]/edit` is the S1.1 form prefilled. Clearing the date of birth works. A 422 shows its message next to the field. A double click sends one request. On success it goes to the detail page and shows "Saved." A role without access sees "You do not have access." and no form.
14. **List links.** In `/patients`, each name links to its detail page. Inactive patients show an "Inactive" badge. All, Active and Inactive links set `?status=`, and keep `q`. Search, page and status live in the URL.
15. **Nav.** "Patients" stays highlighted on the detail and edit pages.

## Changes

- Data (additive, on two existing tables, see Decisions):
  - `patient.status`: text, not null, server default `active`, check in `active`, `inactive`.
  - `audit_event.changed_fields`: text array, nullable. The service only accepts `full_name`, `phone`, `date_of_birth` and `status`.
  - No new table, index or extension. Migration `0005`.
- API (`clinic_id` from the session):

  | Route | Roles | Result |
  | --- | --- | --- |
  | `GET /patients/{id}` | `receptionist`, `clinician`, `clinic_admin` | 200, 401, 403, 404, 422 |
  | `PATCH /patients/{id}` | same | 200, 401, 403, 404, 422 |
  | `PUT /patients/{id}/status` | same | 200, 401, 403, 404, 422 |
  | `GET /patients` | same | gains `status` on items and the `status` filter |

  The PATCH body forbids extra fields. Status has its own route so it gets its own audit action.
- Code, in the existing layers:
  - `domain/patient.py`: `PATIENT_STATUSES`, and a function that compares old and new values and returns the changed field names.
  - `repositories/patient_repository.py`: `get` (optional row lock) and a `status` clause in `search`. `AuditRepository` stays add and read only.
  - `services/patient_service.py`: `get_patient`, `edit_patient`, `set_patient_status`. They load the row with a lock, apply the S1.1 rules, then call `audit_service.record(..., changed_fields=...)` in the same transaction.
  - `api/patients.py`: the three new routes.
- UI: `apps/web/features/patients/`: detail view, a shared patient form (the S1.1 new-patient form becomes create and edit modes), a status button. Pages `app/(app)/patients/[id]/page.tsx` and `[id]/edit/page.tsx`. The detail is loaded on the server. Edit and status go from the browser through the `/api` rewrite. The list gains links and the status filter. No new UI-kit component.
- Migrations: additive. Nothing is dropped or rewritten.

## Out of scope

- Appointments, care, follow-ups, documents or timeline sections on the detail page. Each later slice adds its own. No empty placeholders.
- Delete, merge, or duplicate handling.
- Showing the audit trail. The viewer is S7.3.
- Rules that use status elsewhere. S1.3 should refuse to book an inactive patient. That is not built here.
- New fields (gender, email, address, notes), age display, and optimistic version checks.
- Audit of reads.

## Decisions and risks

Needs your approval first (AGENTS.md stop):

- **Two new columns on existing tables.** `patient.status` and `audit_event.changed_fields`. Both are additive, with a default or null, so no existing data changes. AGENTS.md treats any change to existing tables as a stop, so I am asking rather than assuming. Alternative for status: a separate `patient_status` table. More joins, no benefit at this size.

Your calls (my recommendation first):

- **Status is `active` or `inactive`, no delete (recommended).** Inactive is for patients who moved away or asked to stop. History stays. Alternative: add `deceased` or `archived` later if a real need appears.
- **Who may change status: the same three roles.** It is reversible and hides nothing from search. Alternative: `clinic_admin` only.
- **List shows all patients by default, with a filter (recommended).** Keeps S1.1 behavior and lets staff find an inactive patient to reactivate. Alternative: hide inactive by default, which is tidier but needs an "include inactive" step to find them.
- **Audit stores field names and nothing else.** "phone changed" with no old or new value, as already decided in PRODUCT.md. For status I also store only `["status"]`, so the log says a status changed, not which way. The current status is on the patient. Tradeoff: no value history. If you need one, we would store status transitions only, since status is not personal data.
- **Last write wins on edits.** Two people editing one patient at once: the later save overwrites. I lock the row during the save so the changed-field list is accurate, but I add no version check. Fine at front-desk scale.

Risks:

- Edit is the first update of patient data. Tests use synthetic values, and names, phones and dates of birth stay out of logs, error bodies and audit rows.
- Same CSRF gap as S1.1 (SameSite=Lax, no token). It matters more with edit, still synthetic data only.
- The S1.1 form is refactored into a shared form. The S1.1 form tests must stay green.
- If this is too big, split the status filter and list changes (criteria 10 and 14) into a follow-up.

### Decisions made

- The edit screen is the same form as create. It always sends name, phone, and date of birth. A value that matches what is stored is a no-op and writes no audit event. The button label stays "Save patient".
- Success goes to `/patients/{id}?saved=1`. The detail page shows "Saved." only for that exact query.
- Registered date is the `YYYY-MM-DD` prefix of `created_at`. It is not shifted into the clinic timezone.
- New create events store `changed_fields` as `[]`. Rows written before this migration stay null. Neither stores values.
- A list URL with a status other than `active` or `inactive` is sent to the API, which returns 422, and the page shows the generic error.
- Detail and edit link back ("Patients" and "Patient"). The nav highlight already treats any `/patients/...` path as current.
- `inventory_admin` never sees the form, Edit, or the status button. The API still returns 403.

### Unsure points

- The registered date can be a day off from the clinic's local date when the timestamp is near midnight UTC. Worth a look if the desk expects the clinic's calendar date.
- Two people saving the same patient: the later save wins. The row lock makes the changed-field list accurate. There is no version check, as the brief decided.

### Checklist

- Tenancy: `get` and `search` filter by the session clinic. A second clinic gets 404 on read, edit, and status, and the row and its audit trail stay as they were. Pass.
- Access: the three new routes list `receptionist`, `clinician`, `clinic_admin`. `inventory_admin` is 403. No session is 401. The UI hides edit and the status button for a role that cannot use them. Pass.
- Migration is additive. Downgrade to `0004` drops the two columns. Existing patients become `active`. The check rejects any other status. Pass.
- Edit and status each commit with their audit row. A failed audit write leaves the patient unchanged. Pass.
