# S1.1 Patients

Status: done
Branch: slice/S1.1-patients
Size: M

## Goal

A receptionist can register a patient, then find them again by name, phone or patient ID in a paged list, and every registration is recorded in an audit log.

## Acceptance criteria

1. **Schema.** `alembic upgrade head` creates `patient`, `patient_number_counter` and `audit_event`. `downgrade` to `0003` removes them. Upgrade, downgrade, upgrade works.
2. **Create.** `POST /patients` with `{full_name, phone, date_of_birth?}` returns 201 with `{id, patient_number, display_id, full_name, phone, date_of_birth, created_at}`. `display_id` is `P-` plus the number padded to 4 digits (`P-0001`).
3. **Patient numbers.** Numbers start at 1 for each clinic and go up by 1. Two clinics each have their own `P-0001`. A number is never reused or changed. Two creates at the same time never get the same number (database unique `(clinic_id, patient_number)`).
4. **Validation.** `POST` returns the standard 422, without echoing submitted values, for: blank name, name over 200 characters, blank phone, a phone that is not 7 to 15 digits once spaces, `-`, `(`, `)` and a leading `+` are ignored, a date of birth in the future or before 1900-01-01. Name and phone are trimmed. A failed `POST` writes no patient and no audit event.
5. **Duplicates are allowed.** Two patients may share a phone (a family) or a name. The API does not block or flag them.
6. **List and paging.** `GET /patients?page=&page_size=` returns `{items, total, page, page_size}`. Default `page_size` is 20, maximum 100, `page` starts at 1. Order is name (ignoring case), then number. A page past the end returns an empty `items` with the real `total`. `page` below 1 or `page_size` outside 1 to 100 returns 422.
7. **Search.** `q` filters the list. Name: case-insensitive "contains". Phone: digits only, "contains", so `98765`, `+91 98765 43210` and `(98765) 43210` all find the same patient. Patient ID: `P-0012`, `p0012`, `p-12` or `12` match number 12 exactly. A `q` of only spaces is the same as no `q`. Several words in `q` must all appear in the name. `total` counts the filtered rows.
8. **Roles.** Create: `receptionist`, `clinician`, `clinic_admin`. List: the same three. `inventory_admin` gets 403 on both. No session gets 401.
9. **Tenancy.** With two clinics, a list or search in clinic A never returns B's patients, including an exact patient ID match. The clinic id comes from the session.
10. **Audit.** Every successful `POST /patients` writes one `audit_event` in the same transaction: `clinic_id`, `actor_user_id`, `entity_type` `patient`, `entity_id`, `action` `create`, `occurred_at`. No patient name, phone or date of birth is stored in it. If the audit write fails, the patient is not saved. Audit rows have no update or delete code path.
11. **Deny by default and contract.** The route-walk test passes with the new routes. `openapi.json` and `schema.d.ts` are regenerated. `make check` passes.
12. **Patients page.** `/patients` shows the list with a search box, a "New patient" link and Previous / Next links. It shows an empty state ("No patients yet" or "No patients match"), a 403 message for roles without access, and a generic error state if the API fails. Search and page live in the URL (`?q=&page=`), so the page works as a link.
13. **New patient page.** `/patients/new` has name, phone and optional date of birth. On success it goes to `/patients` and shows the new `display_id` in a confirmation line. A 422 shows a message next to the field named in the error. A double click sends one request. The "New patient" link is shown only to roles that may create.
14. **Nav.** "Patients" is added to the main and mobile navigation.

## Changes

- Data (additive only, UUID ids, `clinic_id` on all three, `created_at` where the table is new):
  - `patient`: `id`, `clinic_id` FK, `patient_number` (int, not null), `full_name` (varchar 200), `phone` (varchar 30, as entered after trimming), `phone_digits` (varchar 15, digits only, used for search), `date_of_birth` (date, null allowed). Unique `(clinic_id, patient_number)`. Unique `(clinic_id, id)` so later slices reference it with a composite key, as S1.0 does. Index on `(clinic_id, lower(full_name))`. Check on `phone_digits` length 7 to 15.
  - `patient_number_counter`: `clinic_id` (primary key, FK), `last_number` (int, not null). The service allocates with `INSERT ... ON CONFLICT DO UPDATE SET last_number = last_number + 1 RETURNING`, which locks the row for the rest of the transaction.
  - `audit_event`: `id`, `clinic_id` FK, `actor_user_id` (composite FK to `app_user` by `(id, clinic_id)`), `entity_type` (text), `entity_id` (UUID, no FK, because later entities share the table), `action` (text, check in `create`, `update`, `status_change`, `delete`), `occurred_at` (timestamptz, default now). Index `(clinic_id, entity_type, entity_id, occurred_at)`. Index `(clinic_id, occurred_at)`.
- API (`clinic_id` always from the session):

  | Route | Roles | Result |
  | --- | --- | --- |
  | `POST /patients` | `receptionist`, `clinician`, `clinic_admin` | 201, 401, 403, 422 |
  | `GET /patients` | `receptionist`, `clinician`, `clinic_admin` | 200, 401, 403, 422 |

  There is no detail, edit or delete route here (S1.2).
- UI: `apps/web/features/patients/` (list view, search form, new-patient form), pages `app/(app)/patients/page.tsx` and `app/(app)/patients/new/page.tsx`, and a nav entry. The list is loaded on the server with the session cookie, like `/auth/me`. The create form posts from the browser through the `/api` rewrite, like login. No new component from the UI kit: a plain table, `Input`, `Label`, `Button`, `Card` and `Badge` that already exist.
- Migrations: one revision `0004`. New tables only. Nothing existing is changed or dropped.
- Code, in the existing layers:
  - `models/patient.py`, `models/patient_number_counter.py`, `models/audit_event.py`.
  - `repositories/patient_repository.py` (add, paged search, count, number allocation) and `repositories/audit_repository.py` (add and read only). Every method takes `clinic_id`.
  - `services/patient_service.py` (normalise and validate, allocate the number, create patient and audit event together, search rules) and `services/audit_service.py` (`record(...)`, the one place that builds an event).
  - `domain/patient.py`: phone and date checks, `display_id`, and the parse of a search term into name words, digits and an optional number.
  - `api/patients.py`, registered in `main.py`.
  - `CurrentUser.id` is already available as the actor.

## Out of scope

- Patient detail page, edit, status (active or inactive), status filter, delete or merge (S1.2).
- Last visit, next appointment, pending attention columns (they need later slices).
- Gender, email, address, emergency contact, notes. Add only when a slice needs them.
- Sorting choices. Order is fixed.
- Duplicate detection or warnings.
- Audit viewer, and audit of reads (S7.3). Login and logout stay unaudited until a later slice decides.
- Importing patients from a file.
- Full-text or fuzzy search. Search is plain "contains".

## Decisions and risks

No new dependency, no new extension. This migration adds tables only, so it is not an AGENTS.md migration stop.

Your calls:

- **Patient ID is a number per clinic, shown as `P-0001` (recommended).** Short enough to say on the phone. Cost: a small counter table so concurrent creates cannot collide, and numbers can have gaps if a create is rolled back after allocation (the counter update rolls back with it, so in practice there are none). Alternatives: `max + 1` with a retry (no extra table, but a race to reason about), or show the UUID (not usable by people).
- **Who may register and list patients.** I recommend `receptionist`, `clinician` and `clinic_admin`, and no access for `inventory_admin`. Clinicians need to register a walk-in. The clinic admin is often the owner. Tradeoff: an admin who is not clinical sees patient data. If you want admin as manage-only, drop it from both routes.
- **Minimum fields: name, phone, optional date of birth (recommended).** Phone is required because the coordinator queue (S2.4) is built around calling people. Date of birth is optional because it is often unknown at the front desk. More fields come with S1.2 or when a later slice needs them.
- **Search by "contains" with no new index.** Plain `ILIKE` on name and a digit match on `phone_digits`. Fine for one clinic with thousands of patients, and it avoids the `pg_trgm` extension (an AGENTS.md stop). If a clinic grows to tens of thousands and search feels slow, that is the time to add a trigram index.
- **Audit stores no patient values.** The event says who created which patient and when, nothing more. That keeps patient data out of a table that is meant to be long-lived and widely read. Tradeoff: S1.2's update events will record changed field names (not values), so the audit shows "phone changed" but not the old number. I would keep it that way unless you need a value history.
- **Audit is written by the service, not by a database trigger or a decorator.** One explicit call, easy to read and test. Tradeoff: every future write must remember to call it. The test for each future slice covers that.
- **Phone is stored as entered and as digits.** The digits form is what search and a later "duplicate" check use. Country codes are not interpreted: `+91 98765 43210` is 12 digits and `98765 43210` is 10, so a search by the last 10 digits finds both.

Risks:

- This is the first slice with a table that holds patient data. All tests use synthetic names and invented phone numbers. Names, phones and dates of birth never go in logs or error messages. The 422 body names the field, not the value.
- The counter row lock makes concurrent creates for one clinic take turns. That is fine at front-desk speed.
- Browser-side create relies on SameSite=Lax with no CSRF token, the known gap already in PRODUCT.md. It matters more now that patient data is written. Synthetic data only, as before.
- The list page shows patient data on screen. Page and component tests use made-up names, and no screenshots go into the repo.

### Decisions made

- A search is one kind of match, not all three at once. `P-0012`, `p0012`, `p-12`, and a bare number of 1 to 4 digits (`12`, `0012`) match that patient number and nothing else. Five or more digits, or digits with `+`, spaces, `-`, or parentheses, match the phone by "contains". Any other text is a name: every word must appear, in any order. `%` is a literal character.
- A bare `10000` is a phone fragment. `P-10000` is the id. Display ids past 9999 still work with the `P-` form.
- `patient` has `created_at`. The counter does not. `audit_event` uses `occurred_at` and does not also store `created_at`.
- A failed create rolls the counter back with the transaction, so the next success reuses that number. Tested.
- The confirmation is `/patients?created=P-0001`. The page shows it only when the value looks like a display id.
- A `page` query that is not a positive integer is treated as page 1.
- `/patients/new` shows "You do not have access." and no form for a role that cannot create. The API still returns 403.

### Unsure points

- The 4-digit cutoff is the part most worth a second look. It is what makes `12` an id and `98765` a phone, which is what the brief's examples do. A clinic past patient 9999 looks up the longer id with `P-`.
- The list page calls `/auth/me` again, the same way the dashboard does, on top of the layout check.
