# S1.5 Appointment status flow

Status: done
Branch: slice/S1.5-appointment-status-flow
Size: M (19 criteria; the proof criteria add a little, but no new feature code)
Actual time: not recorded.

## Goal

Front desk and clinicians can move a visit through arrived, in progress and completed, or mark it no-show, from the calendar, and every change is audited.

## Acceptance criteria

### API

1. **One route.** `POST /appointments/{id}/status` with body `{"status": "<target>"}` returns 200 and the same item shape as cancel (`CalendarItemResponse`). Targets are `arrived`, `in_progress`, `completed`, `no_show`. Any other value, including `scheduled`, `cancelled` or a missing field, returns 422 naming `status`. Extra fields return 422. Errors never echo the value. Cancel stays on `/cancel`.
2. **Allowed moves.** Only these:
   - `scheduled` to `arrived`
   - `scheduled` to `no_show`
   - `arrived` to `in_progress`
   - `in_progress` to `completed`

   Every other pair returns 409 `invalid_status` and changes nothing. That includes the same status again, skipping a step (`scheduled` to `completed`, `arrived` to `completed`), and any move out of `completed`, `cancelled` or `no_show`.
3. **Arrived only today.** `arrived` is refused with 422 on `status`, code `not_today`, unless the visit starts on clinic-today (clinic-local date, from the clinic timezone). A visit on another day, earlier or later, is refused.
4. **No-show only after the start.** `no_show` is refused with 422 on `status`, code `not_started`, while `now` is before `starts_at`. At exactly `starts_at` it is allowed.
5. **Who may do what.** `receptionist`, `clinician` and `clinic_admin` may set `arrived` and `no_show`. Only `clinician` and `clinic_admin` may set `in_progress` and `completed`. A receptionist asking for those gets 403. `inventory_admin` gets 403 for everything, and no session gets 401. A forbidden request changes nothing and writes no audit row.
6. **Order of checks.** 401, then role, then 404 (unknown or other-clinic id), then 422 on the body, then 409 for a bad move, then 422 for the time rules. A 409 therefore never depends on the clock.
7. **Audit.** One `audit_event` in the same transaction: `entity_type` `appointment`, `action` `status_change`, `changed_fields` `["status"]`. No values and no direction, as for cancel. If the audit write fails, the status is not saved. A rejected request writes nothing.
8. **Slots.** `no_show` frees the clinician's and the patient's time at once (the constraints already ignore it): availability offers it and a new booking for it succeeds. `arrived`, `in_progress` and `completed` keep it blocked. A status change never trips an exclusion constraint.
9. **No double move.** The row is locked. Two requests for the same move at once give one 200 and one 409. A status change racing a cancel or a reschedule of the same visit gives one winner and one 409 (a real two-session test, as in S1.4).
10. **Patient state.** Moving a visit whose patient is now `inactive` still works. The inactive rule applies to booking only.
11. **Tenancy.** Clinic A cannot change clinic B's visit (404).
12. **Contract and checks.** The route-walk test passes. `openapi.json` and `schema.d.ts` are regenerated. `make check` and `make web-build` pass.

### Web (calendar rows)

13. **Row actions by status.** A `scheduled` row keeps "Reschedule" and "Cancel" and gains "Arrived" and "No-show". An `arrived` row shows "Start". An `in_progress` row shows "Complete". `completed`, `no_show` and `cancelled` rows show no action.
14. **By role.** "Start" and "Complete" show only to `clinician` and `clinic_admin`. The rows use the roles the page already has. The API check in 5 stays the real rule.
15. **Confirm where it cannot be undone.** "No-show" and "Complete" first ask "Mark as no-show?" or "Mark as completed?" with "Yes" and "Keep". "Arrived" and "Start" send at once. Every action sends one request even on a double click.
16. **Outcomes.** On success the calendar reloads on the same view, date and clinician with a notice: "Marked arrived.", "Marked in progress.", "Marked completed." or "Marked no-show." On 409 "This appointment's status has already changed." and reload. On 403 "You do not have access." On 422 `not_today` "Arrived can only be set on the day of the visit." On 422 `not_started` "No-show can only be set after the start time." Other failures "Something went wrong."
17. **Notice values.** A `notice` outside the known list is ignored, as today. The four new notices are known.

### Proof that it works (tests and screenshots)

18. **Tests that can fail.** Each rule in 2 to 11 has a test that fails if the rule is removed. The checks, in the build:
    - The transition test walks all 36 status pairs (6 by 6) from one expected table written in the test. It does not read `STATUS_TRANSITIONS`, so a wrong edit to the table is caught.
    - The role test walks every role by every target (4 by 4), checks the status code and that the row and the audit table are unchanged on 403.
    - Time rules use a fixed clock at the edges: one minute before and after clinic midnight, `now == starts_at`, and `Europe/London` on a clock-change day.
    - Concurrency tests use two real sessions and assert exactly one 200.
    - Before handing over, the builder breaks each of these once on purpose (drop the role check, drop the row lock, loosen the table, drop the time rule), confirms a test goes red, then restores it. The result goes in the review packet.
    - Web tests assert on what the user sees (button names, notices, requests sent), not on class names or snapshots.
19. **Screenshots of the real app.** The builder runs `make dev` on synthetic data and takes screenshots of the calendar in a browser, saved in `.shipit/proof/S1.5/` as `NN-name.png`, with a short `index.md` saying what each one shows and the steps that produced it. Required shots:
    1. A `scheduled` row as a receptionist: Reschedule, Cancel, Arrived, No-show.
    2. The same row after Arrived: badge "Arrived", with no Start button for the receptionist.
    3. The same visit as a clinician: Start.
    4. After Start: badge "In progress" and Complete. Then the "Mark as completed?" confirm.
    5. After Complete: badge "Completed", no actions, notice "Marked completed."
    6. A visit later today: No-show refused with "No-show can only be set after the start time."
    7. A visit on another day: Arrived refused with "Arrived can only be set on the day of the visit."
    8. A visit whose start has passed: the "Mark as no-show?" confirm, then the row as "No-show" and the same time offered again on the booking screen.
    9. A stale tab: the same visit moved in a second tab, then the first tab shows "This appointment's status has already changed."
    10. An `inventory_admin` opening `/calendar`: "You do not have access."
    Every screenshot uses generated names (for example "Test Patient One"). No real patient data, as AGENTS.md requires. A shot that does not match its caption fails review.

## Out of scope

- Undo. No `no_show` back to `scheduled`, no `arrived` back to `scheduled`. A wrong click is fixed outside the product for now (see risks).
- Cancel from `arrived` or later. Cancel still works on `scheduled` only.
- Care sessions, and completing a visit from a care record (S2.1 and later). Here "completed" is a manual button. Whether care must exist first is S2.1's call.
- A clinician seeing only their own visits, or acting only on their own. Any clinician may advance any visit.
- Late arrival after a no-show, arrival times, wait times, and a status history view (S2.6 timeline).
- Showing status on the patient page's upcoming list. Any change to booking or reschedule rules.
- Role-based nav hiding (S7.1). Reminders or messages to the patient.

## Decisions and risks

Your calls (my recommendation first):

- **Strict forward steps (recommended).** `scheduled` to `arrived` to `in_progress` to `completed`, with `no_show` only from `scheduled`. Simple to test and to explain. Alternative: allow `arrived` to `completed` directly for quick visits. Tradeoff: one fewer click, but a looser rule that S2.1 may want to tighten.
- **Role split (recommended).** Reception sets arrived and no-show. Only a clinician or `clinic_admin` starts and completes. Completing a visit is clinical-adjacent and will later tie to care. Alternative: all three roles do everything, which is simpler but lets reception close a visit the clinician has not seen.
- **Time rules (recommended).** Arrived only on the visit's day, no-show only after the start. These stop typos that would block a slot or hide a real visit. Alternative: no time rules, with fewer error states. The risk is a no-show set at 9am for a 3pm visit, which frees the slot for good.
- **One route with a body, not four routes (recommended).** One schema, one test table, one UI component. Alternative: `/arrive`, `/start`, `/complete`, `/no-show`, where each route declares its roles in plain sight. The cost is four near-identical routes.
- **No undo (recommended for now).** Undoing `no_show` would have to re-take a slot someone else may now hold, which needs conflict handling (409 `slot_taken`). That is a slice of its own. Alternative: allow `no_show` back to `scheduled` here and accept the conflict handling.
- **Screenshots from the browser the agent drives, not Playwright (recommended).** The builder drives a browser with the IDE's browser tools and saves PNGs. No dependency, no CI change. Tradeoff: the proof is a one-time record, not a test that reruns. Alternative: add Playwright with one end-to-end spec that takes the same shots on every run. That is a new dependency, a browser download and a CI job, so it needs your yes, and it fits better in S2.7 (the core loop check) than here.
- **Proof is committed (now a project rule).** About ten small PNGs in `.shipit/proof/S1.5/`, synthetic data only, in their own commit so the diff stays readable. `/ship-seal` embeds them in the PR description with URLs pinned to the pushed commit, using `.github/pull_request_template.md`.
- **Calendar keeps showing `completed` and `no_show`.** Only `cancelled` is hidden, as decided in S1.4.

Risks:

- A wrong "No-show" or "Complete" click cannot be fixed in the product. The confirm step is the only guard. Likely first complaint in review; the answer is an undo slice, not a quiet widening of this one.
- A visit still `scheduled` the next day (nobody marked it) can only become `no_show`, not `arrived`. That is on purpose, but the desk may find it strict.
- `in_progress` and `completed` visits keep blocking the clinician's time, as they do now. If a visit runs long, the next slot is not freed. Not changed here.
- Booking refuses a start in the past, so a visit whose start has passed cannot be made in the app. Screenshots 6 to 8 need a real wait: the builder books the next free slot today and waits for it to pass (15 minutes at most), and must run while the clinic is open. The tests do not wait, they use a fixed clock. No back door, no test-only route and no hand edit of the database.
- Screenshots can drift from the code. Each one is taken after the last UI change and the commit hash goes in `index.md`.
- Role rule sits in the service/domain, not in a route dependency. The route-walk test only proves the three-role gate. The per-target rule gets its own role-by-target test table.

### Decisions made

- Per-target role runs in the service after the row is found and the body is valid, before the transition. A receptionist asking for `in_progress` or `completed` gets 403 even when that move is also illegal. `scheduled` and `cancelled` are not role-gated; the HTTP body rejects them as 422, and a direct service call gets 409.
- The 409 sentence is "This appointment's status has already changed." The page keeps it as the `changed` notice, same pattern as the success notices.
- Start and Complete are hidden with `canAdvance`. inventory_admin never reaches the calendar; the row tests still treat that role as `canAdvance` false.
- Thursday 15 Oct was extended to 22:00 through `PUT /clinic/day` so same-day visits could be booked after 18:00, then restored to 09:00–18:00. Said in `index.md`.

### Unsure points

- A reschedule that commits first leaves the visit `scheduled`, so a later arrived still succeeds. The concurrency test makes the status change take the lock first, then the reschedule gets 409. Both cannot win. The brief's "one winner and one 409" is that test, not a race where reschedule wins.
- Shot 8's booking screen does not list 19:30. Availability only offers a start that is still ahead, and the shot was after 19:30. The service test is what shows a new booking at the freed start succeeding while the clock is still before it.
- A Next.js dev overlay appeared during the shots (it pointed at the calendar screen). It was collapsed and is not in the PNGs. It looks like the browser tool's element refs, not a product error.
