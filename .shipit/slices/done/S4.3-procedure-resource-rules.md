# S4.3 Procedure resource rules and consumption

Status: done
Branch: slice/S4.3-procedure-resource-rules
Size: M
Actual time: about one calendar day (migration 0020, consumption in visit completion, rules API and page, proof).

## Goal

An inventory admin can say which items a visit type uses and how many, and completing a visit of that type takes that stock out automatically, with a history row that points at the visit.

## Acceptance criteria

### Rules

1. **Set a rule.** `PUT /appointment-types/{type_id}/resource-rules/{item_id}` with `{quantity}` creates or replaces the rule and returns 200 with the rule. `quantity` is a whole number from 1 to 1,000 (booleans, decimals, strings are 422). One rule per type and item.
2. **List rules.** `GET /appointment-types/{type_id}/resource-rules` returns the type's rules with item id, item name and quantity, sorted by item name. A type with no rules returns an empty list.
3. **Remove a rule.** `DELETE /appointment-types/{type_id}/resource-rules/{item_id}` returns 204. A missing rule is 404. Past transactions are untouched.
4. **Inactive item.** A rule cannot be created for an inactive item (409 `item_inactive`). An existing rule for an item that is later deactivated stays but is skipped at consumption (see 9).
5. **Roles.** Writes need `inventory_admin` or `clinic_admin`. Reads need those two plus `clinician`. `receptionist` is 403, no session is 401. Order of checks: 401, role, 422, 404, 409. The route-walk test passes.
6. **Tenancy.** Every query filters `clinic_id`. A type or item from another clinic is 404, with no hint of which part failed. The rule row's type and item share its clinic (composite foreign keys).
7. **Audit.** Create, replace and delete each write one `procedure_resource_rule` audit event (field names only, no quantity) in the same transaction.

### Consumption

8. **Completing consumes.** When a visit moves to `completed`, for each rule on its appointment type the service writes a `consumption` transaction in the same transaction as the status change. The change is negative, `reason` is null, and the row stores the visit id.
9. **Which stock.** For each rule, take from batches that are not expired (clinic-local date) with stock above 0, earliest expiry first, batches with no expiry last, ties by batch number. A rule spans several batches when needed. An inactive item is skipped.
10. **Short stock never blocks the visit.** If the available stock is less than the rule quantity, take what exists and leave the rest. If there is none, write nothing for that rule. The visit still completes. Stock never goes below 0. Batches are locked in id order under the visit row lock, so a concurrent adjustment cannot push a batch negative.
11. **Once only.** A visit moves to `completed` once and there is no undo, so it consumes at most once. A test that replays `completed` gets the existing 409 and writes nothing more.
12. **Only on completed.** Arrived, in progress, cancelled and no-show consume nothing. Saving a care session consumes nothing (S2.1b: the session does not complete the visit).
13. **Atomic.** If any consumption or audit write fails, the visit stays at its old status. Nothing partial remains.
14. **Audit and timeline.** Each consumption transaction writes one `inventory_transaction` `create` audit event with no quantity. No new timeline kind and no stock figure on the patient timeline.
15. **History.** `GET /inventory/items/{id}/transactions` rows gain type `consumption` and a nullable `appointment_id`. Existing S4.2 shapes are otherwise unchanged. Stock and batch quantity already sum all transactions, so they drop automatically.
16. **Existing rules hold.** Restock and adjustment checks, the append-only trigger and the S4.2 tests still pass.

### Migration

17. **Migration `0020`** adds table `procedure_resource_rule` and changes `inventory_transaction`: new nullable `appointment_id` with composite foreign key `(appointment_id, clinic_id)` to `appointment`, and the type and sign checks recreated to allow `consumption` (negative change, null reason, `appointment_id` required; the other two types must have it null). Up, down, up works. Existing rows are valid under the new checks.

### Web

18. **Rules screen.** Under `/inventory`, a "Visit type rules" page lists each active appointment type with its rules, and lets `inventory_admin` and `clinic_admin` add an item with a quantity, change a quantity, and remove a rule. Clinicians see it read only. Empty state "No stock is used by this visit type." Fixed text for 404 and 409, field errors for 422.
19. **History.** The item history shows Consumption rows as "Used in visit" with a link to that visit's calendar day.
20. **Break it once.** Remove in turn: the clinic scope on the rule lookup, the batch lock, the expired-batch skip, the earliest-expiry order, and the write-role check on one rule route. A test fails each time. Record it in the review packet.
21. **Visual proof** in `.shipit/proof/S4.3/`.

## Out of scope

- Low-stock, out-of-stock and expiring-soon alerts (S4.4). Expired stock is skipped here, not alerted.
- Rules per care item, per tooth or per clinician. Fractions (whole units only, as in S4.1).
- Recording the shortfall when stock is short, or blocking completion on it.
- Undoing or editing a consumption. A mistake is fixed with a `correction`.
- Backfill for visits completed before this slice.
- Cost, supplier, billing. Receptionist access. Role-based navigation (S7.1).

## Decisions and risks

- **Key rules by appointment type (recommended).** Care items are free text with no catalog (S2.1a), so "procedure" has no id to hang a rule on. A visit type like Scaling is an id, and completion is an event we already have. Tradeoff: a visit with several procedures uses one rule set. Alternative: match by care item name when the item is completed. It is closer to the spec's "service completed", but spelling differences would silently skip consumption. I recommend the visit type now and a catalog later if it matters.
- **Trigger is visit completion.** PRODUCT.md already reads "session completion" as the visit being completed (S2.1b).
- **Short stock takes what exists and never blocks (recommended).** A clinician must be able to finish a visit. Tradeoff: a shortfall is not recorded, and shows only as stock at 0 until S4.4. Alternative: store the unmet quantity on a row, which adds a table or column.
- **Earliest expiry first, expired batches skipped.** This matches S4.2's note that S4.3 picks by expiry. Expired stock still counts in item stock until S4.4 decides.
- **Rule delete is a real delete.** A rule is setup, not history, and it is audited. Past transactions keep their visit link.
- **Existing table change (needs approval).** `inventory_transaction` gains a column and new checks. Nothing is removed. Alternative: a separate `consumption_link` table, which keeps `0019` untouched but splits one fact over two tables. I recommend the column.
- **Lock order.** Visit row first, then batches by id. It adds batch locks inside `change_status`, so I will check the deadlock risk against the S4.2 lock in a test.
- **Open items:** nothing in `.shipit/open.md` blocks this. The appointment concurrency flake may show in `make check`.
- **Branch base.** Current work sits on the S4.2 branch (sealed 2026-10-26). Branch from `main` if its PR is merged, otherwise from `slice/S4.2-restock-and-transactions`.

### Decisions the brief left open

- History also returns `visit_on`, the clinic-local date of the visit. `inventory_admin` cannot `GET /appointments`, and the history link has to open that calendar day.
- A create audit has `changed_fields` `[]`. A replace is always `update` with `["quantity"]`, even when the number is the same. A delete audit has `[]`. None of them store the quantity.
- A rule may point at an inactive appointment type. The page lists active types only. Deleting a rule for an item that is already inactive is allowed.
- A unique clash from two saves at once becomes 404. The brief does not name a code for that race.
- Lock order is the visit row, then the patient row through follow-up and recall, then the item's batches in id order. An adjustment locks one batch and never the visit.
- An empty type list says "No active visit types."
- The add form resets after a successful save so the item and quantity do not stay filled.

### Unsure points

- A consumption insert that fails the foreign key rolls the visit back through the shared flush. The status route would then report 404. That path is unlikely because the visit row is already locked in the same transaction.
- Replacing a rule with the same quantity still writes an `update` audit. The brief says a replace writes one audit. It does not say to skip an unchanged number.

- Roles: the route walk names the rule routes. A clinician sees the page without the forms. The API still returns 403. The nav still lists every section. Role-based navigation is S7.1.
