# S0.2 API skeleton

Status: done
Branch: slice/S0.2-api-skeleton
Size: M

## Goal

Someone can run the API with one command, call `/health` and `/health/ready`, see every
error in one JSON shape, apply an empty Alembic baseline to PostgreSQL, and write a
database-backed test with a ready-made harness.

## Acceptance criteria

1. **Config.** Settings load from environment variables: `DATABASE_URL` (required) and
   `LOG_LEVEL` (default `INFO`, must be a valid level). If `DATABASE_URL` is missing, the
   app refuses to start and the error names the variable.
2. **Liveness.** `GET /health` returns 200 with `{"status": "ok"}` and does not touch the
   database.
3. **Readiness.** `GET /health/ready` returns 200 when the database answers `SELECT 1`.
   When it does not, it returns 503 in the standard error shape.
4. **One error shape.** Unknown route (404), wrong method (405), a raised `HTTPException`,
   request validation failure (422) and an unhandled exception (500) all return
   `{"error": {"code": "...", "message": "...", "request_id": "..."}}`.
5. **No leaks in errors.** A 422 lists the failing field locations and rules but never
   echoes the submitted values. A 500 returns a fixed generic message and no exception text.
6. **Request id.** Every response, including errors, carries an `X-Request-ID` header. It
   is generated by the server (never taken from the client) and matches `request_id` in an
   error body.
7. **Request log.** Each request writes one log line with request id, method, path, status
   and duration. Query strings, headers and bodies are never logged. An unhandled exception
   logs its class name and request id, not its message.
8. **Alembic baseline.** `alembic upgrade head` on an empty database succeeds, creates only
   `alembic_version`, and stores the baseline revision. `alembic downgrade base` followed by
   `upgrade head` also succeeds. `env.py` reads the same `DATABASE_URL` as the app.
9. **Test harness.** Shared fixtures give tests (a) an API client, (b) a SQLAlchemy session
   that rolls back after each test, and (c) a throwaway database created and dropped per
   test run for migration tests. Database fixtures skip when `DATABASE_URL` is not set, as in
   S0.1.
10. **Commands.** `make api-dev` starts the API on port 8000. `make migrate` runs
    `alembic upgrade head`. `make check` and CI still pass, and CI now runs the database
    tests against its PostgreSQL service.
11. **Docs.** README gains the steps to run the API and apply migrations, and `.env.example`
    lists `LOG_LEVEL`.

## Changes

- Data: no tables. Alembic creates `alembic_version` only. A shared SQLAlchemy `Base` is
  added with a constraint naming convention, so later migrations get stable names. No
  `clinic_id` yet because nothing is clinic-owned.
- API, all public by design (see decisions):
  - `GET /health` -> `{"status": "ok"}`
  - `GET /health/ready` -> `{"status": "ok"}` or a 503 error
- UI: none.
- Migrations: additive. One empty baseline revision.
- Code layout under `apps/api/src/dentacircle/`. Only layers that have content are added:
  - `main.py` (app factory, `app`), `core/config.py`, `core/logging.py`, `core/errors.py`,
    `core/request_context.py` (request id and log middleware), `core/database.py` (engine,
    session dependency, `Base`)
  - `api/health.py` (thin routes), `services/health_service.py` (the readiness check)
  - `apps/api/alembic.ini`, `apps/api/migrations/` (`env.py`, baseline revision)
  - Tests: `tests/conftest.py`, `test_config.py`, `test_health.py`, `test_errors.py`,
    `test_request_context.py`, `test_migrations.py`, `test_database_session.py`
- Makefile: `api-dev`, `migrate`. Updated files: `README.md`, `.env.example`, `pyproject.toml`,
  `uv.lock`.

## Out of scope

- Auth, sessions, users, clinics, roles, the tenancy scoping helper (S0.4).
- Any real model, repository or service beyond the readiness check.
- Audit events (first patient write, S1.1).
- CORS, an `/api` path prefix, OpenAPI tuning. S0.3 adds these when the web app needs them.
- JSON or shipped log formats, metrics, tracing, rate limiting.
- A Dockerfile for the API or running it in Compose (S0.5, if needed).
- Async database access (see decisions).

## Decisions and risks

New dependencies need your approval (AGENTS.md stop). Proposed list:

- Runtime: `fastapi`, `uvicorn`, `pydantic-settings`, `sqlalchemy`, `alembic`.
  `psycopg` is already installed from S0.1. Pydantic v2 arrives with FastAPI.
- Dev: `httpx` (needed by FastAPI's test client).

Choices where I recommend one option:

- **Database driver and sync vs async: sync SQLAlchemy 2.0 with `psycopg`.** The FastAPI
  rules prefer async and name `asyncpg`. I recommend sync for now. Alembic is sync anyway,
  `psycopg` is already in the project, and sync code is easier to read, debug and test while
  you are learning the stack. Routes are plain `def`, which FastAPI runs in a thread pool.
  Tradeoff: if the clinic ever needs high concurrency, moving to async touches every
  repository. For one clinic that is unlikely. Tell me if you want async instead. It adds
  `asyncpg` (or psycopg async) and makes tests and Alembic setup more involved. Either way I
  record the answer in PRODUCT.md, since S0.1 left this open.
- **One `DATABASE_URL`.** S0.1 uses `postgresql://...` (plain psycopg). SQLAlchemy needs
  `postgresql+psycopg://...`. I will convert the scheme in config so there is still one
  variable.
- **Settings library.** `pydantic-settings` is a new dependency. The alternative is a small
  Pydantic model that reads `os.environ`, which avoids the dependency but means writing the
  env loading ourselves. I recommend `pydantic-settings`: small, typed and standard.
- **Health routes are public.** AGENTS.md says every route declares its roles and access is
  deny by default. Health checks must work without a login (load balancers, CI), and return
  no clinic or patient data. I will mark them explicitly as public in code. Please confirm
  this exception.
- **Logging unhandled errors.** Database errors can carry SQL parameters, which can be
  patient data. So a 500 logs only the exception class and request id. The full traceback
  is logged only when `LOG_LEVEL=DEBUG`, for local work. Tradeoff: less detail in
  production-like logs when debugging. This matches the rule that patient data never goes in
  logs.
- **Migration tests use a throwaway database.** The test creates and drops its own database
  so it never touches your dev data. This needs the database user to have `CREATEDB`. The
  Compose and CI users are the Postgres owner, so it works in both places.
- **Stacking on S0.1.** S0.1 is built but not reviewed or merged, and this slice needs its
  Makefile, lockfile and CI. Best: review and seal S0.1, merge it, then I branch S0.2 from
  `main`. If you want to keep moving, I can branch from `slice/S0.1-repo-tooling-ci`, but then
  S0.2's diff must be rebased after S0.1 changes. Also note ROADMAP.md still says
  "Now: S0.1 (not started)". `/ship-seal` fixes that.
- **Docker is still not installed here.** As in S0.1, I cannot run PostgreSQL locally. That
  means the readiness test, the migration tests and the session tests would be skipped on
  this machine, and the first real run is in CI. Installing Docker (or Colima) before the
  build would let me run them and report real results. Otherwise the review packet will say
  exactly what was not run.

### Decisions made

- Strict mypy needs `py.typed` and the Pydantic plugin, or it treats the installed package as untyped. No new dependency: the plugin ships with Pydantic.
- `make api-dev` passes `--no-access-log`. Uvicorn's access log prints the query string. Our own line does not.
- `downgrade base` removes the revision row and leaves the empty `alembic_version` table. That is Alembic's behavior. Upgrade puts `0001_baseline` back.
- 404 and 405 are raised as Starlette's `HTTPException`, so the handler is registered on that class. FastAPI's subclass still reaches it.
- The branch starts from the sealed S0.1 commit. `main` does not contain S0.1 yet, so this branch includes those commits until S0.1 is merged.

### Unsure points

- FastAPI's test client warns that `httpx` should be replaced by `httpx2`. The brief approved `httpx`, and the tests pass. I did not add `httpx2`.
- A `LOG_LEVEL=DEBUG` traceback includes the exception text, because Python tracebacks do. The `INFO` line does not.
- `/docs`, `/redoc`, and `/openapi.json` stay on. OpenAPI tuning is out of scope. They describe the health routes only.

### Click-through

1. `cp .env.example .env` if you do not already have `.env`.
2. `make db-up` and wait until `docker compose ps` shows the database healthy.
3. `make migrate`
4. `make api-dev`
5. `curl -D - http://127.0.0.1:8000/health` returns `{"status":"ok"}` and `X-Request-ID`.
6. `curl -D - http://127.0.0.1:8000/health/ready` returns the same while Postgres is up.
7. `curl -D - http://127.0.0.1:8000/missing` returns the error shape, and `request_id` matches the header.
8. `curl -D - 'http://127.0.0.1:8000/health?patient=synthetic-name'` and confirm the server log says `path=/health` and does not contain `synthetic-name`.
9. Stop Postgres with `make db-down`. `/health` still returns 200. `/health/ready` returns 503. Start it again with `make db-up` if you want it left running.

### Checklist result

No clinic-owned rows, so tenancy does not apply. The only routes we added are marked public and return no clinic or patient data. The migration is additive and reversible. The readiness check lives in the service. Logs, error bodies, and tests use synthetic markers, not patient data. Nothing here is an AI call or an audit event. The tests assert status codes, body keys, and that secret values are absent.
