# S5.1 Local WhatsApp inbox

Status: approved
Branch: slice/S5.1-openwa-inbox
Size: M

## Goal

Staff can send a WhatsApp message from a patient's conversation and read a test phone's reply through a local OpenWA container behind a replaceable provider interface.

## Acceptance criteria

1. **Local bridge.** An optional Compose profile runs open-wa (`@open-wa/wa-automate`, `openwa/wa-automate` image), pinned by image digest and runtime version, with API key, private session volume and loopback-only published port. Existing development works without it. Pair one dedicated account/session, bound server-side to one clinic. Only explicitly allowlisted test phones and synthetic records are allowed; show connected/disconnected/unconfigured without exposing credentials.
2. **Patient identity.** Staff explicitly link one full international number (E.164) to one active patient. Links are immutable, unique per patient and per clinic/account/number; repeats are idempotent, conflicts 409. Never infer identity from patient.phone. Ignore unknown senders, other sessions, groups, outgoing echoes and non-text events. Inactive patients retain history/incoming text but cannot be linked or sent to.
3. **Provider seam.** A `MessagingProvider` protocol exposes connection/eligibility, text sending and normalized incoming events. The OpenWA adapter owns HTTP, credentials and provider payloads; core services own validation/history/business rules. A fake adapter passes the same service contract tests. Meta later requires its own adapter, webhook verification and template/window rules; it must reuse the inbox/services.
4. **Outbound reliability.** Accept trimmed text of 1–2,000 characters. Persist an attempt and staff audit before dispatch, with unique client request id. Same request/patient/body returns the saved attempt without redispatch; conflicting reuse is 409. States: sending, accepted, failed, unknown. Accepted means provider acceptance only; timeout means unknown, crash-left sending means unconfirmed. No automatic retries or retry form. Audit state changes with the initiating staff actor; never log bodies/provider error text.
5. **Inbound reliability/access.** Verify the callback's secret header and configured session before trusting it; derive clinic server-side. Persist linked direct text and provider provenance, deduplicating concurrent provider-message ids before acknowledgement. DB failure is retryable 503. Incoming actor is “Patient via WhatsApp,” with no fabricated staff AuditEvent. Staff routes allow receptionist/clinician/clinic_admin only (401/403 otherwise); foreign patients are 404. All reads/joins/counts are scoped. Messaging changes no care, appointment, follow-up, recall or timeline state.
6. **Inbox.** Main/patient navigation opens `/messages` and `/patients/[id]/messages`. Paginated inbox has one patient row with latest message/count, newest activity first; history is newest first with stable id ties (20 default/100 max). Show patient identity, explicit number link, plain-text messages, direction/time/actor/state, Send and Refresh. Include test-demo notice, connection/eligibility, empty/loading/error/no-access/inactive states. Prevent double clicks and retain the request id after uncertain submission. Replies appear on refresh; no simulated-reply form.

## Changes

- Data/migration: two new tables only, additive next Alembic revision (expected `0021`, verify head). `messaging_contact`: UUID id, clinic/patient, provider/account key, E.164 number, staff creator/time; unique patient and account/number per clinic. `message`: UUID id, clinic/contact/account, direction/body/state, nullable staff creator/request UUID/provider id/provider timestamp, created/updated times. Composite clinic FKs, contact/account consistency, body/direction/state/actor checks; unique clinic/request and clinic/account/provider-message ids; clinic/contact/time/id and clinic/time/id indexes. Inbound state is received; outbound states above. No existing table changes, credentials in tables or new system user.
- API: `GET /messaging/connection` → status/eligibility; `GET /messages` → paged patient/latest-message/count rows. `GET`/`PUT /patients/{id}/messaging-contact` → link/null, PUT `{number}`. `GET /patients/{id}/messages` → page; POST `{body,request_id}` → message attempt (201 new/200 replay). Message fields: id, patient_id, direction, body, state, created_at, updated_at, provider_sent_at, created_by `{id,name}`/null. Link fields: id, patient_id, number. Safe 409 for inactive/unlinked/ineligible/conflict, 422 invalid input, 503 unavailable before attempt creation.
- Callback: `POST /integrations/messaging/openwa/events` → 204 committed/duplicate/ignored, 401 bad credential, 422 malformed, 503 DB failure. Extend route-access tests for this explicit credential-protected category; no public bypass. No body/number values in audit/logs/errors.
- Runtime/UI: standard-library HTTP adapter, optional Docker service, ignored keys/session files, provider webhook configuration with durable journal where supported; feature-local screens and generated OpenAPI/types. No extra app dependency, worker or public tunnel. Builder adds README pairing/start/disconnect instructions. Detailed contracts: [messaging design](../../docs/openwa-messaging.md).

## Out of scope

Meta implementation/accounts, templates, automatic replies/campaigns, slot selection/booking (S5.2), reminders (S5.3), real patient use, attachments/groups, old-chat import, unread/search, number reassignment, QR UI, delivery/read receipts, automatic retries and timeline additions.

## Decisions and risks

Revised OpenWA brief approved 2026-11-01. Local hosting still transmits through WhatsApp. OpenWA is unofficial and may disconnect or face account restrictions. Verify the pinned release supports saved-contact test sending and incoming events without a paid licence; no licence purchase is authorized. A send cannot be rolled back: uncertain attempts require inspection. Preserve unrelated checkout changes and build from merged S4.4. If the pinned release needs a custom bridge or broader delivery machinery, stop and propose splitting the slice.

## How it will be verified

Service/API PostgreSQL tests cover each criterion: adapter contracts, identity/allowlist, boundaries, roles/tenancy/FKs, paging, duplicate/concurrent sends/events, before/after-send DB failures, safe logs, atomic audits and unchanged business state. Vitest covers forms, literal text, refresh, request-id reuse and all listed states. Validate Compose; run `make api-types`, `make check`, `make web-build`. Routine CI mocks WhatsApp.

Human proof: pair dedicated test phones, send/reply/refresh, restart, disconnect and replay a callback. Record unavailable live checks. Screenshots in `.shipit/proof/S5.1/`: inbox, two-way conversation, empty/unlinked, disconnected/uncertain and inactive history. Hide test numbers, QR/session secrets and actual account identity; include sanitised samples and pinned versions.
