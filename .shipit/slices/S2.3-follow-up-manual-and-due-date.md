# S2.3 Follow-up: manual create and due date on completion

Status: approved
Branch: slice/S2.3-follow-up-manual-and-due-date
Size: M (one column made nullable, one create route, one optional field on the status route, two small UI pieces)

## Goal

Staff can create a follow-up for a patient by hand, and a clinician can set the follow-up date when completing a visit, so a callback no longer depends on unfinished care items.

## Acceptance criteria

### API

1. **Schema.** Migration `0011` makes `follow_up.appointment_id` nullable. Upgrade, downgrade, upgrade works. Downgrade to `0010` is refused with a clear error if any row has a null `appointment_id`. The composite FK to `appointment` still holds when the value is set. Nothing else on the table changes.
2. **Manual create.** `POST /patients/{id}/follow-up` with `{due_on}` creates one `follow_up`: status `scheduled`, `appointment_id` null, the given `due_on`. It returns 201 with the same body as the read route.
3. **Date rules.** `due_on` must be today (clinic-local) or later, and at most 365 days ahead (the S1.3 horizon). Earlier or later gives 422 `validation_error` with the field name, and no row. A missing or non-date value gives 422. Extra fields are refused.
4. **One open follow-up.** If the patient already has an open follow-up (`scheduled`, `contacted`, `booked`), create gives 409 `follow_up_open` and changes nothing. A `completed` or `cancelled` one does not block.
5. **Inactive patient.** Manual create gives 409 `patient_inactive` and writes nothing.
6. **Create audit.** Manual create writes `follow_up` / `create` / `changed_fields: []`, with the creating user as actor, in the same transaction. If the audit write fails, no row is saved.
7. **Roles and tenancy (create).** `clinician`, `receptionist`, `clinic_admin` may create. `inventory_admin` gets 403. No session gets 401. Order of checks: 401, role, 404 (unknown or other-clinic patient), 422, 409.
8. **Date on completion.** `POST /appointments/{id}/status` accepts an optional `follow_up_due_on` (date). It is allowed only with `status: completed`. With any other status it gives 422 and the visit does not move. The rest of the request and the response are unchanged.
9. **Date creates a follow-up.** Visit completes, patient is active, `follow_up_due_on` is set, no open follow-up: one follow-up is created with that `due_on`, `appointment_id` = the visit, status `scheduled`. This happens even when no care item is open.
10. **Date replaces the default.** Same, but the patient also has open care items: the follow-up uses the clinician's date, not completion plus 7 days.
11. **Date on an existing follow-up.** If an open follow-up exists, its `due_on` becomes the clinician's date and its `appointment_id` becomes the visit. Its status is kept. Audit is `follow_up` / `update` / `["appointment_id", "due_on"]`. Without the date, S2.2 behaviour is unchanged (only `appointment_id` moves).
12. **Date rules apply here too.** The same today-to-365-days check as criterion 3, using the clinic-local day of completion. A bad date gives 422 and the visit stays `in_progress`.
13. **Inactive patient.** A visit of an inactive patient still completes and writes no follow-up, even with a date (same as S2.2).
14. **Who may set the date.** Only roles that may complete a visit (`clinician`, `clinic_admin`). A role that cannot complete still gets 403 from the existing check, before any date check.
15. **All or nothing.** If the follow-up write or its audit write fails, the visit stays `in_progress` and no row or audit event is saved.
16. **No change without the date.** Every S2.2 test still passes unchanged: with no `follow_up_due_on`, the default 7-day rule and the open-item check behave as before.
17. **Contract and read.** `GET /patients/{id}/follow-up` returns `appointment_id: null` for a manual follow-up. The route-walk test passes. `openapi.json` and `schema.d.ts` are regenerated. `make check` and `make web-build` pass.

### Web

18. **Create form.** `/patients/[id]/care` shows a "Follow-up date" field and a "Create follow-up" button when the patient has no open follow-up and the role may create. Success shows the new line "Follow-up due …" with the Scheduled badge. The form is hidden when a follow-up exists. `inventory_admin` still sees "You do not have access."
19. **Create form errors.** A past or too-distant date shows a plain message. "Already has an open follow-up." on 409 `follow_up_open`. "This patient is inactive." on 409 `patient_inactive`. A stale form after another tab created one refreshes to the existing line.
20. **Completion date.** On the calendar, confirming "Mark as completed?" shows an optional "Follow-up date" field. Empty sends no `follow_up_due_on`, so S2.2 behaviour. A date sends it. A 422 for a bad date shows a message in the confirm box and the visit is not completed.
21. **Care page null visit.** A manual follow-up (no visit) shows the same line as any other. Nothing on the page needs `appointment_id`.

## Changes

- Data:
  - `follow_up.appointment_id`: not null becomes nullable. No other change. The composite FK stays (a null part skips the check), so a set value is still clinic-checked. `clinic_id`, indexes, and the one-open partial index are untouched.
- Migration `0011`: one `ALTER COLUMN ... DROP NOT NULL`. Relaxes a constraint, loses no data. **This changes an existing column, so it needs your approval (see decisions).**
- API (`clinic_id` from the session):

  | Route | Roles | Result |
  | --- | --- | --- |
  | `POST /patients/{id}/follow-up` body `{due_on}` | clinician, receptionist, clinic_admin | 201, 401, 403, 404, 409, 422 |
  | `POST /appointments/{id}/status` adds optional `follow_up_due_on` | unchanged | unchanged, plus 422 for the date |

  `FollowUpBody.appointment_id` becomes nullable in the schema.
- Code, in the existing layers: `domain/follow_up.py` (create roles, date window as a pure function); `repositories/follow_up_repository.py` (no new query expected); `services/follow_up_service.py` (`create_manual_follow_up`, and `record_incomplete_care` takes an optional date); `services/appointment_service.change_status` passes the date through; `api/follow_ups.py` gets the POST; `api/appointments.py` gets the body field. `models/follow_up.py` makes the column optional.
- UI: a create form in `features/care/`, wired in `care-screen.tsx`. An optional date field in `features/calendar/status-button.tsx`, shown only for Complete. A client function for the POST and an optional argument on `changeAppointmentStatus`.
- No new dependency.

## Out of scope

- Any change of follow-up status (contacted, booked, completed, cancelled), editing a follow-up's date by hand, and the coordinator queue. That is S2.4.
- Due and overdue wording. `due_on` stays stored and shown as a date.
- A reason, note, or care-item link on a follow-up. No free text at all.
- Closing a follow-up when care finishes (still in `.shipit/open.md`).
- Setting the date from the care session form, or when completing from anywhere but the calendar.
- Recalls (S2.5), the timeline (S2.6), messages and reminders.
- A settings screen for the 7-day default.

## Decisions and risks

Recommendation first. Both migration and the behaviour in 11 need your call.

- **Make `appointment_id` nullable (recommended).** A manual follow-up has no visit, for example a patient who called in, or a patient who never had one. Tradeoff: every reader must handle null, and the column no longer proves a visit exists. AGENTS.md stops me from changing an existing column without asking. Alternatives: require a visit id on manual create (awkward, blocks the no-visit case), or add a second table (two lists, which PRODUCT.md rules out).
- **Clinician's date replaces an existing follow-up's date (recommended).** The clinician is the most recent authority on when the patient should return, and the brief for S2.2 only protected the coordinator's date from automatic changes. Tradeoff: it can move the date of a `booked` or `contacted` follow-up. Alternative: keep the existing date and ignore the clinician's, which silently discards what they typed.
- **Inactive patient with a date: nothing is written, the visit still completes (criterion 13).** Matches S2.2. Tradeoff: the clinician's date is dropped without a message. The calendar does not know the patient's status. Alternative: refuse completion with 409, which blocks routine work for a rare case. Tell me if you prefer the refusal.
- **Receptionist may create (recommended).** They are the coordinator. Tradeoff: more writers on follow-up data. Alternative: clinician and clinic_admin only.
- **A manual create on a patient with an open follow-up is refused, not merged.** It is a 409, not an update, and the page shows the existing one. Tradeoff: the user cannot change that date until S2.4.
- **The date window is today to 365 days, clinic-local.** Same guard as booking. Same-day follow-up is allowed.

Risks:

- Making a column nullable touches the S2.2 code path and its tests. Criterion 16 keeps them as the regression guard.
- Two requests creating at once rely on the partial unique index. The service locks the patient row first, as S2.2 does, so the loser gets a clean 409 rather than a 500. A concurrency test covers it.
- The branch is `slice/S2.2-incomplete-care`, which is sealed but not merged. Branch S2.3 from it, or from `main` once that merges.
