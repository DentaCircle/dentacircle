# S3.1 Document upload

Status: built
Branch: slice/S3.1-document-upload
Size: M

## Goal

Staff upload a PDF or image to a patient's record, see it in a list on the patient's Documents page, and download it again. The file sits behind a storage interface, so the disk can be swapped for a cloud store later.

## Acceptance criteria

### Storage interface

1. **One interface.** `integrations/storage/` defines `DocumentStorage` with `put`, `open` and `delete`, keyed by an opaque string. Core code (services, routes) imports only the interface and a `get_storage()` factory, never a path or an SDK. A test fails if a service module imports `pathlib` file writes or the local adapter directly.
2. **Local adapter.** The only adapter in this slice writes under `STORAGE_ROOT` (new setting, default `.data/documents`, git-ignored, listed in `.env.example`). The key is `{clinic_id}/{document_id}`, built by the server. A key that would leave the root (`..`, absolute path) is refused by the adapter.
3. **Fake for tests.** An in-memory adapter lets service and API tests run without disk.

### Upload

4. **Route.** `POST /patients/{id}/documents?filename=<name>` takes the raw file as the request body (no multipart) and returns 201 with the document item (see 11). `receptionist`, `clinician` and `clinic_admin` may call it. `inventory_admin` gets 403, no session 401. Order of checks: 401, role, 422, 404, then the rest.
5. **Allowed types.** PDF, PNG and JPEG. The type is decided from the first bytes of the file (`%PDF-`, the PNG signature, `FFD8FF`). The `Content-Type` header must agree with it. A different or unknown type is 415 `unsupported_media_type`. An empty body is 422.
6. **Size limit.** At most 8 MiB (8,388,608 bytes), counted while the body is read, never from `Content-Length` alone. Over the limit is 413 `payload_too_large`, and nothing is stored. 8 MiB is under the 10 MB default proxy limit that Next applies to `/api` (the note in PRODUCT.md for this slice).
7. **Filename.** Required, trimmed, folders removed (`a/b\c.pdf` becomes `c.pdf`), control characters removed, at most 200 characters after that. Empty after cleaning is 422. The name is only a label. It never becomes part of a storage key or a path.
8. **Inactive patient.** Upload is refused (409, same wording style as care and booking). An inactive patient's existing documents can still be listed and downloaded.
9. **Write order and rollback.** The file is stored first, then the row and the audit event are written in one transaction. If the database write fails, the stored file is deleted. A test with a failing database write asserts no row and no file remain.
10. **Audit.** A successful upload writes one `document` `create` audit event (who, what, when, no filename and no values). Failed uploads write none.

### Read

11. **List.** `GET /patients/{id}/documents?page&page_size` returns `{items, total, page, page_size}`, newest first (`created_at`, then `id`). Paging and 422 rules match `GET /patients/{id}/timeline`. An item has `id`, `filename`, `content_type`, `size_bytes`, `uploaded_at` and `uploaded_by` (`id`, `name`; deactivated users still resolve). Same three roles. Inactive patients can be read. Another clinic's patient is 404.
12. **Download.** `GET /patients/{id}/documents/{document_id}/file` streams the bytes for the same three roles. The response sets `Content-Type` from the stored type, `Content-Disposition: attachment` with a safe filename, `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`. A document of another patient or another clinic is 404. The storage key is read from the row, never from the request.
13. **Not audited.** Listing and downloading write no audit row (as for the timeline).
14. **No echo.** No error body or log line contains the filename or file content. A test posts a distinctive filename to every failing path (415, 413, 422, 409) and checks it is absent from the body.

### Web

15. **Page.** `/patients/[id]/documents` has a file picker with an Upload button, then the list: filename, type, size, who and when (clinic-local), and a Download link per row. Empty state: "No documents for this patient yet." `inventory_admin` sees "You do not have access." Not-found and error states match the care and timeline pages. Pagination as on the timeline.
16. **Upload feedback.** The picker checks type and size before sending, only to save a round trip. The API stays the authority. Success shows a notice and the new row. 413, 415, 409 and network or timeout errors each show fixed text. The upload has its own timeout, longer than the 5 s used for ordinary calls.
17. **Entry point.** The patient page has a "Documents" button next to "Care" and "Timeline" for the three roles. For an inactive patient the page hides the upload form and says why.
18. **Proxy works.** A file just under 8 MiB uploads through the `/api` rewrite on `make dev`, and one just over gets the API's 413, not a proxy error. If the proxy cuts it off, `next.config.ts` raises `proxyClientMaxBodySize`. This is a config change, not a dependency.

### Proof

19. **Break it once.** Before handover the builder removes the audit call, the tenancy scope on download and the magic-byte check in turn, sees a test fail each time, restores them, and records it in the review packet.
20. **Visual proof** in `.shipit/proof/S3.1/` (see below).

## Changes

- Data, migration `0015`, additive: new table `document` with `id`, `clinic_id`, `patient_id`, `uploaded_by_user_id`, `filename` (1 to 200 characters, check), `content_type` (check: the three allowed values), `size_bytes` (check: 1 to 8,388,608), `storage_key` (unique), `created_at`. Composite FKs `(patient_id, clinic_id)` and `(uploaded_by_user_id, clinic_id)`, plus unique `(id, clinic_id)` so S3.2 can link documents without a rebuild. Index on `(clinic_id, patient_id, created_at DESC, id DESC)`. No change to any existing table or constraint.
- Config: `STORAGE_ROOT` in `core/config.py` and `.env.example`. `.data/` in `.gitignore`.
- API, new `api/documents.py`: the three routes above. Pydantic response models and fixed error messages. New coded errors for 413 and 415 through `CodedHttpError`, with codes added next to the existing ones.
- Code, existing layers: `domain/document.py` (types, limits, filename cleaning, magic-byte sniffing, all pure and unit-tested), `models/document.py`, `repositories/document_repository.py` (every query scoped by `clinic_id`), `services/document_service.py`, `integrations/storage/` (`base.py`, `local.py`, `memory.py`, `__init__.py` with `get_storage`). This is the first code in `integrations/`.
- UI: `features/documents/` (screen, upload form, row, access, sizes and notices), the page under `app/(app)/patients/[id]/documents/`, the button on `patient-detail.tsx`, `listDocuments` and `uploadDocument` in `lib/api/client.ts`, regenerated `openapi.json` and `schema.d.ts`.
- No new dependency. Streaming uses `Request.stream()`, which FastAPI already has. Multipart is not used because it needs `python-multipart`, which is not in `uv.lock`.

## Out of scope

- Inline viewing or preview, thumbnails, and linking a document to a follow-up or an appointment. All S3.2.
- Lab work and its statuses. S3.3.
- Document type, document date and description. The spec lists them, but S3.1 stores only what the file itself tells us. Revisit in S3.2.
- A timeline entry for uploads. See decisions.
- Delete, replace, rename, undo. A mistaken upload stays until a later slice adds a retire path with its own audit.
- Several files at once, drag and drop, progress bar, resumable uploads.
- Virus scanning, text extraction, OCR, any AI call. DICOM and X-ray management stay outside the project.
- A cloud adapter, signed URLs, encryption at rest beyond what the disk gives. Synthetic data only until the DPDP question is settled.
- Cleanup of orphan files left by a crash between the file write and the commit.

## Decisions and risks

- **Raw body, not multipart (recommended, needs your call).** The browser sends the `File` as the body and the name as a query parameter. No new dependency, simple to test, and the size is counted as the stream is read. Tradeoff: it is not the form a reader may expect, and only one file per request. Alternative: add `python-multipart` (AGENTS.md stop: new dependency) and use `UploadFile`.
- **Types and size (recommended).** PDF, PNG, JPEG at 8 MiB. Covers reports, scans and phone photos. Tradeoff: large scans or other formats are refused. A bigger limit also needs the proxy setting in 18.
- **Local disk as the only adapter.** No new service or account. Tradeoff: files live on the API host, so a deployed API needs a persistent volume. Deployment is still deferred, so this is acceptable now.
- **Downloads only, never inline (recommended).** `attachment` plus `nosniff` means a crafted file cannot run in our origin. S3.2 can decide on inline PDF and image display with the viewer, and may need a stricter sandbox then.
- **No timeline entry yet (your call).** The timeline check constraint lists a closed set of kinds, so a `document_uploaded` kind needs a migration that changes an existing constraint, which is a stop in AGENTS.md. Recommendation: add it in S3.2, which also links documents to visits and follow-ups and so needs the subject columns anyway. Alternative: do it here, with the constraint change reviewed.
- **File and row are not one transaction.** Storage first, then the row, delete the file if the row fails (criterion 9). A crash in between can leave an unreferenced file. Harmless, never served, and listed as out of scope.
- **Filenames may hold patient names.** They are stored in the database like a patient name is, but never in audit rows, logs, error bodies or storage keys. Test and demo files use synthetic names.
- **Upload timeout.** The shared client uses a 5 s timeout, too short for 8 MiB on a slow link. The upload gets its own value and a test for it.
- **Branch base.** The working tree is on `slice/S2.8-appointment-client-maintenance`, which is sealed. Branch from its head, or from `main` once its PR merges.
- **Open items:** none in `.shipit/open.md` block this.

### Decisions made (the brief did not settle these)

- A filename over 200 characters after cleaning is 422. It is not cut short, so the user sees the problem.
- The service commits, so it can delete the stored file when the commit fails.
- The upload route is `async def` and runs DB and service work in the thread pool, because it reads the body as a stream.
- Receptionist may upload and read (write roles equal read roles).
- A row whose file is missing in storage returns 404 and logs only the document id.
- Relative `STORAGE_ROOT` resolves under the repo root. `.data/` is git-ignored.
- The upload notice uses `?notice=uploaded`, like the care pages, so it shows again on reload.
- The browser pre-check runs on submit only, not on file pick.
- Patient buttons now wrap (`flex-wrap`) because the new button pushed "Patients" off screen.

### Unsure points

- Next's dev proxy: after a body bigger than 10 MB, the next request on that connection hit a
  dead socket (about 30 s hang, then 500). The API's own 413 arrives fine, and the browser
  blocks files over 8 MiB, so I did not change `next.config.ts`. Please decide if that needs a
  follow-up slice.
- The filename is in the query string. The Makefile runs uvicorn with `--no-access-log`, so it is
  not logged. A server started with access logs on would log it.
- The download OpenAPI entry also lists `application/json` (the error shape).
- Rollback on failure is tested by forcing an audit failure and a commit failure. A crash of the
  process between the file write and the commit would leave an orphan file. No cleanup job exists
  (out of scope).
