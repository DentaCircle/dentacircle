# S6.1 Dashboard

Status: done
Branch: slice/S6.1-dashboard
Size: M

## Goal

Staff can start the clinic day from one dashboard and open the exact calendar or queue behind each count.

## Acceptance criteria

1. Receptionists, clinicians and clinic admins see the clinic-local date and today's clinic-wide appointments. Use the calendar's day-range rules: exclude cancelled visits; include no-shows and completed visits, including visits for inactive patients. Show the first six in start-time order, with ID as the tie-breaker, time, patient, visit type, clinician and status. The total covers the full day, not just the preview; its link opens that day's calendar without a clinician filter. Patient names link to patient detail.
2. Show separate counts for Follow-ups due, Recalls due, Open lab work and Reminders due. Follow-ups and recalls match their Due views: scheduled/contacted, due today or earlier, active patients only. Lab matches Open: pending/ready, including inactive patients. Reminders match S5.3's Due view: pending, due now or earlier, active patient and still-future scheduled visit. Use API totals, including when a queue spans multiple pages. Do not sum these into a patient count: queues may overlap.
3. Every displayed count is a link to its matching view: `/calendar?date=<clinic-today>`, `/follow-ups?view=due&page=1`, `/recalls?view=due&page=1`, `/lab?view=open&page=1`, or `/reminders?view=due&page=1`. Any repeated queue counts use the same destination. Keep the first three due follow-ups in API order, with patient links and due/overdue and contacted labels. Keep Find patient and Register patient shortcuts. Remove the existing numeric visit-progress summary so it does not promise an unsupported completed-only calendar filter.
4. Empty sections show zero and clear empty copy. A failed request shows unavailable, never zero or caught-up copy; other successful sections remain usable. A missing or invalid clinic timezone makes the date and agenda unavailable without fetching appointments for a guessed day. Refreshing the page fetches current data; there is no background polling.
5. An inventory-only user sees the existing inventory shortcuts and triggers no patient, calendar or coordination-queue requests. A user with no supported role sees the restricted state. A user with both an inventory and coordination role sees the coordination dashboard. Signed-out access still redirects through the existing page guard. No role permissions change.

## Changes

- **Data / migrations:** none. Counts are calculated by existing list endpoints; no stored dashboard state or audit writes.
- **API:** no new or changed endpoints or schemas. Reuse `GET /clinic/day`, `/appointments` (today's range), `/follow-ups` and `/recalls` (`view=due`), `/lab-work` (`view=open`), and S5.3's `/reminders` (`view=due`, page 1). All coordination lists permit receptionist, clinician and clinic_admin. Keep their existing tenancy and role checks.
- **UI:** extend `features/dashboard/load-dashboard.ts`, `dashboard-screen.tsx` and their tests; add the typed web reminder-list helper only if S5.3 has not already supplied it. Reuse the current dashboard layout and server-side cookie forwarding. Keep queue failures independent and make numeric summaries links. Leave actions on the destination screens.

## Out of scope

Inventory attention (S6.2), analytics (S6.3/S6.4), a separate incomplete-care queue, WhatsApp inbox/takeover counts, missed calls, document-review states, dashboard mutations, new filters, polling, dependencies and an overall navigation redesign.

## Decisions and risks

Phase 5 is unfinished in this checkout; S5.3 is approved but its reminder API/UI is absent. Build after S5.3 is integrated, including its S5.2 prerequisites. The open-items file has no dashboard blocker. Much of this dashboard already exists; verify and extend it rather than rebuild it. Recommendation for approval: reuse the existing endpoints rather than add an aggregate `/dashboard` endpoint. This keeps queue definitions authoritative and partial failures independent, at the cost of several reads and possible count changes between loading and clicking, especially across midnight. No cross-request snapshot is promised.

## How it will be verified

Map criteria 1–5 to dashboard loader/component tests: clinic-local midnight, appointment ordering and preview limits, totals beyond one page, exact links, follow-up labels, zero versus partial failure, invalid timezone, roles and mixed roles. Use API integration coverage to confirm the source lists' clinic isolation and inclusion/exclusion rules; add missing cases where needed. Run `make check` and `make web-build` with `API_BASE_URL` set.

### Click-through

1. Start PostgreSQL, migrate with `make migrate`, provision a synthetic coordinator using `make create-user`, and run `make dev` with `DATABASE_URL` configured. Use synthetic data only.
2. Sign in as a receptionist, clinician or clinic admin. Create synthetic visits and queue items through the existing pages; refresh the dashboard.
3. Open each count and check its calendar or queue destination. Check the agenda and patient links.
4. Sign in as an inventory-only user to check the inventory shortcuts.
5. To reproduce the unavailable state, run a local proxy which returns 503 for `GET /reminders` and forwards the other API requests; point `API_BASE_URL` to it and reload.
