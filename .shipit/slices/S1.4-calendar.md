# S1.4 Calendar, reschedule and cancel

Status: built
Branch: slice/S1.4-calendar
Size: L by criteria count. Kept as one slice at the developer's choice, built as six commits (see Review in pieces).

## Goal

A receptionist can see a day or week of appointments, filter by clinician, move an appointment to a new free time, and cancel it.

## Acceptance criteria

### Calendar (read)

1. **List route.** `GET /appointments?from=&to=` returns the clinic's appointments between two clinic-local dates, both inclusive, sorted by `starts_at` then `id`. Each item has `id`, `starts_at`, `ends_at`, `status`, `patient {id, full_name, display_id}`, `clinician {id, full_name}`, `appointment_type {id, name}`. This item shape is used by every appointment route in this slice.
2. **Range edges.** An appointment on the `from` day and one on the `to` day are included. One the day before `from` and one the day after `to` are not. Day edges are clinic-local midnight, not UTC. An appointment that overlaps midnight into `from` is included.
3. **Cancelled hidden.** `cancelled` appointments are not returned. All other statuses are, including `no_show`.
4. **Clinician filter.** With `clinician_id`, only that clinician's appointments return. An unknown, other-clinic, inactive or non-clinician id returns 422 naming `clinician_id`.
5. **Range rules.** 422 naming the field for: `from` or `to` missing or not a date, `to` before `from`, a span over 7 days, or `to` more than 365 days after clinic-today. Past dates are allowed. Errors never echo the value.
6. **Times and inactive patients.** Times use the clinic's offset, as in S1.3. An appointment for a patient who is now `inactive` is still listed.
7. **Roles, tenancy, no writes.** `receptionist`, `clinician` and `clinic_admin` get 200, `inventory_admin` gets 403, no session gets 401. Clinic A never sees clinic B's appointments. The route writes no audit event and no row.

### Cancel and reschedule (write)

8. **Get one.** `GET /appointments/{id}` returns the item. Unknown or other-clinic id returns 404.
9. **Cancel.** `POST /appointments/{id}/cancel` on a `scheduled` appointment sets `status` to `cancelled` and returns 200 with the item. The slot is free at once: availability offers it, and a new booking for it succeeds.
10. **Cancel rules.** Unknown or other-clinic id returns 404. Any status other than `scheduled` returns 409 `invalid_status` and changes nothing. There is no request body and no reason field.
11. **Cancel audit.** One `audit_event` in the same transaction: `entity_type` `appointment`, `action` `status_change`, `changed_fields` `["status"]`. No values and no direction. If the audit write fails, nothing is saved. A rejected cancel writes nothing.
12. **Availability when moving.** `GET /appointments/availability` accepts `reschedule_appointment_id` instead of `appointment_type_id`. Exactly one of the two is required, otherwise 422. With the appointment id, the duration is the appointment's existing length, and the appointment's own span does not block. An inactive type does not matter here. Unknown or other-clinic appointment id returns 422 naming `reschedule_appointment_id`. Without it, availability behaves exactly as in S1.3.
13. **Reschedule.** `POST /appointments/{id}/reschedule` with `starts_at` (timezone-aware) and an optional `clinician_id` moves a `scheduled` appointment. The patient and type stay. The length stays. `ends_at` is the new start plus that length. Returns 200 with the item. Extra fields return 422.
14. **Reschedule rules.** The start must be one availability would offer for that clinician, with the appointment's own span ignored. Otherwise 422 on `starts_at` with the same codes as booking (naive, past, beyond 365 days, outside hours, not on the 15-minute grid). `clinician_id` invalid as in S1.3 returns 422. Moving to an overlapping time of its own old span (09:00 to 09:15) is allowed. The same start and clinician as now returns 422 `unchanged`.
15. **Reschedule conflicts.** Not `scheduled` returns 409 `invalid_status`. A clinician clash returns 409 `slot_taken`. The same patient overlapping another of their own appointments returns 409 `patient_busy` (the appointment being moved does not count). Unknown or other-clinic id returns 404. Two reschedules of different appointments into the same slot for one clinician give one 200 and one 409 (the constraint decides).
16. **Reschedule audit.** One `audit_event`, same transaction: `appointment`, `update`, `changed_fields` `["starts_at", "ends_at"]`, plus `"clinician_user_id"` when the clinician changed. No values. If the audit write fails, nothing is saved. A rejected move writes nothing.
17. **Roles and tenancy for the three new routes.** The same three roles. `inventory_admin` gets 403, no session 401. Clinic A cannot read, cancel or move B's appointments, and cannot assign B's clinician.
18. **Contract and checks.** The route-walk test passes. `openapi.json` and `schema.d.ts` are regenerated. `make check` and `make web-build` pass.

### Web

19. **Day view.** `/calendar` shows clinic-today. `?view=day&date=YYYY-MM-DD` shows that day as a list sorted by time. Each row shows the time range ("09:15–09:45"), patient name (a link to `/patients/[id]`) with display ID, type, clinician, and a status badge for anything but `scheduled`. An empty day shows "No appointments."
20. **Week view.** `?view=week&date=...` shows Monday to Sunday of the week holding `date`, one section per day with a heading ("Mon 12 Oct") and the same rows. An empty day shows "No appointments." Today's heading is marked.
21. **Moving around.** Previous, Next and Today links step by a day or a week and keep the view and clinician. A Day / Week toggle keeps the date and clinician. A clinician select with "All clinicians" and an Apply button (a plain GET form) sets `clinician=<id>`.
22. **Bad URL values.** A bad `view` falls back to `day`, a bad `date` to clinic-today, a `clinician` not in the list to all, a `notice` that is not known to none. No error is shown.
23. **Calendar states.** "You do not have access." for a role that cannot read it, and "Something went wrong." when the API fails.
24. **Navigation.** The main nav gains "Calendar" (desktop and mobile), current on `/calendar`.
25. **Row actions.** Only a `scheduled` row shows a "Reschedule" link and a "Cancel" button. Other statuses show neither.
26. **Cancel UI.** "Cancel" first asks "Cancel this appointment?" with "Yes, cancel" and "Keep". "Yes, cancel" sends one request even on a double click. On success the calendar reloads with "Appointment cancelled." On 409 it says "This appointment can no longer be cancelled." and reloads. On 403 "You do not have access." On other failures "Something went wrong."
27. **Reschedule page.** `/appointments/[id]/reschedule` shows who, what and when it is now (patient name, type, current time), then clinician (default: current), date (default: current date, or today if that is past) and free times. States: "The clinic is closed on this day.", "No free times on this day.", "Appointment not found", "You do not have access.", "This appointment can no longer be moved." (not scheduled, no form), generic error. "Reschedule" sends one request even on double click. On 409 `slot_taken` or `patient_busy` it shows "That time is not available. Pick another." and reloads the times. On success it opens the calendar on the new date with "Appointment rescheduled."

## Out of scope

- Status changes other than cancel (S1.5). Only `scheduled` can be cancelled or moved. There is no way to undo a cancel.
- A cancel reason or any note. Free text invites clinical detail.
- Changing the type or length of an appointment, or moving it to another patient.
- A time-grid layout, drag and drop, a month view, booking from the calendar.
- Reschedule or cancel from the patient page. Showing closed days or working hours on the calendar.
- Role-based nav hiding (S7.1). Reminders or messages to the patient.

## Decisions and risks

Your calls (my recommendation first):

- **Agenda list, not a time grid (recommended).** A list per day is plain server-rendered markup and easy to test. A grid needs layout maths for overlaps. Tradeoff: no gaps at a glance.
- **Cancelled hidden, no-show shown (recommended).** The desk gets the free time back without noise. No-show stays visible. Cancelled history belongs on the patient timeline (S2.6). Alternative: show everything with a badge.
- **Only `scheduled` can be cancelled or moved (recommended).** Once a patient has arrived, the status flow (S1.5) owns what happens. Alternative: let cancel work on `arrived` too. That raises questions about care records that do not exist yet.
- **Reschedule changes time and, optionally, clinician. Not the type.** The type sets the length and later the care and stock rules. Alternative: time only, which is smaller but forces a cancel and rebook to change clinician.
- **Reschedule keeps the original length.** So a type whose default duration changed later does not silently alter existing visits, and a deactivated type does not block moving. Tradeoff: availability needs the appointment id parameter in 12.
- **Reschedule updates the row in place.** One row, one audit `update`. Alternative: cancel the old row and insert a new one, which gives a two-row history and a harder audit story. No version history is kept; the audit row lists field names only.
- **Patient name appears in the calendar response.** Only to the three roles that can already list patients. Not in logs, errors or audit rows.
- **Seven-day cap, Monday week start.** Bounded response without paging. Monday matches working-hours numbering.
- **No new dependency.**

Risks:

- Size. Twenty-seven criteria is more than S1.3's seventeen. If review of any commit shows it is too big, I will stop and say so rather than widen it. The six-commit order lets the first four commits ship even if the last two slip.
- Timezones. Day bounds are clinic-local midnights. A DST day is 23 or 25 hours, so a test uses `Europe/London`.
- Races. Cancel and reschedule take a row lock, and the exclusion constraint settles slot clashes. A test uses two real database sessions, as in the S1.3 concurrency test.
- Availability gets a second input mode (12). Without the appointment id it must stay identical to S1.3, which the existing tests will keep proving.
- The nav shows Calendar to `inventory_admin`, who then sees "You do not have access." S7.1 fixes it.

### Decisions made

- OpenAPI and `schema.d.ts` were regenerated with each API commit so `make check` stayed green, not only at the end.
- The shared slot refactor is its own commit, before the reschedule page. That is seven commits rather than the six in the plan.
- A successful reschedule opens the day view of the new date and does not keep the clinician filter, so a change of clinician is still on screen.
- A successful cancel keeps the view, date and clinician, and adds `notice=cancelled`.
- A visit that starts before the listed day and overlaps into it is shown on the first day of the view.

- A network failure on the reschedule submit says "Could not reach the server." Other submit failures say "Something went wrong."
