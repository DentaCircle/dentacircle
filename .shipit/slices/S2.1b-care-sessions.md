# S2.1b Care sessions

Status: built
Branch: slice/S2.1b-care-sessions
Size: M (second half of S2.1. About 20 criteria. If the UI part runs long, split it out as S2.1c.)

## Goal

A clinician can record, against an arrived or in-progress visit, which care items they started or completed, and the items move through the S2.1a status rules in the same step. Reception can read what was recorded.

## Acceptance criteria

### API

1. **Schema.** `alembic upgrade head` creates `care_session` and `care_session_item`. `downgrade` to `0008` removes them and the two unique constraints this migration adds. Upgrade, downgrade, upgrade works. The database refuses a second session for one visit, a session item whose result is not `started` or `completed`, the same item twice in one session, and any row pointing at a visit, patient, user or item of another clinic.
2. **Record.** `POST /appointments/{id}/care-session` with `{items: [{care_item_id, status}]}` returns 201 with the session: `id`, `appointment_id`, `patient_id`, `recorded_by_name`, `created_at`, and `items` (each `care_item_id`, `name`, `plan_title`, `status`). `status` is `started` or `completed`. One to 20 entries. An empty list, more than 20, a repeated item, any other status, or an extra field returns the standard 422 without echoing values and writes nothing.
3. **Items move through S2.1a.** Each entry goes through the same service method and transition table as `POST /care-items/{id}/status`. So `planned` to `started` or `completed`, and `started` to `completed`, are allowed. Every other pair (for example `started` to `started`, or any move out of `completed` or `cancelled`) returns 409 `item_changed` and the whole request saves nothing.
4. **Visit state.** Only a visit that is `arrived` or `in_progress` can take a session. `scheduled`, `completed`, `cancelled` and `no_show` return 409 `invalid_status`.
5. **One session per visit.** A second `POST` for the same visit returns 409 `session_exists` and changes nothing. Items missed in the first session are moved with the manual status route from S2.1a.
6. **Items must belong to the patient.** Every `care_item_id` must be an item of a plan of this visit's patient in the caller's clinic. An item of another patient or another clinic, or an unknown id, returns 422 on `items` with code `unknown_item`. The response does not say which case it was and writes nothing.
7. **Read.** `GET /appointments/{id}/care-session` returns 200 `{session: <session>}` or `{session: null}` when none was recorded. Item names are the current names.
8. **Who may do what.** `POST`: `clinician` and `clinic_admin`. `GET`: also `receptionist`. `inventory_admin` gets 403 on both. No session gets 401. A forbidden request changes nothing and writes no audit row. Any clinician may record for any visit; it does not have to be the assigned clinician.
9. **Order of checks.** 401, then role, then 404 (unknown or other-clinic visit), then 422 on the body shape, then 409 `invalid_status`, then 409 `session_exists`, then 422 `unknown_item`, then 409 `item_changed`.
10. **Inactive patient.** A visit whose patient is now `inactive` still takes a session, so open care can be wrapped up. This matches S1.5 and S2.1a.
11. **Tenancy.** Clinic A gets 404 on both routes for clinic B's visit.
12. **Audit.** In the same transaction: one `audit_event` with `entity_type` `care_session`, `action` `create`, `changed_fields` `[]`, plus the existing `care_item` `status_change` row (`["status"]`) for each item moved. No names or status values are stored. If any audit write fails, nothing is saved. A rejected request writes nothing.
13. **No double record.** The visit row and each item row are locked (items in id order, so two sessions cannot deadlock). Two requests at once for one visit give one 201 and one 409 `session_exists`. A session racing a manual status move of one of its items, or racing `complete` or `cancel` of the visit, gives one winner and one 409 (two real sessions, as in S1.5).
14. **Visit status is untouched.** Recording a session does not change the visit's status. The clinician completes the visit with the existing "Complete" action.
15. **Contract and checks.** The route-walk test passes. `openapi.json` and `schema.d.ts` are regenerated. `make check` and `make web-build` pass.

### Web

16. **Calendar link.** An `arrived`, `in_progress` or `completed` row gets a "Care session" link to `/appointments/[id]/care`, for the three roles that use the calendar. Other rows do not.
17. **Care session page.** Shows the visit (patient name, time, status badge). If a session exists it lists the items with "Started" or "Completed" and "Recorded by". If none exists and the visit is not `arrived` or `in_progress`, or the user cannot write: "No care session recorded." A load failure shows "Care session could not be loaded." 403 shows "You do not have access." 404 shows not found.
18. **Recording form (clinician, clinic_admin, visit arrived or in progress, no session).** Lists the patient's open items (planned or started), grouped by plan. Each has a choice: "No change" (default), "Started" (not offered for an already `started` item) or "Completed". "Save care session" is disabled until one item is chosen. It asks first: "Save care session? Completed items cannot be undone." with "Yes" and "Keep". One request even on a double click. A patient with no open items sees "No open care items." and a link to the care page.
19. **Outcomes.** On success the page reloads showing the session with "Care session saved." On 409 `session_exists`: "A care session was already recorded for this visit." On 409 `invalid_status`: "This visit can no longer take a care session." On 409 `item_changed`: "A care item has already changed." and the form reloads with current items. On 422 `unknown_item` or any other failure: "Something went wrong." On 403: "You do not have access." An unknown `notice` value is ignored.
20. **No clinical fields.** There is no notes field and no tooth or area field. Helper text: "Choose what was done today. No clinical notes."

    2. The recording form for a clinician with items from two plans.

## Out of scope

- Session notes, tooth or area, cost, duration, or any clinical field. Care notes stay out until a slice needs them.
- Editing or deleting a session, and adding a second session to the same visit. No undo.
- Completing the visit from this page. The calendar's "Complete" stays the only way.
- Detecting incomplete care, follow-ups and due dates (S2.2, S2.3). This slice does not decide what "session completion" means for them. See the last decision.
- Inventory use (S4.3), documents, the timeline (S2.6), and showing a session on the patient page.
- Cancelling items from a session. Cancel stays on the care page.
- Tightening the manual item status route from S2.1a.

## Decisions and risks

Your calls (my recommendation first):

- **One session per visit, saved in one step (recommended).** No draft, no session status, no edit. It is the smallest thing that records the visit and drives the S2.1a rules. Tradeoff: a clinician who forgets an item must use the manual route on the care page. Alternative: allow several sessions per visit, or edit until the visit completes. Better for forgetful use, but it needs a session status and more rules.
- **Visit must be arrived or in progress, as the roadmap says (recommended).** Tradeoff: once a clinician presses Complete, nothing can be recorded, and there is no undo (see `.shipit/open.md`). The UI helper text should make that clear, and the visit can be recorded before Complete. Alternative: also allow `completed` visits. More forgiving, but weakens "recorded during the visit".
- **Saving a session does not complete the visit (recommended).** A consultation visit may have no care items, so the visit cannot depend on a session. Tradeoff: two clicks.
- **Session results are only `started` and `completed` (recommended).** Cancelling an item is not something done in a visit. Cancel stays on the care page.
- **Keep the manual status route as it is (recommended).** Removing it would break S2.1a and leave no way to fix a missed item. Tradeoff: an item can still be completed without a session. A later small change can restrict it if the clinic wants that.
- **Any clinician or clinic_admin may record for any visit.** Not only the assigned clinician. Simple, and matches how reception covers for each other. Tradeoff: no check that the person recording was the one in the room.
- **Unique constraints on `appointment` and `care_item`.** See Changes. Alternative: single-column FKs plus a service check. That leaves the database unable to refuse a cross-clinic row, which breaks the tenancy rule, so I do not recommend it.
- **For S2.2 and S2.3, open question.** S2.3 says follow-ups are created "on session completion". A session has no status here, so that can only mean when the session is saved, or when the visit is completed. I suggest the visit completing, because that is when the clinician decides on the next step. I will not decide it here. Record your answer in PRODUCT.md when you approve, so S2.2 starts clean.

Risks:

- Item names are free text and appear on the session page. They stay out of audit rows and logs, as in S2.1a.
- The page loads all of the patient's plans to list open items, with no paging. Fine at the sizes the spec expects.
- Locking the visit row blocks a concurrent "Complete" for a moment. That is intended.

### Decisions the brief did not settle

- `patient_id` on the session is copied from the visit inside the service. The request cannot set it.
- Session lines get distinct `created_at` values, a microsecond apart, so a read comes back in save order. Postgres `now()` is one value for the whole transaction.
- A target that is not `started` or `completed` is a 422 on the body, before the transition table. An illegal `started` or `completed` pair is 409 `item_changed`.
- Unknown, other-patient, and other-clinic items all become a validation error whose type is `unknown_item`. The response code is `validation_error`, and the message is `body.items: unknown_item`.
- The calendar link is based on the visit status. Inventory admin never sees the calendar, and the page still returns 403.
- Item names on the page are the current names. The line status is the status saved on the session.
- After `item_changed`, the form drops the confirm and remounts from the current open items. A soft navigation was keeping Yes disabled.

### Unsure points

- Recording a session and then completing the visit both succeed. Completing the visit first makes the session 409 `invalid_status`. The session does not change the visit, so it cannot block a later Complete.
- Cancelling an arrived visit is already refused, because cancel is scheduled-only. A session racing that cancel wins.
- The page loads every plan for the patient. The brief accepts no paging.
- The screenshots are the narrow browser frame (891 wide), so they show the mobile header.
