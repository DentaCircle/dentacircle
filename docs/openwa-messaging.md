# OpenWA messaging design

Implementation detail for [S5.1](../.shipit/slices/S5.1-openwa-inbox.md).
Approved 2026-11-01. The slice brief governs scope; this document expands its contracts.

## Goal

Staff can send a WhatsApp message from a patient's conversation and read a reply from a test phone, through a local OpenWA container behind a replaceable provider interface.

## Acceptance criteria

1. **Local connection.** An opt-in Compose profile runs open-wa (`@open-wa/wa-automate`, image `openwa/wa-automate`), with image digest and runtime version pinned, API key, private persistent session volume and loopback-only published port. Existing `make dev` works without it. One configured account/session is bound server-side to one clinic. Pair a dedicated test account through the provider's own tools; show connected/disconnected/unconfigured in the inbox without exposing QR/session secrets. Runtime uses an explicit recipient allowlist of test phones. Only synthetic records and operational demo text are permitted.
2. **Patient link.** Staff explicitly set a full international number (E.164) for an active patient; do not infer it from the existing non-unique patient phone. It must be allowlisted, and unique per clinic/provider account. A link is immutable in this slice; repeating the same link returns it, a conflicting number/patient returns 409. A patient has at most one link. Unknown senders, groups, account/session mismatches, status broadcasts, outgoing echoes and non-text events create no patient history and trigger no reply. Direct text replies for a linked inactive patient remain readable, but inactive patients cannot be linked or sent to.
3. **Provider boundary.** `MessagingProvider` under `integrations/messaging/` supports connection state, text-send eligibility, a send result and normalized inbound events. `OpenWaMessagingProvider` owns HTTP payloads, address conversion, credentials and error translation. Core services own links, validation, persistence and permissions; they never import provider SDKs. A fake provider proves the same service/UI flow without WhatsApp in automated tests. A later Meta adapter can supply its own webhook verification and template/window restrictions; no promise of a configuration-only switch.
4. **Durable sends.** Trim outbound bodies to 1–2,000 characters, rejecting blank/oversized/extra fields with safe 422. Commit the outbound row and staff create audit before calling OpenWA, using a client-generated `request_id` unique per clinic; replay of the same patient/body/request returns the existing attempt, conflicting reuse is 409. Only the creator request dispatches it. Show `sending`, `accepted`, `failed` or `unknown`; a timeout/ambiguous provider result becomes unknown. A crash/finalization failure can leave sending: display “Sending outcome unconfirmed.” Never automatically resend either state, or redispatch a replayed request. Accepted means provider acceptance, not delivery/read. Definite rejection is failed; retry UI is out of scope. Send-state changes write field-name-only audit with the initiating staff actor. No provider body/error text enters logs, errors or audit.
5. **Incoming messages.** An authenticated provider webhook verifies a configured secret header before processing, validates the configured session and binds clinic from server configuration. Body-supplied clinic/patient ids are never trusted. Persist normalized direct text (1–2,000 characters after trimming) with provider message id, sender link, received time and nullable provider-sent time; deduplicate by clinic/account/provider message id, including concurrent deliveries. Empty/oversized/unsupported/unknown-sender events are acknowledged without storage; invalid payload is 422, bad credentials 401. Acknowledge supported messages only after commit; database failure is retryable 503. Incoming actor is “Patient via WhatsApp,” not an authenticated patient or invented staff user. No inbound AuditEvent requiring a staff actor; the message stores provenance. No incoming event or send changes booking, care, follow-up, recall or timeline state.
6. **Read access.** `receptionist`, `clinician`, `clinic_admin` may list, link and send; `inventory_admin` is 403 and no session is 401. All queries/counts/joins are clinic-scoped; foreign patient ids return 404. Inbox: one row per patient with messages, including inactive patients, ordered by latest `created_at DESC, id DESC`. History uses that same newest-first order. Both use page/page_size, default 20/max 100, and `{items,total,page,page_size}`. Known patient with no messages has empty history. Reads write nothing.
7. **UI.** `/messages` links to `/patients/[id]/messages`; add main and patient navigation. Show patient identity/status, explicit number-link form, plain-text history, direction, clinic-local timestamps, outbound actor/state and one Send form. Include a “WhatsApp test demo” notice, connection/eligibility feedback, manual Refresh, pagination, and empty/loading/error/no-access states. Block sends for inactive/unlinked/disconnected/ineligible patients. Prevent double clicks, reuse the request id for the same submission after transport uncertainty and refresh saved history to resolve it; do not silently create a second send. Incoming replies appear on refresh; no simulated-reply form.

## Changes

- Data: `messaging_contact` with UUID `id`, `clinic_id`, `patient_id`, provider/account key, E.164 number, staff creator and `created_at`; unique `(clinic_id,patient_id)`, `(clinic_id,account_key,number)` and `(id,clinic_id,account_key)`. `message` with UUID `id`, `clinic_id`, `contact_id`, direction, body, state (`received` inbound; the four outbound states above), nullable staff creator, nullable UUID `request_id`, `account_key`, nullable provider message id, `created_at`, `updated_at` and nullable provider timestamp. Composite clinic FKs to contact, patient and staff where applicable; checks for direction/state/body and required outbound actor/request id. Unique clinic/request id and clinic/account/provider-message identity; composite FK keeps message account consistent with its contact. Index contact history `(clinic_id,contact_id,created_at DESC,id DESC)` and inbox `(clinic_id,created_at DESC,id DESC)`. Message addresses stay on contacts, not patient.phone; no credentials in tables.
- API: staff `GET /messaging/connection` → `{status,can_send_text}`; `GET /messages` → inbox page with `{patient:{id,display_id,full_name,status},latest_message,message_count}` rows. `GET /patients/{id}/messaging-contact` → link or null; `PUT` on that path with `{number}` → link. `GET /patients/{id}/messages` → history page; `POST` with `{body,request_id}` → attempt (201 new, 200 replay), or safe 409 for inactive/unlinked/ineligible/conflicting request, 503 if unavailable before creating an attempt. Message shape: `{id,patient_id,direction,body,state,created_at,updated_at,provider_sent_at,created_by:{id,name}|null}`. Link shape: `{id,patient_id,number}`. Provider ids stay internal. `POST /integrations/messaging/openwa/events` → 204 for committed/duplicate/ignored events, with credential authentication instead of a staff session. Extend deny-by-default route coverage for this exact credential-protected category; do not mark it an unauthenticated public route.
- Migration: additive next revision after verifying Alembic head (expected `0021`); two new tables and constraints/indexes only. Link create and outbound writes use existing audit table, with no values. No audit/session/patient schema changes or new system user.
- Runtime/web/docs: thin routes → messaging service → repositories/models; adapter HTTP uses the standard library, no new Python/Node dependency in core apps. Optional Docker bridge, ignored local secrets/session files and webhook configuration; feature-local screens, generated OpenAPI/types, README pairing/start/refresh/disconnect instructions. Enable and persist the provider's durable inbound webhook journal if supported by the pinned release; document its finite retry/recovery limits. Container reaches the local API over a configured host address; no public tunnel or Meta account is needed for this local demo.

## Out of scope

Meta adapter/account setup, templates, automatic replies/campaigns, reminders (S5.3), slot selection/booking and coordinator status changes (S5.2), production/real patient use, attachments or group chats, historical chat import, unread/search, patient authentication, number reassignment, app-owned QR screens, delivery/read receipts, automatic send retries, background workers and timeline additions.

## Decisions and risks

**Direction agreed 2026-11-01:** local OpenWA now; replaceable provider adapters; Meta later. The revised implementation scope/schema was approved 2026-11-01. OpenWA is unofficial, requires pairing and outbound internet, can disconnect or face account restrictions, and is not a guarantee of free features. Use saved allowlisted test contacts and verify the pinned release can send/receive without a paid licence; stop if it cannot. Secrets and provider callback bodies must not be logged. Local storage does not prevent WhatsApp processing messages.

**Proposed tradeoffs:** two tables and immutable number links keep first delivery bounded; inbound messages retain provider provenance without changing the staff-only audit schema. Persist-before-send prevents silent loss of attempts, but no database transaction can undo an external send: uncertain outcomes require inspection, not blind retry. Provider eligibility supports future Meta rules without implementing templates now. S4.4 is merged per the developer; use a verified build base containing it and preserve the current checkout's unrelated changes. If a viable pinned image needs a custom bridge service or broader delivery machinery, stop and propose a split rather than expanding this slice.

Provider references: [Docker setup](https://openwa.dev/docs/getting-started/docker), [webhook contract](https://openwa.dev/docs/reference/workspaces/integrations/webhook), [capabilities/licensing and unofficial status](https://openwa.dev/). Verify against the pinned release before implementing; similarly named OpenWA projects use different APIs.

## How it will be verified

- Criteria 1–3: Compose validation; adapter fixtures from the pinned release plus provider contract tests with fake and OpenWA transports; link validation/conflicts, wrong account and allowlist tests. Mock all external traffic in routine CI.
- Criteria 4–6: service/API PostgreSQL tests for two-way persistence, roles/tenancy/FKs, safe errors/logs, paging/order, atomic audits, duplicate/concurrent requests and callbacks, provider rejection/timeout, database failure before/after send, crash-left sending states and no redispatch. Confirm unchanged business state/timeline. Test the explicit credential-authenticated route classification and every denied callback case.
- Criterion 7: Vitest for links, states/forms, literal HTML text, timestamps, refresh, uncertainty/request-id reuse and empty/error/inactive/no-access views. Run `make api-types`, `make check` and `make web-build`; report unavailable checks.
- Manual proof with dedicated allowlisted phones and synthetic records: pair, send in-app, reply on WhatsApp, refresh, restart without losing history, disconnect, and replay a callback without duplication. Check current saved-contact licence requirements. If pairing/phones are unavailable, report live integration as unverified.
- Visual proof in `.shipit/proof/S5.1/`: inbox; two-way test conversation; empty/unlinked view; disconnected/uncertain-send state; inactive history. Never capture phone numbers, QR codes, session credentials or real conversations; redact test-account identifiers too. Include sanitised callback/send samples and the pinned versions.
